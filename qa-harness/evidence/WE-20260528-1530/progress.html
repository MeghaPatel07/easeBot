WE-20260528-1530 — translation withRetry tuning

Branch: fix-WE-20260528-1530 off Bug-Resolve-claude

File: easebot-backend/src/services/translation.ts

Severity: P2 — perf tail-latency on chat critical path

Root cause

Both detectLanguage and translateText wrap their fetch in withRetry(fn, { maxRetries: 2, baseDelayMs: 500, maxDelayMs: 4000 }). The chain under Azure 429 / 5xx blooms to ~8.5s tail. Because every non-English chat turn runs both inbound detect-and-translate AND outbound translate, the user sees up to ~17s of pure translator wait in the worst case.

Latency math

Before {2, 500, 4000}After {1, 200, 800}
Attempts on full failure3 (initial + 2 retries)2 (initial + 1 retry)
Sleep #1 (attempt 0 → 1)500ms + jitter ≈ 500-650ms200ms + jitter ≈ 200-260ms
Sleep #2 (attempt 1 → 2)min(1000, 4000) + jitter ≈ 1000-1300msn/a
Backoff overhead worst case~1.95s~0.26s
Total tail (3× ~500ms API call + sleeps)~3.45-8.5s~1.0-1.5s
Critical-path tail per chat turn (inbound + outbound)~7-17s~2-3s

Why these specific knobs

  • maxRetries: 1 — Azure translator 429s replenish per-second; one fast retry is sufficient. More importantly, retries here multiply per-chat-turn: inbound and outbound each get their own retry budget, so going from 2 → 1 means 4 → 2 max retries per message turn.
  • baseDelayMs: 200 — Translator rate-limit reset is sub-second; 200ms is enough delay to let the next 1-second token bucket open without blocking the user perceptibly.
  • maxDelayMs: 800 — Caps the single retry sleep so a worst-case chain stays under ~1.5s end-to-end.

Why we don't strip retries entirely

Translator already sits behind translatorCircuitBreaker (failureThreshold: 3, windowMs: 60s, cooldownMs: 30s). Compounding: retries handle the transient single-request flakes, the breaker handles sustained outages. Both stay; only the retry envelope tightens. The fallback paths ('en' for detect, original text for translate) already gracefully degrade if the breaker trips.

Out of scope (separate tickets recommended)

  • Per-thread cache of the detected user language (ticket suggestion #2).
  • Server-Timing header surfacing (ticket suggestion #3).
