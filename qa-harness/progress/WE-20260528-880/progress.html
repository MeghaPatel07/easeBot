Bug summary

On mobile (<768px) the Settings modal renders one tab at a time. When the user scrolls deep in a tab (eg. Plan & Billing), taps Back to the list, then re-enters the same tab, the content remounts and scroll resets to top. UX paper cut on tabs with lots of content.

Audit trail

2026-05-29 — step 1
Read ticket WE-20260528-880 and SettingsShell.tsx end-to-end.
Mobile flow uses a single mobileShowingContent boolean. The content view renders <ActiveComponent /> inside <div className="flex-1 overflow-y-auto p-4">. Going Back flips mobileShowingContent=false which unmounts that scroll div, losing scrollTop. Desktop (≥1024px) and tablet (768–1023px) keep the scroll container mounted across tab changes, so they're unaffected — fix only needs to touch the mobile branch.
2026-05-29 — step 2
Diagnosis & approach.
Smallest-diff fix: add a scrollPositionsRef (a Map<tabId, number>) inside SettingsShell. Wrap the mobile back & tab-switch handlers so they snapshot scrollTop before unmounting. Attach a ref to the mobile scroll container and, on mount/when activeTab changes, restore the saved scrollTop via requestAnimationFrame (waits for layout). No new files, no new deps, no new hooks needed — fits inside SettingsShell.tsx.
2026-05-29 — step 3
Implemented the fix in src/pages/settings/SettingsShell.tsx.
Added scrollPositionsRef (Map), mobileScrollRef (ref to the mobile content scroll div), a helper snapshotMobileScroll() used by the Back button and by the tab-switch path inside the content view, and a useLayoutEffect that restores scroll on mount of the content view (and whenever activeTab changes while the content view is open).
2026-05-29 — step 4
Lint + typecheck.
tsc --noEmit -p tsconfig.app.json → zero new errors related to SettingsShell.tsx (30 pre-existing project-wide errors, all in services/components I did not touch — Firebase types, payment service, etc.).
eslint src/pages/settings/SettingsShell.tsx → zero new warnings/errors from my diff. The remaining 3 ESLint errors on this file are pre-existing user: any prop typings on the side-nav components — out of scope for this ticket.
2026-05-29 — step 5
Edge-case hardening: scroll snapshot on tab change while in content view.
Initially I only snapshotted on the Back tap. But if the user uses browser back/forward (which mutates ?settings=<tab>) while still in the mobile content view, activeTab changes without going through Back. To cover that, I moved the per-tab snapshot into the useLayoutEffect cleanup — it captures the OLD tab's scrollTop just before React re-runs the effect for the new tab. Best of both: Back-button path is explicit (because React clears the ref before cleanup when the JSX unmounts), and in-place tab changes are caught automatically.
