Bug summary

Tab A and Tab B both open the same /notes/:id, both edit, both save. With no version field, no etag, and no updatedAt precondition on the Firestore write, last-writer-wins — Tab A's content is silently destroyed by Tab B's save. P0 silent data loss. Note: an A1 (Approach B) conflict banner already exists, but it only fires on inbound remote changes while local edits are still buffered. The clobbering save path itself had no precondition check.

2026-05-29 — design
Optimistic-lock precondition via runTransaction + lastSeenUpdatedAt millis.
(a) Add a NoteConflictError + extend updateNote() to accept an expectedUpdatedAtMillis. When provided, run a Firestore transaction: read current updatedAt, compare with expected; if different, throw NoteConflictError with the remote doc snapshot; otherwise commit. (b) Track lastSeenUpdatedAtRef from the subscription in useNoteEditor (parallel to prevRemoteContentRef); thread it into all 4 write sites (flushPending, scheduleSave, save, unmount). On NoteConflictError, restore pending edits, set the conflict banner from the returned remote snapshot. This reuses the existing UI without any banner-component changes.
