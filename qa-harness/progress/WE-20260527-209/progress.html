WE-20260527-209 — /api/transcribe leaks server temp paths via ffmpeg stderr

Severity P1 · Category security/CWE-209 · Repo easebot-backend · Branch fix-WE-20260527-209

Diagnosis

  • src/services/stt.ts:77 wrapped ffmpeg error as new Error(`Audio conversion failed: ${err.message}`) — ffmpeg's err.message embeds the absolute temp path (/var/folders/.../viva-input-<ts>.webm).
  • src/controllers/transcribeController.ts:61 echoed err.message straight to the client: res.status(500).json({ error: err.message ?? 'Transcription failed' }).
  • Composite leak: server filesystem layout + millisecond process timestamp + confirmation that ffmpeg is in use.

Fix

  • Controller: replace dynamic err.message in the 500 response with a static { error: 'Audio could not be processed', code: 'TRANSCRIBE_FAILED' }. Continue to console.error the full err for ops, and keep the PostHog transcription_failed capture intact (uses err.code/err.name, not message).
  • STT service (defense in depth): scrub absolute paths (POSIX /var/folders/..., /tmp/..., and Windows C:\...) from err.message before constructing the wrapped Error, replacing them with the literal <tmp>. Raw error still logged to console.error first.

Verification

  • tsc — clean (npx tsc --noEmit)
  • npm run test:all — pass (phase1 cache + controller, phase2 phrases, langfix — 12+8+15 tests)
  • Updated test — STT throws → 500 with scrubbed body asserts no /var/folders, no viva-input-, no Invalid data, and exact body shape.
  • Smoke run via patched controller with the ticket's exact leaked string returns: 
    { "_status": 500, "error": "Audio could not be processed", "code": "TRANSCRIBE_FAILED" }
