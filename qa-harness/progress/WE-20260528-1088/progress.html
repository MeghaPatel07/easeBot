Bug summary

Thread search in ChatSidebar uses a 500ms debounce for analytics tracking. The ticket flags two a11y concerns under WCAG 2.1.1 (Keyboard) and 4.1.3 (Status Messages):

  • No aria-busy="true" on the thread list while the debounce timer is pending.
  • No aria-live announcement of the search result count (e.g. "3 threads match Goa").

Investigation notes

The original ticket title mentions "focus trap" — but a careful read of ChatSidebar.tsx shows there is no focus trap:

  • No onKeyDown on the search input that calls preventDefault().
  • No inputRef.current?.focus() being called mid-debounce.
  • The list filtering (filteredThreads) is fully synchronous — it re-derives on every searchQuery change. Only the analytics track('thread_searched', ...) fire is debounced (500ms, line 153).
  • Tab / Switch Control keyboard navigation is not blocked. The Input is a plain shadcn <Input> with only onChange.

The actual ticket body (Expected section) confirms this: the requested fix is the a11y status-messages pair, not removal of a trap.

Fix shape

Smallest viable change in src/components/chat/ChatSidebar.tsx:

  1. Track debounce-pending state with a single useState<boolean> flag (isSearchDebouncePending).
  2. Set true when typing starts a new debounce; clear inside the timer callback.
  3. Add role="region" + aria-busy={isSearchDebouncePending} + aria-live="polite" wrapper around the thread results.
  4. Add a visually hidden aria-live="polite" announcement region with the result count: "N threads match QUERY".
