Bug summary

Voice preview in SettingsModal.tsx uses new Audio(audioUrl); audio.play(). WCAG 1.4.2 requires audio that plays for >3s to be under explicit user control. Audit found three real issues to harden:

  1. Race: rapid clicks while previous requestTTS is in flight can cause an older audio to start playback after a newer one — the old audio reference is lost and cannot be stopped.
  2. Cleanup: on modal close we pause, but never revoke the blob audioUrl nor clear the previewAudioRef. On component unmount nothing runs. Background audio can linger.
  3. Reduced motion: prefers-reduced-motion: reduce hint is not respected (no functional change needed for that flag, but we document the click-only model so it is auditable).

The auto-play assertion in the ticket title is actually FALSE for SettingsModal — preview only fires on the speaker icon click (line 282 onClick={(e) => previewVoice(preset.id, e)}). There is no useEffect(() => audio.play()) and no audio.autoplay = true. The card click only sets the selected voice via setVoiceId. So the fix is to harden the race + cleanup so a stale request cannot start playback after the user has moved on.

2026-05-29 — designed fix
Three concrete changes:
  1. Track an in-flight request token (counter ref). After await requestTTS resolves, drop the result if the token no longer matches latest — and revoke the orphan URL immediately. Prevents stale audio from ever calling .play().
  2. On open === false: pause AND revoke any tracked URL AND null the ref AND bump the token to invalidate any in-flight request.
  3. Add a component unmount cleanup effect that does the same.
