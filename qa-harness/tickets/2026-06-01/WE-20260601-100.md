## Description

For logged-in users the current turn's user message is sent to the LLM **twice**: once inside the
recalled history and once as the live turn. This wastes prompt tokens (which are billed to the user
via tokenMeter), can confuse the model (it sees the same user line repeated), and on the very first
turn of a thread the entire "history" is just a duplicate of the message being answered.

Root cause is an ordering/contract overlap between the frontend and backend:

1. `useChat.sendMessage` (logged-in branch) **persists the user message to Firestore first**:
   `await addMessage(threadId, { role: 'user', content: text, ... })` — `useChat.ts:481-493`.
2. It then calls `streamChatMessage(...)` with `threadId` set and `history: undefined`
   (`useChat.ts:497`: `const history = user ? undefined : ...`).
3. Backend `handleChatStream` calls `getChatHistory(threadId, providedHistory)` (`chatController.ts:1211`).
   With a `threadId` present, `getChatHistory` queries Firestore for the last 10 messages ordered by
   `timestamp desc` (`chatController.ts:388-397`) — which now **includes the user message just written
   in step 1**.
4. The backend then calls `streamCallAzureAI(effectiveHistory, userMessageForLLM, systemPrompt, ...)`
   (`chatController.ts:1369`). `userMessageForLLM` is the same current message (`injectAttachmentsIntoUserMessage(englishText, ...)`), appended AFTER history. No de-dup of the
   trailing user message is performed in `getChatHistory` or before the LLM call.

Net effect: `messages = [ ...history(includes current msg), userMessageForLLM(current msg) ]`.

(The guest path is unaffected — guests send `history` from in-memory `messagesRef` which excludes the
just-added bubble, and have no `threadId`, so `getChatHistory` returns the provided array.)

## Steps to reproduce (by reading)

1. Logged-in user sends "Plan my sangeet" on a brand-new thread.
2. `useChat.ts:466` creates the thread, `useChat.ts:481` writes the user message to Firestore.
3. Stream POST sends `{ threadId, history: undefined, message: "Plan my sangeet" }`.
4. Backend `getChatHistory(threadId, undefined)` returns `[{role:'user', content:'Plan my sangeet'}]`.
5. Backend issues LLM call with messages `[system, {user:'Plan my sangeet'}, {user:'Plan my sangeet'}]`.

## Expected

The current turn's user message appears exactly once in the LLM context. History should contain only
*prior* turns (everything before the message being answered).

## Actual

The current user message is present twice — once via Firestore-recalled history, once as the live
turn. Token usage is inflated (prompt tokens charged include the duplicate) and the model sees a
repeated user line; on turn 1 the "history" is a pure duplicate.

## Evidence

- `useChat.ts:481-493` writes the user message to Firestore before streaming.
- `useChat.ts:497` sets `history: undefined` for logged-in users.
- `chatController.ts:388-397` `getChatHistory` returns last-10 by timestamp desc, no trimming of the trailing user message.
- `chatController.ts:1369` LLM call appends `userMessageForLLM` after `effectiveHistory`.
- STATIC — needs live re-verify (capture the outgoing Azure `messages[]` array) when MCP+backend restored.

## Notes

Fix options: (a) in `getChatHistory`, drop the last message if its role is `user` and it equals the
current `message`; or (b) fetch `historyLimit + 1` and slice off the trailing current-turn user
message; or (c) have the frontend persist the user message AFTER kicking off the stream (riskier for
durability). Suggested specialist: `fix-backend-api`.
