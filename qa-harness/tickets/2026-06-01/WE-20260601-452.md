## Description

`ChatRequestSchema.mode` is `z.enum(['planner', 'stylist', 'knowledge']).optional()` (chat.ts:6). But `assistant` is a first-class mode: it is the default returned by `detectMode` (modeRouter.ts:61), it has its own prompt (`getAssistantPrompt`), its own tool binding branch (`getToolsForMode` case `'assistant'`, chatController.ts:270), and `Mode` includes it.

Because `'assistant'` is not in the enum, a client that explicitly sets `mode: 'assistant'` on the validated `/chat` route is rejected with HTTP 400 "Validation failed". The frontend's only way to reach assistant mode is to omit `mode` entirely and hope the keyword router falls through to it — there is no way to *pin* assistant mode (e.g. to stop the router from misclassifying a borderline message into planner/stylist/knowledge).

This is a contract gap: the set of modes the API documents (schema enum) is a strict subset of the modes the pipeline actually supports. It also interacts with WE-20260528-1403 (the `styler` typo) — both are symptoms of the schema enum drifting from the canonical `Mode` union in `types.ts`.

## Steps to reproduce (by reading)

1. chat.ts:6 — enum is `['planner','stylist','knowledge']`.
2. modeRouter.ts:43-62 — `detectMode` default-returns `'assistant'`; the scores record includes `assistant`.
3. chatController.ts:265-291 — `getToolsForMode` has an explicit `case 'assistant'`.
4. Send `{ "message": "hi", "mode": "assistant" }` to `/chat` → validateBody fails the enum → 400.

## Expected

The mode enum matches the canonical `Mode` union (`assistant`, `planner`, `stylist`, `knowledge`), so any supported mode can be explicitly requested. Ideally derive the enum from the `Mode` type / a shared constant so it cannot drift.

## Actual

`mode: 'assistant'` is rejected with 400 even though assistant is the default, fully-implemented mode.
