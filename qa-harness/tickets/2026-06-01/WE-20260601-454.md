## Description

`handleTTS` catches synthesis failures and returns the raw error string to the client:

```
res.status(500).json({ error: err.message ?? 'TTS generation failed' })
```

`err.message` here is whatever Azure Speech SDK / network layer threw — it can contain the Azure region/endpoint, SDK error codes, key-config diagnostics, or rate-limit detail. This is the same provider-leak class that was explicitly fixed for the chat path in WE-20260527-353 ("stop echoing arbitrary err.message; log it server-side and return a generic 500"). The chat controller now logs server-side and returns `{ error: 'Internal server error' }`; the TTS controller still leaks.

Assertion-eval angle: a response must not leak upstream provider identity or internal diagnostics. The TTS 500 path violates this. It is also a poor UX signal — the frontend can't distinguish a transient Azure outage from a bad-input error, and shows a raw SDK string to the user.

## Steps to reproduce (by reading)

1. ttsController.ts:80 — catch block returns `err.message` verbatim with status 500.
2. Compare chatController.ts:1142 (post -353 fix) — returns generic `{ error: 'Internal server error' }` and logs `err` server-side only.

## Expected

Log the full error server-side; return a generic, stable client error (e.g. `{ error: 'tts_failed', message: 'Audio could not be generated right now. Please try again.' }`). Map a 429 to a friendly rate-limit message. Never echo `err.message`.

## Actual

Raw Azure Speech error string is returned to the browser in the 500 body.
