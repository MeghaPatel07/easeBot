## Description

`ChatRequestSchema` (the Zod validator) has drifted badly from the real wire contract the controller
actually reads (`ChatPayload`). Because `validateBody` does `req.body = result.data` and Zod objects
**strip unknown keys by default**, every field present on `ChatPayload` but absent from
`ChatRequestSchema` is silently deleted from `req.body` before the handler runs.

Fields the frontend sends + the controller reads, but which `ChatRequestSchema` does NOT declare
(so they get stripped on any validated route):

- `audioBase64`  → voice-input transcription path (`processInbound(message, audioBase64, ...)`)
- `userPersonalization` → nickname / voice / tone injection
- `imageBase64` (schema instead has a never-read `imageData`) → vision + image-edit
- `lastGeneratedImageUrl` → iterative image editing + "save that image to my note"
- `styleMemory` → cross-generation style consistency
- `skipImageGeneration`
- `attachments` → notes/checklists/timeline/image context for the turn
- `requestId` → explicit Stop / cancellation registry

Additionally the schema declares two keys the controller never reads: `imageData` (should be
`imageBase64`) and `toneSettings` (personalization is carried by `userPersonalization`).

Today this is mostly latent because the **active** path is `POST /api/chat/stream`, which does NOT
mount `validateBody` (the SSE wrapper in `routes/chat.ts:37-72` skips it), and the non-stream
`POST /api/chat` route — which DOES validate — has no live frontend caller (`functionsService.ts`
only wires `streamChatMessage`).

The risk is concrete and imminent: the in-review PR #59 (WE-20260528-103) explicitly states it
"mounted validateBody(ChatRequestSchema) on POST /api/chat/stream (was missing)". If that lands while
the schema is still missing these fields, it will **strip audio, personalization, attached/edited
images, last-image context, style memory, attachments, and requestId from every streamed chat
request** — silently breaking voice input, image editing, attachments, personalization, and Stop.

## Steps to reproduce (by reading)

1. Compare `schemas/chat.ts:3-20` against `types.ts:27-58` (ChatPayload) and the destructure at
   `chatController.ts:651` / `chatController.ts:1187`.
2. Note the schema lacks `audioBase64`, `userPersonalization`, `imageBase64`, `lastGeneratedImageUrl`,
   `styleMemory`, `skipImageGeneration`, `attachments`, `requestId`; uses `imageData` not
   `imageBase64`; and adds an unread `toneSettings`.
3. `validateBody` (`middleware/validateRequest.ts:15`) reassigns `req.body = result.data`, dropping
   unknown keys.

## Expected

`ChatRequestSchema` is the single source of truth and accepts every field `ChatPayload`/the controller
reads, so it can be safely mounted on `/api/chat/stream` without dropping functional payload.

## Actual

Schema is missing ~8 fields the controller relies on, renames `imageBase64`→`imageData`, and includes
2 unused fields. Any validated route silently drops voice/image/personalization/attachment/cancel
payload.
