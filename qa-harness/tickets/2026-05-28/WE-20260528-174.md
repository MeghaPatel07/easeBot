## Description

If the user deletes the currently active thread while a streamed message response is still arriving, the abort controller is not necessarily fired, and the subscription unsub doesn't tear down until the next render cycle. Resulting Firestore writes can attempt to write to the doomed thread / messages collection (silent Firestore rule denials) or briefly re-create the thread doc if `addMessage`'s `updateDoc(doc(db,'chats',threadId),{updatedAt})` resurrects it via `merge` semantics. The sidebar then shows a ghost thread for a tick.

## Steps to reproduce

1. Open a thread. Send a long-running query (e.g. "Plan an entire 5-day wedding").
2. While the assistant is mid-stream, open the sidebar menu for that thread → Delete.
3. Watch the sidebar.

## Expected

Stream aborts cleanly, no ghost thread, the deletion holds.

## Actual

Brief flicker — thread reappears for ~200–800ms with a partial message preview before vanishing. Subsequent reload confirms thread is gone, but the in-tab UX is jarring.

## Evidence

- Screenshot(s): `qa-harness/evidence/WE-20260528-174/screenshots/`
- Console log: `qa-harness/evidence/WE-20260528-174/console.log` (look for FirebaseError: PERMISSION_DENIED writes to deleted thread)

## Notes

Wire deleteThread to (1) abort inflight `abortControllerRef.current?.abort()`, (2) clear `activeThreadIdRef.current` synchronously, (3) ensure no in-flight `addMessage` is scheduled.
