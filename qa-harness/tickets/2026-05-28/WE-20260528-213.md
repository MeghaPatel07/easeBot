## Description

Three different rate limiters return three different JSON shapes on 429:

- `apiRateLimiter` → `{"error":"Too many requests, please try again later."}` (no code, no retryAfter)
- `chatBurstRateLimiter` → `{"error":"chat_burst_limit","retryAfter":10}` (machine-friendly code, retryAfter)
- `imageRateLimiter` → `{"error":"Too many requests, please try again later."}` (same as apiRateLimiter)

The frontend would need three branches to detect rate-limit vs. parse the human string, and only `chat_burst_limit` exposes `retryAfter` — so the UI can't show a uniform "you can resend in 10s" countdown for the other two.

## Steps to reproduce

```bash
# Burn the chat burst limit (10 in 10s)
for i in $(seq 1 11); do curl -s -X POST http://localhost:3001/api/chat \
  -H "Content-Type: application/json" -d "{\"message\":\"hi $i\"}"; done
# Last response: {"error":"chat_burst_limit","retryAfter":10}

# Burn the general api limit (30 in 60s) — hits another endpoint
# Response: {"error":"Too many requests, please try again later."}
```

## Expected

All limiters return the same shape:

```json
{ "error": "rate_limited", "code": "RATE_LIMITED", "retryAfter": <seconds> }
```

…with `Retry-After` header set (standardHeaders is already on, so this is mostly free).

## Actual

Inconsistent shapes, retryAfter only on chat_burst_limit.
