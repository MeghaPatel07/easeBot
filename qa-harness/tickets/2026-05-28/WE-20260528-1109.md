# WE-20260528-1109 — Image post-processor "compress cascade" linearly retries 4 quality levels — should binary-search

**Severity:** P3
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Image processing algorithm
**File:** `easebot-backend/src/services/imagePostProcessor.ts:64-83`
**Discovered:** 2026-05-28

## Symptom
The `compressImage()` cascade iterates qualities `[92, 85, 78, 70]` sequentially, re-encoding the full buffer from scratch each iteration:
```ts
for (const quality of [92, 85, 78, 70]) {
  const compressed = await sharp(inputBuffer).jpeg({ quality, mozjpeg: true }).toBuffer()
  if (compressed.length <= MAX_IMAGE_BYTES) return compressed
}
```

Measured on a noisy 5.7MB 2400×2400 JPEG: the cascade runs all 4 attempts (no early-exit triggers under 2MB) in **6416ms**. Worst case it then re-resizes and re-encodes — adding another ~1s.

## Root cause
- mozjpeg is ~2× slower than libjpeg; using it 4× is wasteful.
- No binary search: should converge in ~2 attempts.
- Re-decoding the original buffer each iteration costs JPEG decode time per iteration (~150-300ms).

## Suggested fix
```ts
// Try q=80 first (median of range). If too big, try 70; if still too big, resize.
// If under, try q=88; if under that, q=92. Total: 2-3 attempts not 4.
```
Or use Sharp's `withMetadata: false` + reuse the decoded pixel buffer (`sharp.raw()`) across attempts to skip per-iteration decode.

## Expected impact
Compress cascade: 6.4s → ~2s. Combined with -1103 (move off request path) the user-perceived latency on image generation drops sharply.
