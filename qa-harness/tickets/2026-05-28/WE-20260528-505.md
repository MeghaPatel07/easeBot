## Description

Round-trip Flow F: user generates an image in image mode → wants to ask "what color flowers are in this image?" → there is **no UI affordance** to re-attach the just-generated image as a vision input for the next turn.

Workarounds the user would have to do:
1. Right-click the rendered image → "Save image as..." → upload it back via the image-attach button. (For guest users the image is a `data:image/png;base64,...` URI — saving works but is friction.)
2. Worse: if they manage to grab the b64 and the FE infers `image/jpeg` (the common default for camera uploads), the BE Azure call rejects with `400 You uploaded an unsupported image. Please make sure your image is valid.` because the actual bytes are PNG.

## Steps to reproduce

1. Open chat in image mode, prompt: "a beach wedding setup".
2. Wait for the image to render.
3. Try to send a follow-up like "make the arch taller" referencing the image — chat mode has no "use last generated image" button.
4. If you save+re-upload but use the wrong mime, you get the unsupported-image error.

## Expected

- Each rendered assistant image should have a "Use as next attachment" / "Refine this" action that pre-fills the input with the image attached + correct mime.
- For image mode, this is implicit in the edit-pipeline; for chat-mode vision Q&A it should be exposed.
- Backend should sniff bytes (PNG/JPEG/WebP magic bytes) and infer mime rather than trust the client header — when the bytes are PNG and mime says JPEG, prefer the byte truth.

## Actual

User must download → reupload manually, and risk a 400 if mime is wrong.
