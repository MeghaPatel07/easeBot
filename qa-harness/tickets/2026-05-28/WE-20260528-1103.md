# WE-20260528-1103 — Sharp image post-processing pipeline: 8 seconds on a 2MB image (upscale+webp)

**Severity:** P1
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Image generation backend
**File:** `easebot-backend/src/services/imagePostProcessor.ts`
**Discovered:** 2026-05-28

## Symptom
Direct Sharp benchmark on a noisy 5.7MB 2400×2400 JPEG (representative of a model-generated image after base64 decode):
- `metadata`: <1ms
- `resize 2x lanczos3`: **240ms**
- `webp q=90` alone: **882ms**
- `jpeg mozjpeg q=92` alone: **2171ms**
- **Full pipeline (`upscale + webp`): 7975ms (~8s)**
- **Compress cascade (4 attempts at q=92→70): 6416ms**

In the worst case (upscale + webp + cascade triggered because result > 2MB) a single image post-processing pass can take **~14s** before Firebase Storage upload even starts. This is fully serial on the backend.

## Root cause
`postProcessImage()` runs all stages synchronously per image. The cascade in `compressImage()` re-encodes the buffer from scratch each iteration instead of binary-searching or starting from the prior compressed buffer. `mozjpeg` is ~2× slower than libjpeg for marginal quality benefit at q=92.

## Suggested fix
1. **Default to JPEG NOT mozjpeg** for compress cascade unless tier=premium — saves 50% on the slow path.
2. **Binary-search the quality** instead of linear scan [92,85,78,70] — typically 2 attempts not 4.
3. **Skip upscale path** in stream/chat flows where the user is waiting on SSE — they don't need 4K wedding inspo. Reserve upscale for download/gallery-export.
4. **Move post-processing off the request path**: emit the raw image to the client immediately, post-process async, swap URL when ready (the existing imageStorage flow supports the swap).
5. Re-measure: target ≤ 1s on the request-blocking path; the upscale tail can take 8s asynchronously.
