## Description

Journey 4 (mode-switching) surfaces a triple mismatch:

1. **Client Mode union** (`types/index.ts:4`): `'planner' | 'stylist' | 'knowledge' | 'assistant'`. Commented-out: `'therapist' | 'consultant'`.
2. **Server schema** (`schemas/chat.ts:6`): `z.enum(['planner', 'styler', 'knowledge']).optional()`.
3. **Server `/api/chat/stream` enforcement**: permissive — accepts `stylist`, `assistant`, anything, falls back silently to a default router.

Consequences I reproduced:

- `POST /api/chat {mode:'stylist'}` → **HTTP 400** `Invalid enum value. Expected 'planner' | 'styler' | 'knowledge', received 'stylist'`
- `POST /api/chat {mode:'assistant'}` → **HTTP 400** same shape
- `POST /api/chat/stream {mode:'stylist'}` → **HTTP 200**, returns a planner-style answer (mode in `d` event was `planner`, NOT `stylist`)
- Default chat (no mode) works on both paths because the field is `.optional()`.

Client `stylist` (with-T) vs server `styler` (no-T) is a straight spelling difference. The `assistant` mode is intentionally not in the server enum at all (it's the implicit default), but the client union promises it as a first-class value.

## Steps to reproduce

```bash
# 400 from non-stream
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"message":"hi","history":[],"mode":"stylist"}' \
  http://localhost:3001/api/chat
# → {"error":"Validation failed","details":[{"received":"stylist","options":["planner","styler","knowledge"], ...}]}

# 200 from stream (silently lies about mode)
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"message":"hi","mode":"stylist"}' \
  http://localhost:3001/api/chat/stream
# → SSE id:1 data:{"t":"c","v":"Hi"} ... eventual d:{... "mode":"planner" ...}
```

## Expected

- Single source of truth for mode names (pick `stylist` OR `styler` — recommend `stylist`).
- Both endpoints reject the same set of inputs.
- Stream endpoint should not silently swallow an invalid mode.

## Actual

- Three inconsistent surfaces. Image mode buttons in the UI work because they map through `useChat`'s `modeArg`-omit path (defaults to omitted = no mode field). But any client code that ever sends explicit `mode:'stylist'` to `/api/chat` (the non-stream path used by image gen) gets a 400 instead of a graceful answer.
