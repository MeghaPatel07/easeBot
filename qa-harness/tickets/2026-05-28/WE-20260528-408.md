## Description

`plannerTools.ts` exposes `create_reminder` (alias `save_reminder`) but **no `delete_reminder`, `update_reminder`, or `create_recurring_reminder`** tool to the LLM:

```
case 'save_reminder':
case 'create_reminder': { … }
```
…and that's the only reminder branch in `executeToolCall`.

Backend service `reminderService.ts` exposes `updateReminder` (line 251) and `deleteReminder` (line 264), but they're never wired to a tool definition. When the user says:
- "Delete that reminder I just made" → LLM has nothing to call → either hallucinates "I've deleted it" or apologizes and asks the user to do it manually.
- "Change my Haldi reminder to 8 PM" → same.
- "Remind me every Friday at 5 PM" → no `recurrenceRule` parameter; LLM either creates a single one-shot or apologizes.

Sprint 2 brief lists "calendar event creation, recurrence, edit, delete, conflict with existing event" as the focal areas for `save_reminder`. Three of five are not implemented.

## Steps to reproduce

1. Planner mode, "Remind me about my florist meeting tomorrow at 10 AM."
2. Confirm — reminder created (toast).
3. "Actually, change that to 11 AM."
4. Observe: LLM responds "Sure, I've updated it" but **no tool call fires** (check the SSE stream — only `t:'d'` final, no `t:'tool'` event).
5. Refresh the reminders page → reminder still says 10 AM.

## Expected

Wire `update_reminder` and `delete_reminder` tools backed by `reminderService.updateReminder` / `deleteReminder`. Add `recurrenceRule` parameter to `create_reminder` (RRULE string for FREQ=WEEKLY etc.). Implement conflict-detection by querying existing pending reminders within ±15 min of the proposed time.

## Actual

- Two of three CRUD ops are missing.
- LLM hallucinates success in natural language, breaking trust.
- No recurrence at all.

## Evidence

- Source: `plannerTools.ts:293-331` — only `create_reminder` handler.
- Source: `reminderService.ts:251,264` — `updateReminder` + `deleteReminder` exist, never called from tool layer.
