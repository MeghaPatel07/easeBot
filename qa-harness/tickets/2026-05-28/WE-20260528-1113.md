# WE-20260528-1113 — `imagePostProcessor.ts` re-uses `sharp(buf)` for upscale + format-convert, decoding source twice

**Severity:** P3
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Image pipeline efficiency
**File:** `easebot-backend/src/services/imagePostProcessor.ts:32-47`
**Discovered:** 2026-05-28

## Symptom
The pipeline calls `sharp(buffer).resize(...).toBuffer()` then `sharp(buffer).webp().toBuffer()` — the source buffer is JPEG-decoded twice, the upscaled buffer is re-encoded as PNG (Sharp's default intermediate) then re-decoded for the WebP step.

Measured: standalone `webp q=90` on 5.7MB JPEG = 882ms. Standalone `upscale 2x lanczos3` = 240ms. Combined pipeline (current code) = **7975ms**, not 1.1s, because of the double-decode + intermediate buffer allocation.

## Root cause
Sharp's instance is single-use: every chained operation needs a new `sharp()` call which restarts the decode. The chain `.resize(...).webp(...)` on a *single* sharp instance is much faster than two sequential `sharp(buf).x().toBuffer()` calls.

## Suggested fix
```ts
// Before (current):
buffer = Buffer.from(await sharp(buffer).resize(...).toBuffer())
if (options.outputFormat === 'webp') {
  buffer = Buffer.from(await sharp(buffer).webp({ quality: 90 }).toBuffer())
}

// After:
buffer = Buffer.from(
  await sharp(buffer)
    .resize(meta.width * 2, meta.height! * 2, { kernel: 'lanczos3' })
    .webp({ quality: 90 })   // chain on same instance
    .toBuffer()
)
```

## Expected impact
Pipeline 7975ms → ~1500ms (only one full decode, in-process resize → encode chain). Combined with -1103 (off-request-path) and -1109 (binary search) this is a 5-10× speedup on the slow path.
