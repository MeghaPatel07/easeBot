## Description

If the backend stamps `users/{uid}.onboardingCompleted = true` after the first message (server-side observer), the in-tab Index.tsx gate keeps relying on the frozen AuthContext profile. The onboarding modal does not pop again in the same session (because local state already suppressed it on first show), but if the user opens a SECOND tab during the same session, the second tab still has `profile.onboardingCompleted=false` from its own sign-in snapshot (taken before backend wrote) and re-shows the modal. UX: "Hey, I already finished onboarding, why is this asking again?"

## Steps to reproduce

1. New account. Sign in in Tab A.
2. Send the first message → onboarding modal closes, backend writes onboardingCompleted=true.
3. Open Tab B (same account, signed in same browser session).
4. Observe Tab B's onboarding gating.

## Expected

Tab B reads the fresh server state (onboardingCompleted=true) → no modal.

## Actual

Tab B's AuthContext getDoc may race the backend write — sometimes Tab B sees the post-write value, sometimes not. Without a listener, there's no consistency guarantee.

## Evidence

- Screenshot(s): `qa-harness/evidence/WE-20260528-173/screenshots/`

## Notes

Listener-level fix (WE-20260528-152) closes this. Until then, consider a request-level check (`getDoc` once before showing modal) instead of relying solely on the cached profile.
