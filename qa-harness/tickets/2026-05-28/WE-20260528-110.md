## Description

The SSE stream emits `id: 1`, `id: 2`, etc., suggesting client reconnection via the standard `Last-Event-ID` header. But it is not honored. I sent:

```bash
curl -s -X POST -H "Content-Type: application/json" \
  -H "Last-Event-ID: 5" \
  -d '{"message":"hi"}' \
  http://localhost:3001/api/chat/stream
```

Response begins with `id: 1` instead of resuming from `id: 6`. This is the same finding as WE-20260527-225 / WE-20260527-358 (already collapsed as duplicates), filed here under e2e-flow because it materially affects Journey 5/6 (mid-stream reload, network drop): the user sees their AI reply appear partially → tab reload → reply repeats fully → if the original message was already persisted at id=1, the client now has two AI bubbles for one user prompt.

The cancel endpoint (`POST /api/chat/cancel {requestId}`) returns 204 correctly, so the server has *some* request-tracking. The missing piece is event-replay-from-last-id.

## Steps to reproduce

```bash
# 1. start stream
curl -s -X POST -H "Content-Type: application/json" \
  -d '{"message":"500-word essay on wedding history"}' \
  --max-time 60 -N http://localhost:3001/api/chat/stream &
# 2. capture last id from output (say id 12)
# 3. kill curl after a few seconds
# 4. retry with Last-Event-ID: 12
curl -s -X POST -H "Content-Type: application/json" \
  -H "Last-Event-ID: 12" \
  -d '{"message":"500-word essay on wedding history"}' \
  -N http://localhost:3001/api/chat/stream
```

## Expected

Stream resumes at `id: 13`. Per EventSource spec, server should honor the header and skip already-emitted chunks (or re-emit a coherent prefix).

## Actual

Stream restarts from `id: 1`. Header is silently ignored.
