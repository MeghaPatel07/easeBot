## Description
Each turn runs `inbound.processInbound` → `detectLanguage` independently. The chat history (`getChatHistory`) returns messages as raw text without language tags. So if turns 1-5 are English, 6-8 are Hindi, 9-10 are English:
- Turn 6 (Hindi): user message is translated to English for the LLM. Response is translated back to Hindi. The LLM sees ENGLISH user text + ENGLISH history — but the history English text was actually generated from a Hindi response in turn 5. Round-trip translation drift sets in.
- Turn 9 (English): user message stays English. LLM sees English. Response stays English. BUT the history contains Hindi responses (from turns 6-8) — wait, let me re-check: `getChatHistory` pulls from Firestore; what's stored? If the stored message is the FINAL Hindi-translated text, the LLM gets Hindi history while being asked to respond in English. Even if the stored message is the English source, that's two-language conversations stored confusingly.

Either storage scheme creates a problem. The cleaner design (store English source + per-turn language label) is not visible in inbound/outbound.

## Steps to reproduce
1. T1-5: English chat.
2. T6: `{"message":"मेरी शादी दिसंबर में है","language":"hi"}`
3. T9: `{"message":"so what's next","language":"en"}`
4. Check Firestore message documents — what language is stored? Is the LLM seeing a coherent thread?

## Expected
- Store messages with `originalLanguage` and `englishText` fields.
- Always feed the LLM the English version + a one-line language tag per message ("[user wrote this in HI]").
- Translate the LLM output to current turn's target language.

## Actual
Storage and pipeline don't carry per-turn language tags. Mixed-language threads degrade.

## Notes
Look at `db.collection('chats', threadId, 'messages').doc(...)` writes in chatController. If only `content` is stored without language, fix the schema. The summarizer service has the same issue.
