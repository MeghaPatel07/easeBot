## Description

PRD-TTS-Pipeline §5b lists controls (Play/Pause, Waveform Seek, Speed, Stop, Close) but there is no dedicated **Replay** affordance after playback ends — Sprint 2 brief explicitly calls this out ("replay button after first listen").

In code (`AudioPlayer.tsx:150-154`), when audio ends:
```ts
const handleEnded = () => {
  setState('ended')
  setProgress(1)
  onEnded?.()
}
```
…the only way to replay is to click the same Play/Pause button (`togglePlay` at `:166-188`), which DOES reset `currentTime = 0` from `ended`/`stopped`, but the affordance is identical to the initial Play. Users have no visual cue that "ended" is now a "Replay" state — the play icon is the same Play arrow.

Compare: ChatGPT / Spotify / Apple Music expose a Replay-icon (curved arrow) after track end. The current design relies on the user discovering that the Play arrow doubles as Replay.

## Steps to reproduce

1. Open chat, click Volume2 on any assistant message.
2. Let audio play to end.
3. Observe: no dedicated Replay button; the Play arrow appears unchanged. The waveform shows 100% filled (not reset).
4. Click Play — audio replays from 0. There was no clear visual signal that this was possible.

## Expected

- After `ended` state, swap the Play icon for a `RotateCcw` / replay-circular icon, OR add a separate "Replay" pill next to the close button.
- Reset the waveform to 0% (or visually distinguish "ended" via a tint) so the user knows the track is replayable.

## Actual

- Same Play arrow; waveform stays 100% filled; no labeled "Replay".
- Discoverable only by trial and error.

## Evidence

- Source: `AudioPlayer.tsx:148-188` (handlers), `:270-360` (render).

## Notes

Cheap fix: when `state === 'ended'`, render `<RotateCcw size={16} />` in the play button slot and update `aria-label="Replay"`.
