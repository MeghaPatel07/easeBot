## Description

Journey 1 step 6: I measured `POST /api/generate-image` with prompt `"sunset wedding mandap"`:
- Wall time: **47.55 s**
- Response size: 2.63 MB (full base64 PNG)

Step 7 (`/api/chat` with `forceImageGeneration:true`):
- Wall time: **55.37 s** before the 500 (see WE-20260528-101)

The frontend chat flow uses non-stream `/api/chat` for vibe mode, which means the user sits on a spinner for ~50s with no progress signal — no "1 of 3 layers", no "still generating", no estimated time. Combined with no `/api/health` (WE-20260527-315) and no INP/web-vitals (WE-20260527-312), there is no observability for users OR ops.

Compare: streaming chat-text TTFT is sub-second; image gen is 60× slower with no parity in UX feedback.

## Steps to reproduce

```bash
time curl -s -X POST -H "Content-Type: application/json" \
  -d '{"prompt":"sunset wedding mandap"}' \
  -o /tmp/img.json http://localhost:3001/api/generate-image
```

## Expected

- Either: stream the image generation events (e.g. "queued" → "rendering" → "post-processing" → bytes) over SSE so the UI can show progress.
- Or: at minimum, show an animated estimated-time-remaining (Azure docs suggest 30-60s, so a 60s linear bar isn't ideal but is honest).
- Or: switch to a smaller/faster model for the first preview, then upscale on demand.

## Actual

Single 50s round-trip with no progress. User cannot distinguish "loading" from "frozen".
