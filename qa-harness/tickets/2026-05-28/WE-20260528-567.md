## Steps to reproduce
1. Open a long thread (50+ messages).
2. Trigger summarization (likely automatic per backend pipeline when context > threshold).
3. WHILE the summarizer is producing the summary, send 3 messages in quick succession.

## Expected
Both the new messages and the summary land cleanly; old turns are summarized into a single `system` message, new messages append in order.

## Actual
- `useChat.ts:182` keeps `messages` in local React state and `messagesRef.current` (line 198) is the ref used by the streaming pipeline.
- The pipeline reads `messagesRef.current` (lines 497, 661, 762, 870, 956) — if the summarizer endpoint returns a `messages` field that should REPLACE the working set, and that replacement is `setMessages(result.messages.map(...))` (line 956), it will clobber any pending optimistic inserts that haven't yet been ref-mirrored (the `useEffect` at line 200 mirrors `messages → ref` but is asynchronous).
- Net: a race where in-flight user message can be dropped if the server response arrives between optimistic append and `messagesRef` update.

## Impact
P1 — silent user-message loss in active long conversations. Hard to reproduce intentionally but corrupts the chat record.

## Fix direction
1. Make the summarizer return a `summary` token and `keepFromMessageId` rather than a wholesale `messages` array — merge client-side by id.
2. When applying server-driven message updates, dedupe by `id`: `setMessages(prev => mergeById(prev, serverMessages))`.
3. Add an integration test that streams while replaying a summarize response.

## Evidence
- `src/hooks/useChat.ts:182-200, 497, 956-989`
- Backend pipeline summarizer at `easebot-backend/src/pipeline/*` (not inspected this sprint)
