## Description

The chat message is capped `min(1).max(10000)` but the vibe payload allows:
- `vibeTitle: min(1).max(60)` — single field
- `vibeDescriptors: array(min(1).max(40)).max(20)` — up to 800 chars across the array
- plus `message.max(10000)` separately

So a caller can submit `message` = 10K chars PLUS a vibe payload composing another ~860 chars, plus a 4MB base64 image (`imageData` is just `z.string().optional()` with no max), all within the 20MB body limit. Total LLM token budget pushed without a unified cap.

`imageData` lacks any size check at the schema level — relies entirely on `express.json({ limit: '20mb' })`.

## Steps to reproduce

```bash
# Construct a payload with max-fill on every cap:
python3 -c "
import json
print(json.dumps({
  'message':'A'*10000,
  'forceImageGeneration':True,
  'vibeTitle':'B'*60,
  'vibeDescriptors':['C'*40]*20,
  'imageData':'D'*(4*1024*1024),
  'imageMimeType':'image/jpeg'
}))
" > /tmp/vibe.json
curl -s -X POST http://localhost:3001/api/chat -H "Content-Type: application/json" -d @/tmp/vibe.json
```

## Expected

Either a unified character/byte budget at the schema level OR a `superRefine` that rejects when the total `message + vibeTitle + vibeDescriptors.join` exceeds a sensible bound (e.g. 12K chars).

## Actual

All caps pass independently. The LLM pipeline takes the union.
