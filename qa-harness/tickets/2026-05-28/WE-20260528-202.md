## Description

`requireAuth` in `src/middleware/auth.ts:21-27` short-circuits to `next()` when no Bearer token is present:

```ts
if (!authHeader?.startsWith('Bearer ')) {
  // No token → guest pass-through (preserved behavior)
  next()
  return
}
```

The function name and its placement on `/api/chat`, `/api/transcribe`, `/api/tts` STRONGLY implies these routes require authentication. They do not. Every downstream check (`req.user?.uid ?? null`) silently treats absence as guest.

Why this is P0 in 2026-05-28 reality:
- Cost-bearing endpoints (Azure TTS, STT, OpenAI/Azure OpenAI) can be hammered by any unauthenticated caller. Quota check exists but is keyed on `X-Guest-Id` header — caller can mint unlimited UUIDs.
- The schema-level prompt-injection (WE-20260528-201) becomes externally exploitable by anyone.
- WE-20260527-204 flagged this yesterday. Status today: middleware unchanged on main.

## Steps to reproduce

```bash
# No Authorization header at all
curl -s -X POST http://localhost:3001/api/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"hi"}'
# → HTTP 200 with full LLM response

curl -s -X POST http://localhost:3001/api/tts \
  -H "Content-Type: application/json" \
  -d '{"text":"hi"}'
# → HTTP 200 with WAV audio bytes (Azure TTS billed)
```

## Expected

`requireAuth` should respond `401 Authentication required` when no Bearer token is present, OR be renamed `optionalAuth` and the route-level decision (require/optional) be explicit per route.

## Actual

Anonymous requests succeed on every route that uses `requireAuth`. The comment "preserved behavior" in the middleware suggests the rename was deferred.
