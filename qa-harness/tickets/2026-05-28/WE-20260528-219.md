## Description

The SSE event payloads use single-letter field names:

```
id: 1
data: {"t":"c","v":"Hi"}
id: 2
data: {"t":"c","v":" there"}
```

`t` likely means "type" and `c` "chunk", `v` "value" — but this is undocumented in the schemas dir. A consuming client (mobile app, future widget embed) has no way to know the event vocabulary without reading the server source. There's no `schemaVersion` field.

This is a forward-compatibility risk: when the team adds a new event type (e.g. `t: "tool"`, `t: "image"`), older clients silently swallow the value because they only branch on known `t` values.

## Steps to reproduce

```bash
curl -N -X POST http://localhost:3001/api/chat/stream -H "Content-Type: application/json" -d '{"message":"hi"}'
```

Observe abbreviated `t` / `v` fields with no schema marker.

## Expected

Either:
- Use full-name fields (`{"type":"chunk","content":"Hi"}`),
- OR keep abbreviations but document them in a TypeScript interface that's shipped to the frontend (`src/types/streamEvents.ts`), and emit a `t:"meta",v:{schemaVersion:"2026-05-28"}` event as the first frame.

## Actual

Single-letter undocumented protocol.
