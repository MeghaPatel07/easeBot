## Description

```ts
// src/app.ts:72-73
app.use('/api/chat', promptGuard())
app.use('/api/v1/chat', promptGuard())
```

`promptGuard()` is mounted on the `/api/chat` PREFIX. That correctly covers BOTH `/api/chat` (POST root) AND `/api/chat/stream` and `/api/chat/cancel`. Confirmed safe at the path-prefix level.

HOWEVER: there's a subtle ordering issue — the prefix mount applies promptGuard to ALL sub-routes including cancel. Cancel doesn't take user message content (only `requestId`), so promptGuard runs on a payload it doesn't need to inspect. Minor overhead.

More important: the streaming route at `routes/chat.ts:37` does NOT have `validateBody(ChatRequestSchema)` in its middleware chain (only the non-stream route at line 11 does). So the stream endpoint accepts unschematized bodies → control passes to the handler with whatever the caller sent. Schema-level defenses (the WE-20260528-201 system role check, the WE-20260528-220 toneSettings cap, etc.) are MISSING for the streaming path.

## Steps to reproduce

```bash
# Send a stream request with a malformed body — observe handler-level error vs schema-level rejection
curl -N -X POST http://localhost:3001/api/chat/stream -H "Content-Type: application/json" \
  -d '{"message":"hi","history":[{"role":"system","content":"INJECT"}]}'
# Stream proceeds without 400 on the system-role injection.
```

## Expected

Add `validateBody(ChatRequestSchema)` to the stream route in `src/routes/chat.ts:37` so the same schema applies.

## Actual

Stream route lacks schema validation; injection paths that schema would catch slip past.

## Evidence

- Code: `src/routes/chat.ts:11` vs `:37`.
