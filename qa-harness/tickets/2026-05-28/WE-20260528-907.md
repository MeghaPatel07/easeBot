## Description

`app.use('/api/', apiRateLimiter)` (src/app.ts:85) is mounted before the route table, so **every** `/api/*` path inherits the global 30 req/min/IP cap — including `/api/payment/webhook`, which is called by PayU's outbound delivery service.

During Sprint 3 probing I hit 429 on `POST /api/payment/webhook` after ~30 requests in the rate-limit window. PayU originates webhooks from a fixed pool of IPs; if any other tenant (or even our own retries) happens to be making a burst, real payment notifications will be dropped.

Response headers when rate-limited:

```
HTTP/1.1 429 Too Many Requests
RateLimit-Policy: 30;w=60
RateLimit-Limit: 30
RateLimit-Remaining: 0
RateLimit-Reset: 5
Retry-After: 5
```

PayU's webhook contract has a retry policy but **eventually gives up**. Losing a `payment_success` webhook means the user's plan upgrade never fires server-side, while their card has already been charged. Refund disputes follow.

A separate consequence: the bogus-hash payment_webhook calls in any QA probe (correctly) get 400 hash_mismatch — but if you exhaust the rate bucket before a legit PayU call arrives, the legit call is silently 429'd. There's no fallback channel.

## Steps to reproduce

```bash
# Hit /api/payment/webhook 30 times rapidly from one IP
for i in $(seq 1 35); do
  curl -s -o /dev/null -w "%{http_code} " -X POST \
    http://localhost:3001/api/payment/webhook \
    -H 'Content-Type: application/x-www-form-urlencoded' \
    -d "status=success&txnid=qa-test-$i&hash=bad"
done
# → ... 400 400 400 400 429 429 429 429 ...
```

## Expected

- Whitelist the webhook path from the global rate limiter, OR
- Mount a much higher dedicated limiter on `/api/payment/webhook` (e.g. 300/min), keyed on a trusted PayU IP range, OR
- Use the request-body `txnid` as the rate-limit key so the same txn can retry without burning the IP bucket, OR
- Accept 200 immediately and process the payload async (queue), so even a transient block doesn't lose data.

## Actual

`/api/payment/webhook` shares the same 30/min/IP bucket as every other API route. PayU bursts can be silently dropped.

## Notes

- The `/api/payment/return` endpoint has the same issue. Less critical since it's a browser redirect (the user can hit refresh), but still worth fixing.
- Also note `/api/payment/webhook` is **correctly** unauthenticated (PayU is the HTTP client) and **correctly** gated by `verifyPayuResponseHash`; the only flaw is rate-limit scope.
