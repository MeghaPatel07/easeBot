## Description

`apiRateLimiter` and `imageRateLimiter` use the default `express-rate-limit` key (`req.ip`). With `TRUST_PROXY` defaulting to `1`, Express trusts the first `X-Forwarded-For` hop, so a client-supplied XFF rewrites `req.ip`. Verified locally — 50 sequential requests each with a different XFF (`X-Forwarded-For: 9.9.9.<n>`) never tripped the 30/min/IP limiter.

Two consequences:

1. **Attacker bypass**: a malicious client rotating XFF can ignore rate limits entirely.
2. **Innocent-user DoS**: in production behind a load balancer, a coordinated attack from a single source with rotating XFFs can fill the shared limiter buckets so legitimate users from neighbouring IPs get 429s instead of service. Express-rate-limit shares a single `Map<key, count>` — there is no per-real-IP guarantee when the key is spoofable.

In addition, the chat-burst limiter's `guestFingerprint` is `sha256(user-agent + accept-language + ip)` — same problem: attacker rotates UA + AL + XFF and gets unlimited messages.

## Suggested fix

1. Tighten `trust proxy` behind a real LB: trust only the actual hop subnet (`process.env.TRUST_PROXY = "10.0.0.0/8"` etc.) rather than `1`.
2. For `apiRateLimiter`, override `keyGenerator` to use `req.socket.remoteAddress` (the actual TCP peer) when behind a known LB whose `X-Forwarded-For` is verified by signed-header or shared secret. Or use Cloudflare's `CF-Connecting-IP`.
3. For `guestFingerprint`, drop `accept-language` (attacker-controlled) and use a stronger anchor (e.g. `req.socket.remoteAddress` + cookie-pinned id minted at first visit).
