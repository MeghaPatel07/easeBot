## Description

The attachment tray supports `note`, `checklist`, `timeline`, `image`, `file` kinds. When a user attaches a note, the chat send presumably reads the note's full content (server-side via the attachment ID resolution) and inlines it into the LLM prompt.

There's no visible per-kind size cap in `ChatInput.tsx` (which renders the chip but doesn't validate). A user attaching a 10K-character meeting-notes document means the LLM context budget is silently consumed even though the user's `message.max(10000)` would otherwise cap it.

Cumulative effect: user types a 10K message + attaches a 10K note + attaches a 10K timeline → LLM sees 30K+ tokens of context. Either:
- The backend silently truncates → user wonders why the LLM "didn't notice" part of the note.
- The backend errors at the LLM provider tier → user sees a generic 500.

## Steps to reproduce

1. Create a long note (~10K chars).
2. In chat, attach the note via the `+` picker.
3. Send a message. Observe what the LLM sees vs. what was attached.

## Expected

- Visual indication of "attachment size: ~3K chars / context budget remaining ~7K".
- Server-side total-token-cap that gracefully degrades (drop the OLDEST attachment first, with a warning).

## Actual

Silent fan-in to LLM context.

## Evidence

- Code: ChatAttachmentsContext.tsx — no length validation on attachment resolution.
