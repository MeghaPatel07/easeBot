## Description

The identity form initialises from `profile?.name / profile?.nickname` where `profile = accountProfile ?? authProfile`. The reset useEffect (line 155-159) only fires when those refs change. If the user changes name to "Riya" remotely (in another tab) while editing locally, the local form does not warn or re-sync because (a) cross-tab profile changes never reach this tab (WE-20260528-152), and (b) the dep guard `profile?.uid, profile?.name, profile?.nickname` is identity-equal to the cached value.

## Steps to reproduce

1. Open Settings → Account in Tab A. Begin editing name to "X".
2. In Tab B, change name to "Y" → Save.
3. In Tab A, click Cancel without reloading.

## Expected

Cancel reverts to the latest server value ("Y").

## Actual

Cancel reverts to the cached snapshot ("OriginalName"), throwing the user back to a value that hasn't existed since before Tab B's save. Subsequent Save in Tab A will overwrite "Y" with "OriginalName".

## Notes

This is a classic lost-update concurrency bug on top of the broader stale-profile issue. Solve at the listener level (WE-20260528-152) and add ETag/version check on PATCH.
