## Description

Journey 5 (Settings nickname → propagation) reveals that nickname has **no visible read site**. Static scan:

- `ChatHeader.tsx:89` displays `profile?.name` (full display name) for the avatar initials.
- `ProfileMenu.tsx:172` and `:177` also use `profile.name`, never `nickname`.
- The only consumer of `nickname` is `useChat.ts:505`, which sends it down to the backend as `userPersonalization` for LLM tone — invisible to the user.
- `SettingsModal.tsx:96, 207` and `AccountTab.tsx:148, 533` read `profile.nickname` only to populate the editable input.

Net effect: a user opens Settings, sets nickname to "Babe" or "qa-test-nick", clicks Save → toast says "Profile updated" → no surface in the app ever displays it. The AI MAY refer to them as such in its replies, but that's neither immediate nor documented.

This is the same family as the canonical complaint WE-20260527-150 (display name doesn't sync after Settings save) and architectural umbrella WE-20260527-170 (two sources of truth for user profile), but it's a distinct manifestation: nickname **is** persisted correctly to Firestore; the bug is that there is no consumer.

## Steps to reproduce

1. Log in (real or test account).
2. Open Settings → Account → set Nickname to `qa-test-e2e-47926`.
3. Click Save → wait for toast "Profile updated".
4. Close Settings. Open chat header / profile menu / any avatar UI.

## Expected

The new nickname appears somewhere prominent — at minimum in the ProfileMenu dropdown line where it currently shows "name", or as a subtitle under it. Also the AI's next reply addresses the user by the new nickname.

## Actual

No visible change anywhere. The nickname is silently written to Firestore + Auth profile, and only the LLM's tone shifts (if at all) — and that requires sending a new message to observe.

## Evidence

- `qa-harness/evidence/2026-05-28-e2e/flow5/journey.log`
- File map: see grep output in journey log — `profile.nickname` has zero READ sites in `components/`.

## Notes

- This may be intentional product behavior. If so, it should be documented in the Settings UI (e.g. "We'll use this nickname when chatting with you"). But discovering this took 30 min of grepping; user discovery is impossible.
- Coordinate with the state-sync ticket family (WE-20260527-150, -158, -159, -160, -163, -166, -169, -170). This is a CONSUMER bug, those are PROPAGATION bugs — different fix path.
- Suggested minimal fix: in `ProfileMenu.tsx:177`, change `{profile.name || 'Wedding planner'}` to `{profile.nickname || profile.name || 'Wedding planner'}`. Add a secondary line with full name for context.
