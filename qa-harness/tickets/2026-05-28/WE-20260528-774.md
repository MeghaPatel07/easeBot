## Description
Backend has `chatBurstRateLimiter` middleware on the stream route (chat.ts:37). When the user (or a script) blows through the burst limit, the middleware returns a 429. Upstream of that, Azure OpenAI itself can 429 a high-volume burst — and the controller has no specific 429-handler that translates to a friendly user-facing message.

When tested manually (200 requests in 60 seconds), the FE receives either:
- A 429 HTTP response → raw "Too many requests" string surfaced in the chat as an error bubble, OR
- An SSE stream that opens then closes with an `error` event whose payload is the Azure error verbatim ("Azure OpenAI rate limit exceeded, retry after 47s").

Neither is actionable for a non-technical user. There's no "We're slow right now, try again in a minute" copy, no auto-retry with backoff, no banner queue.

## Steps to reproduce
1. Open chat. From DevTools console: `for(let i=0;i<200;i++) fetch('/api/chat/stream', {method:'POST', body: JSON.stringify({message:'test'+i})})`.
2. Observe error UX in the chat panel: raw 429 text, no retry button, no countdown.

## Expected
- 429 from backend OR from Azure → controller catches and emits an SSE error frame with code `RATE_LIMIT` + a user-friendly message ("Lots of couples chatting right now — try again in [retry-after] seconds.").
- FE: show a banner with countdown, NOT an error bubble in chat. Optionally disable the input until backoff expires.

## Actual
Raw error string, no UX affordance. User confused, may double-click and hit again, deepening the problem.
