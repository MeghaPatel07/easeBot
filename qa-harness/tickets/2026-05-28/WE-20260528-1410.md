## Description

```ts
history: z.array(z.object({
  role: z.enum(['user', 'assistant', 'system']),
  content: z.string(),
})).optional(),
```

No `.max()` on the array. No `.max()` on each item's `content`. The `message` field is capped at 10,000 chars; `history` is unbounded. Express body parser limit is 20 MB — so a request can carry ~20MB of history. The pessimistic estimator (`buildRawSkeleton`) DOES sum history tokens, so cost is metered, but:

- The estimator's `roughTokenCount` is `ceil(len/4)`. A 20 MB history → 5M-token estimate → wouldExceedMonthly for everyone except heavy promax. So most attackers get 402'd at the gate. But this is the only line of defense — the schema permits it.
- A pro user with > 5M monthly remaining can submit 20 MB on a single turn. Even before any LLM call, the JSON parse alone consumes server CPU + memory.
- The `getChatHistory` function in the controller does `providedHistory.slice(-10)` for in-body history, so only last 10 entries are sent to the LLM. The other 90% of payload is parsed, validated, then discarded — wasted resources.

## Expected

Add `.max(100)` to the history array and `.max(20000)` to each `content`. Reject early in `validateBody` instead of relying on the estimator + 402.
