## Steps to reproduce
1. Open `/` as a guest (signed-out) in tab A.
2. Send 4 messages in tab A. `localStorage.easebot-guest-msg-count = 4`.
3. Open `/` in tab B (still guest, same browser context). 
4. Tab B reads localStorage on mount → has 4 too.
5. Both tabs now send 1 message in quick succession.
6. Tab A writes count = 5, tab B writes count = 5 (each independently incremented from 4).

## Expected
Combined count should be 6. Quota should remain a single source of truth.

## Actual
- `Index.tsx:175-177` reads count on mount only.
- `Index.tsx:394, 845` writes on every send.
- No `window.addEventListener('storage', …)` to react to tab A's increment.
- The two tabs are oblivious; user effectively gets 2× quota by opening 2 tabs, 5× with 5 tabs, etc.

## Impact
P1 — direct revenue impact. Guest quota is the conversion funnel to upgrade.

## Fix direction
1. Add a `storage` listener for both keys; on event, update local React state.
2. Better: store quota count server-side via existing usage endpoint, gated by anonymous device id from PostHog (`$device_id` is already in localStorage).
3. Use BroadcastChannel `guest-counter:update` for instant cross-tab consistency.

## Evidence
- `src/pages/Index.tsx:175-177, 394, 809-810, 845`
- Probe confirmed: tab A writes `localStorage.easebot-guest-msg-count = 99`, tab B sees the LS value (because LS is shared) but never updates its React state — so the UI is also stale even after tab A's write.
