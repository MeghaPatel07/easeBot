## Description

```ts
const BAD_HOSTS = ['cdn.openai.com', 'example.com', 'placeholder.com', 'placehold.it'];
if (typeof src === 'string' && BAD_HOSTS.some(h => src.includes(h))) {
  return null;
}
```

`src.includes(h)` is a substring check. It catches the intended hallucinated hosts, but does NOT catch:
- `https://cdn.openai.com.evil.com/x` — `includes('cdn.openai.com')` is TRUE, returns null. (Actually safe in this case — but only by coincidence; this is BLOCK list, not allowlist, so the converse problem.)
- `https://attacker.com/cdn.openai.com.png` — `includes('cdn.openai.com')` is TRUE, returns null. (Again safe by accident.)
- `https://attacker.com/x.png` — bypasses entirely, model can render arbitrary remote images.

So a prompt-injected assistant reply can include `![](https://tracker.evil.com/beacon.png)` and the user's browser silently fetches it — a tracking-pixel / network-beacon vector that leaks the user's IP and approximate session timing to any URL the LLM is tricked into emitting.

Worse: the `src` is also handed to `<img src={src}>` without `referrerPolicy="no-referrer"` → the user's chat URL is sent in the Referer header.

## Steps to reproduce

1. Use the prompt-injection vector (WE-20260528-201) to plant an assistant message containing `![](https://your-controlled-host/x.png)`.
2. Load the chat — observe the browser fetch.

## Expected

Either:
- Allowlist the image source hosts (Firebase Storage, Azure Blob CDN, the team's CDN).
- Or set `referrerPolicy="no-referrer"` on the rendered `<img>` and run a Content Security Policy `img-src` directive that blocks third-party hosts.

## Actual

Blocklist of 4 known-bad hosts. Anything else passes.
