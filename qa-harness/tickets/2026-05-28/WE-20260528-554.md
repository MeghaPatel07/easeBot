## Steps to reproduce
1. Open a note in tab A. Type "tab A line".
2. In tab B, open the same note from the notes list.
3. In tab B, type "tab B line" (without seeing tab A's edits).
4. Tab A saves; ~2 s later tab B saves.

## Expected
Either:
- (a) merge/CRDT, or
- (b) detect remote-update conflict and prompt user, or
- (c) at minimum, tab B's `subscribeToNote` listener overwrites tab B's local state with tab A's changes before tab B saves so tab B sees the update.

## Actual
`useNoteEditor.ts:131-146` subscribes to the note via Firestore, but the comment at line 207 admits: "We avoid stomping unsaved local edits by only [applying remote when local is unchanged]." That guards against losing tab B's typing — but on tab B save, the entire doc is overwritten, eating tab A's changes.

The localStorage draft mirror (`easebot:note-draft:<id>`) doesn't fire a `storage` event listener either (see WE-20260528-551), so tab B never knows tab A is drafting.

## Impact
P1 — silent data loss. Wedding planning notes (the entire E-1 sprint output) are exactly where users open two tabs (one with a checklist, one with planning notes).

## Fix direction
1. On save, include the doc's `updatedAt` from when the editor opened; if Firestore current `updatedAt` is newer, surface "Note was updated in another tab — reload?" toast.
2. Subscribe to a BroadcastChannel `note:active` so tab B knows tab A is editing.
3. Long-term: yjs / automerge for true collaborative editing.

## Evidence
- `src/hooks/useNoteEditor.ts:131-146, 207-225`
- `src/services/notesService.ts:240-260` (`updateNote` writes raw object)
