## Description

The backend ships `Access-Control-Allow-Origin: *` (verified — preflight from `Origin: http://evil.com` returns `204` with `Access-Control-Allow-Origin: *` and `Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS`). The comment at `app.ts:46` argues the wildcard is fine because credentials are off and auth is bearer-only.

That reasoning fails because the `requireAuth` middleware (`middleware/auth.ts:21-32`) **passes through guest requests** (no Bearer header → `next()` with `req.user = undefined`). So any browser landing on a malicious website can have its JS issue cross-origin POSTs against:

- `/api/chat` and `/api/chat/stream` — burns Azure OpenAI quota (already filed WE-20260527-204).
- `/api/tts` — burns Azure Speech TTS quota (today's WE-20260528-003).
- `/api/speech-token` — leaks an Azure Speech JWT that can be used outside our domain (today's WE-20260528-001).
- `/api/transcribe` — burns Azure Speech STT quota.
- `/api/generate-image` — burns Azure DALL-E quota.

The total cost surface area is "whoever visits a malicious page during a coordinated campaign × the per-request Azure cost". One viral tweet pointing to a hidden iframe could rack up significant bills before rate-limiters catch up.

This ticket exists separately from WE-20260527-204 / WE-20260528-001 because the fix is not (just) adding auth to those routes — it's also tightening CORS to a whitelist of trusted origins (`weddingease.ai`, the dev hosts, etc.) so the bearer-token argument actually holds.

## Steps to reproduce

```
curl -sS -X OPTIONS http://localhost:3001/api/chat \
  -H "Origin: http://evil.com" \
  -H "Access-Control-Request-Method: POST" -i | head -20
# → 204 with `Access-Control-Allow-Origin: *`

# Combined with WE-20260527-204:
curl -sS -X POST http://localhost:3001/api/chat \
  -H 'Origin: http://evil.com' -H 'Content-Type: application/json' \
  -d '{"message":"hi"}'
# → 200, valid LLM response, billed to our Azure account
```

## Expected

- `cors({ origin: ['http://localhost:8081','https://*.weddingease.ai',…], credentials: true })` — explicit allow-list.
- Either keep cookies + credentials and use SameSite=Lax, OR keep bearer + tighten CORS — but not "wildcard + guest pass-through".

## Actual

`origin: '*'`, anyone can hit the burn-quota endpoints.

## Evidence

- `qa-harness/evidence/WE-20260528-015/curl.log`

## Notes

This is the umbrella security finding for today. Closing it requires either:
1. Stop allowing guest pass-through in `requireAuth` (would close WE-20260527-204 alongside), OR
2. Tighten CORS origin allowlist.

Both are recommended. The dev fix has zero user impact; just adjust `cors({})` config + `requireAuth` behavior in tandem.
