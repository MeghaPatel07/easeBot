## Description
`determineTargetLanguage(payloadLanguage, detectedLanguage)` priority: explicit non-'auto' payloadLanguage wins. So if the UI passes `"language":"hi"` and the user types `"please respond in English"`, the response will still be in Hindi — the in-message override is invisible to the determiner because the determiner only sees `payloadLanguage` + `detectedLanguage`, not message content.

The `buildLanguageInstruction` output then forces the system prompt to say `"You MUST write your entire response in Hindi. Do not switch to English at any point."` — directly contradicting the user's explicit ask. This is a contract violation: the user's IN-CONVERSATION language override is not respected.

## Steps to reproduce
1. `curl -X POST http://localhost:3001/api/chat/stream -d '{"message":"please respond in english from now on","language":"hi"}'`
2. Response is in Hindi (forced by the language instruction suffix).
3. User repeats "ENGLISH PLEASE" — still Hindi because the payload language never changes mid-thread.

## Expected
- Detect in-message language switch requests ("respond in X", "switch to X", "from now on please use X") and either (a) override the payload language for this turn AND emit a frontend hint to update the saved preference, or (b) let the user know the language toggle is in settings.
- At minimum, the prompt should acknowledge the conflict: "I see you'd like English, but my settings here are pinned to Hindi — could you switch language in the menu?"

## Actual
Silent disregard for the user's in-message ask. The forcing instruction at line 59-61 is unconditional once `payloadLanguage` is set.

## Notes
Simple fix: in chatController, run a tiny regex/intent scan on `message` for "respond in X", "switch to X", "use X language" — if matched and the new language is supported, override `payloadLanguage` for this turn. The settings menu update is a separate concern.
