## Description

`handleWebhook`:
```ts
if (!txnid || !expectedHash) { res.status(400).json({ error: 'bad_payload' }); return }
if (!verifyPayuResponseHash(payload, expectedHash, salt)) {
  res.status(400).json({ error: 'hash_mismatch' }); return
}
// ...
res.status(404).json({ error: 'unknown_txnid' });
```

The error codes returned distinguish:
- `bad_payload` → missing txnid or hash
- `hash_mismatch` → fields present, but hash wrong
- `unknown_txnid` → hash valid (somehow), but txnid not in Firestore (cannot reach without correct salt)

An external scanner can probe with different payload shapes and infer which fields exist + that the server understands PayU's protocol. While none of these by themselves enable attack, defense-in-depth says: webhook endpoints should return ONE 400 `error: 'invalid_request'` for ALL malformed inputs, logged-with-detail server-side, generic response.

`emit('payment.hash.mismatch', { ip: req.ip, claimedStatus: payload.status, source: 'webhook' })` correctly logs internally for monitoring. That's the right pattern; the response codes leak it externally.

## Steps to reproduce

```bash
# Distinguishable responses:
curl -X POST localhost:3001/api/payment/webhook -d "" -w "\n%{http_code}\n"
# {"error":"bad_payload"} 400

curl -X POST localhost:3001/api/payment/webhook -d "txnid=X&hash=YY" -w "\n%{http_code}\n"
# {"error":"hash_mismatch"} 400

# Each tells the attacker exactly what was wrong.
```

## Expected

Collapse all `400` responses to `{error: 'invalid_request'}`. Keep internal observability granular.
