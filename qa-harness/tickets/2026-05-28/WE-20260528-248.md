## Description

VERIFIED live:

```bash
$ curl -sI -X OPTIONS http://localhost:3001/api/chat \
    -H "Origin: https://evil.example.com" \
    -H "Access-Control-Request-Method: POST" \
    -H "Access-Control-Request-Headers: content-type"
# Access-Control-Allow-Origin: *
# Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS
# Access-Control-Allow-Headers: Authorization,Content-Type
```

`src/app.ts:51-58` configures `cors({ origin: '*', credentials: false, ... })`. The comment explains the choice (bearer-only auth means no credentialed cookies), but COMBINES with two other live findings to form an exploit chain:

- WE-20260528-202: `requireAuth` lets anonymous through, so `/api/chat` accepts un-Bearer-tokened calls.
- WE-20260528-201: schema accepts `role: 'system'` so any anonymous payload can prompt-inject.
- WE-20260528-248 (this): any website can call `/api/chat` from a victim's browser via `fetch(..., { method: 'POST', body: ... })`.

End-to-end: a victim browses `evil.com`. evil.com's JS calls `fetch('https://api.weddingease/api/chat', { method: 'POST', body: JSON.stringify({ message: 'x', history: [{role:'system',...}, ...] }) })`. The chat-burst limit (10/10s) is keyed on guest fingerprint (UA+AL+IP), so a single victim can burn ~10 requests per 10 seconds. With many victims, this scales to a billing-DoS.

The CORS-wildcard alone is debatable for a public chat API. Combined with the auth/schema findings, it's a P0.
