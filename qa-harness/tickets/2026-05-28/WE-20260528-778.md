## Description
When a tool call fails (e.g. `create_reminder` throws because Firestore is unreachable, `create_checklist` throws on a validation error, `generate_image` 500s from Azure), the chatController should:
1. Catch the tool error.
2. Pass the error message back to the LLM as a `tool` role message with the error text.
3. Let the LLM react ("I tried to save your reminder but there was an issue — want me to try again, or note it down without scheduling?").

Empirically (static read of chatController.ts), it's unclear whether the second-pass-with-error flow exists. Many implementations either (a) swallow the tool error and emit a generic "something went wrong" to the user, or (b) crash the SSE stream entirely with an error frame.

Without this flow, the user sees a chat message that says "I'll save that reminder" but the reminder isn't created and there's no follow-up message acknowledging the failure. Trust-eroding.

## Steps to reproduce
1. Force a `createReminderDoc` failure (e.g. point Firestore Admin at a dead project, or inject a throw).
2. Send "remind me to confirm venue on December 1".
3. Observe: does the chat surface the failure?

## Expected
- Wrap every tool dispatch in try/catch.
- On error: build a `tool` role message `{role:"tool", tool_call_id, content: "ERROR: " + err.message}` and feed back to a second LLM pass with the same context.
- Second LLM pass MUST acknowledge the failure to the user.

## Actual
Static read suggests the error path is at best a generic "something went wrong" — needs verification when backend is up.

## Notes
This is core to the agentic loop quality. Without robust tool-error handling, tools become a single-shot "fire and hope" instead of a real agentic capability.
