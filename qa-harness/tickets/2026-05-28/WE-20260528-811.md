## Description

Sprint 3 brief adversarial item #1: "Auth race conditions — sign up + immediately try chat before email-verify completes; log out while a stream is in flight; refresh token expiry mid-session."

`handleSignOut` (AuthContext.tsx:205-212) does:
```tsx
const handleSignOut = async () => {
  track('logout')
  await signOutUser(user?.uid)
  setUser(null)
  setProfile(null)
  reset()
  register({ is_authenticated: false })
}
```

It does NOT cancel any in-flight chat stream. `useChat.ts:203` holds `abortControllerRef`, but it is only `.abort()`-ed by the user-driven "Stop generation" button at line 941. There is no `useEffect(() => () => abortControllerRef.current?.abort(), [user?.uid])` cleanup, and AuthContext has no abort-event channel.

Race sequence:
1. **t=0** User sends a long planner message; backend opens a streaming SSE response and starts writing tokens.
2. **t=2s** User clicks Logout. AuthContext sets `user=null`. UI flips to logged-out chrome.
3. **t=3s** Stream keeps yielding tokens (browser fetch is still alive). `setMessages` keeps running. Backend keeps spending Azure tokens.
4. **t=5s** Stream completes. Backend writes final assistant message to `users/{uidA}/threads/{tid}/messages/{mid}` via Admin SDK (Firebase rules permit; the request was already authenticated).
5. **t=5.5s** If user signs back in as uidB on same tab, the leftover `setMessages` call may briefly flash uidA's reply in uidB's chat view depending on threadId routing luck.

Concrete consequences:
1. **Phantom messages** for ~3–10s after logout.
2. **Wasted token spend** — Azure OpenAI completes the call after the user lost interest.
3. **Cross-uid Firestore write** — chat write lands under the previous uid.
4. **Possible cross-bleed** if a new user signs in on the same device before the stream completes.

Bonus failure mode (signup-immediate-chat): AuthContext doesn't gate chat on `emailVerified`. `requireAuth` middleware (auth.ts:36-46) verifies token signature but doesn't check `email_verified`. The phone-WhatsApp signup path stores SESSION_KEY before email verification → chat is billable from t=0.

## Steps to reproduce

Live:
1. Sign in. Open Chat. Send a long multi-paragraph message (e.g. "Plan my entire 12-month wedding timeline with vendor recommendations for each phase").
2. While the streaming response is rendering, click ProfileMenu → Logout.
3. Observe the chat continues to stream tokens for several more seconds AFTER the logged-out chrome appears.

Code-level:
```bash
grep -nE "abortControllerRef\.current\?\.abort" Wedding-Ease-Viva-Chat/src/hooks/useChat.ts
# 941: abortControllerRef.current?.abort()   ← only inside stopGeneration

grep -nE "abort\(|cleanup|useEffect.*\\[user" Wedding-Ease-Viva-Chat/src/contexts/AuthContext.tsx
# (no abort signaling on signOut, no useEffect that fires on auth change to cancel chat)
```

## Expected

ONE of:
- (a) AuthContext.handleSignOut emits a custom event `auth:signout`; useChat listens and aborts.
- (b) useChat adds `useEffect(() => () => abortControllerRef.current?.abort(), [user?.uid])` so any auth change cancels.
- (c) Backend `requireAuth` re-validates the token before each streamed chunk and 401-aborts if revoked.

Plus a decision on whether unverified-email signups can chat at all (currently they can).

## Actual

Stream runs to completion under the previous uid. No abort, no token-spend cap, no UI signal that a stale write occurred.
