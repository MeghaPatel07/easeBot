## Steps to reproduce
1. Sign in as a user in tab A.
2. Open the app in tab B (same browser context). Both tabs show the chat as the authenticated user.
3. In tab A → Profile menu → Sign out.
4. Observe tab B — without touching it.

## Expected
Tab B should detect the auth-state change within ~1 s and switch to the signed-out shell (or redirect to login).

## Actual
Tab B still shows the authenticated UI (profile name, settings link, plan tier) until the user clicks something that hits backend (then it may 401-fail in confusing ways) or reloads.

## Root cause
`AuthContext.tsx` calls `onAuthStateChanged(auth, …)` once per tab. Firebase Auth persistence is `local` (default) which DOES emit `onAuthStateChanged(null)` in other tabs on `signOut()` — BUT the app's `useEffect` early-returns `if (isHandlingAuth.current) return` (line ~89) and also skips re-checking `sessionStorage[SESSION_KEY]` after first mount. More importantly, ALL feature components (Index, Settings, etc.) hold their own React state derived from the first profile snapshot — that state is not invalidated when auth flips back to null.

## Impact
P0 — privacy/security risk. A shared device where the owner logs out in tab A, another user opens tab B and sees the owner's chat history, name, wedding date until they navigate.

## Fix direction
1. AuthContext should not early-return on `isHandlingAuth.current` for the logout transition (`firebaseUser === null` should always run).
2. On `signOut`, write a `localStorage.setItem('easebot-auth-event', 'logout:' + Date.now())` and add a `storage` listener that calls `signOut()` locally in other tabs.
3. Wipe TanStack Query cache + Zustand stores on sign-out (`qc.clear()`).

## Evidence
- `src/contexts/AuthContext.tsx:87-144` — single listener, isHandlingAuth guard
- No `BroadcastChannel` usage anywhere (`grep -r BroadcastChannel src` → 0)
- No `storage` listener for `firebase:authUser:*` keys
