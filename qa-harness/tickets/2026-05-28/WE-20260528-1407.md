## Description

In `handleChatStream`, the per-tool-call loop checks `streamAbort.signal.aborted` BEFORE invoking the next tool but does NOT cancel a tool that's already in-flight. For `generate_image` the inner pipeline propagates `signal:` and the storage upload honors it. For planner tools — `executeToolCall(uid, tc.name, tc.args, isPremium, undefined, {turnImageUrls})` — there is no signal parameter on `executeToolCall`. None of `createChecklist`, `createNote`, `appendToNote`, `createReminderDoc`, `createTimelineEvent` accept an AbortSignal.

Sequence:
1. LLM emits two tool calls in round 1: `create_checklist` (200 items) + `create_note`.
2. Loop calls `executeToolCall('create_checklist', ...)`. This kicks off Firestore writes via `firebase/firestore` `setDoc` — client SDK call, no abort plumbing.
3. Client disconnects.
4. The current iteration completes (writes commit to Firestore). `streamAbort.signal.aborted === true` on the NEXT iteration → loop breaks, `create_note` is skipped.
5. Net result: checklist landed in Firestore, note did NOT. The client never knew either way (SSE `d` event never sent).
6. UI on reconnect now shows a checklist the user "didn't ask for" (they cancelled mid-write).

This compounds with -951/-952 (offline retry queue): if the client retries the same request, a SECOND checklist is created. No idempotency key on plannerTools.

## Steps to reproduce

```bash
# Start a stream that will create artifacts
( curl -sN -X POST http://localhost:3001/api/chat/stream \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer <jwt>" \
    -d '{"message":"create a 20-item haldi checklist titled Haldi Day","mode":"planner"}' \
    > /tmp/stream.txt ) &
PID=$!
sleep 1.5     # let the LLM tool-call fire and createChecklist begin
kill -9 $PID
# Wait 5s; query Firestore for new checklist:
# checklist exists despite disconnect.
```

## Expected

Plumb `streamAbort.signal` through `executeToolCall` and every planner-tool helper. On abort BEFORE the write commits, throw `CancelledError` and skip the write. Add idempotency keys to all creates so retries don't double-write.

## Cost impact

User data integrity: stale/duplicate Firestore docs. Retry from offline queue (WE-20260528-951) compounds — every cancelled-then-retried tool call creates a new doc.
