## Description

Journey 6 (share flow) surfaces three durability/privacy issues in the share artifact:

1. **Snapshot includes everything**: `createSharedChat()` (chatService.ts:324) copies every message from `chats/{tid}/messages` into `sharedChats/{id}.messages`, including the full `content`, `imageUrls`, `products`, `mode`, and timestamps. If the user typed contact info, a vendor's price, or personal photos in any earlier message, all of it lands in the public-read collection.
2. **No revoke endpoint**: the doc carries `expiresAt = now + 7d`, but there is no `deleteSharedChat(shareId)` function anywhere in the codebase. The owner has no way to retract a leaked link before 7 days expire.
3. **No share-creator metadata**: the doc has no `ownerUid` field, so even an admin-side cleanup can't find "all shares by user X". The original thread owner is unrecoverable from the share doc alone.

The README/docs imply the share is a "snapshot for collaborators" — but in practice it's a 7-day public URL with no kill switch.

## Steps to reproduce

(Static — would require Firebase writes to fully exercise.)

1. As authed user, send messages including any sensitive content ("My email is x@y.com", "My venue cost was 5L INR").
2. Click Share → copy URL.
3. Realize the message contained PII; try to revoke.
4. Search codebase: `grep -rn 'deleteSharedChat\|revokeShare\|sharedChats.*delete' src/` → returns nothing.

## Expected

- `revokeShare(shareId)` deletes the doc (or sets `expiresAt = now`).
- Share UI shows "Active shares" list with revoke buttons.
- Share doc records `ownerUid` for admin recovery.
- Optional: warn user before share if any message contains PII patterns (email, phone, INR amounts).

## Actual

- No revoke. No PII detection. No owner field.
