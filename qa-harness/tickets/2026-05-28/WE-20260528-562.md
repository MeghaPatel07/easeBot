## Steps to reproduce
1. Tab A signed in. Open Settings → Personalization → set wedding date to 2026-12-01.
2. Tab B signed in. Open chat with ProgressDashboard widget rendered (or TimelineView).
3. In tab A, change wedding date to 2027-06-15. Save.
4. Look at tab B.

## Expected
Tab B's countdown text updates within ~1 s (Firestore write should propagate via profile listener).

## Actual
Tab B's `profile.weddingDate` does not update in real-time. Per Sprint 1 -152 root cause, `AuthContext` uses `getDoc` (one-shot) instead of `onSnapshot` for the user profile doc. So when tab A patches `weddingDate`, tab B has NO subscription to receive the change. Tab B's `ProgressDashboard` keeps the old `weddingDate` prop forever.

## Impact
P1 — chains off Sprint 1 -152. The user's date IS the core anchor of every planning surface.

## Notes
Sprint 1 -161 likely files the SAME tab profile staleness for wedding date countdown. This ticket scopes the cross-tab dimension and confirms ProgressDashboard / TimelineView / SubscriptionsTab all read `profile.weddingDate` via context and would all stay stale.

## Fix direction
Resolves automatically when -152 is fixed (move AuthContext to `onSnapshot(doc(db, 'users', uid))`). Add this to that ticket's verification matrix.

## Evidence
- `src/contexts/AuthContext.tsx:90` uses `getDoc` (referenced by Sprint 1 -152)
- `src/components/ProgressDashboard.tsx:86-93` recomputes from `weddingDate` prop only when prop changes
- `src/components/TimelineView.tsx:496-505` same pattern
