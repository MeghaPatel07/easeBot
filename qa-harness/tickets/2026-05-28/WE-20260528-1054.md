## Description

`handleLoadedMetadata` calls `audio.play()` automatically — the moment a TTS asset's metadata loads, audio starts. WCAG 1.4.2 requires that any audio playing automatically for more than 3 seconds must have a pause/mute mechanism OR the user must initiate playback. The user *did* tap a "play TTS" button to fetch the asset, but the gesture context can expire between fetch start and metadata-ready event (the code itself admits this — "If browser blocks autoplay, fall back to 'paused'"). So in some flows the user gets surprise audio with no preceding gesture.

More critically: for screen-reader users who pressed the TTS button intentionally, the audio collides with the SR's own announcement of "playing" — overlapping speech, no easy way to interrupt the announcer.

## Steps to reproduce

1. Open chat with VoiceOver enabled
2. Click any TTS play button → audio starts simultaneously with VoiceOver announcement
3. (Alt flow) Block first interaction via a slow network — gesture context expires, then autoplay may still fire when metadata arrives later

## Expected

Play should be USER-initiated explicitly. After TTS audio loads, show a "ready to play" state and require a second tap. OR: only auto-play if (a) the user explicitly enabled "auto-play TTS" in Settings AND (b) prefers-reduced-motion is NOT set (screen-reader users typically have it on).

## Actual

Auto-plays on metadata load by default.

## Notes

Combine fix with `prefers-reduced-motion: reduce` check — Mac VoiceOver users typically have this on and don't want audio that fights with the SR.
