## Description

Sprint 3 brief adversarial item #2: "Free → Pro upgrade race — PayU webhook arrives BEFORE user navigates to /payment/success; navigates BEFORE webhook."

Case A (webhook-first) is handled fine — both `handleReturn` and `handleWebhook` call the same idempotent `finalizePayment` (verified at `subscriptionStateMachine.ts:437-459` and `tokenMeter.ts:649-720` — both wrap in `runTransaction` with per-txnid history docs).

**Case B (user-first) has a bug.** PaymentSuccess polls `/api/payment/verify` for at most 5 attempts at 1-second intervals:

```tsx
// PaymentSuccess.tsx:37-47
for (let attempt = 0; attempt < 5; attempt++) {
  res = (await verifyPayment(txnid)) as VerifyResponse
  if (res.state === 'paid' || res.state === 'failed') break
  await new Promise((r) => setTimeout(r, 1000))
}
```

5 seconds total. PayU sandbox commonly takes 5–15s to fire the server-to-server webhook. If the user navigates to `/payment/success` immediately after PayU redirects them BEFORE the webhook posts to `/payment/return` and finalizes the doc, the user sees "Verifying your payment…" then a stuck UI with no further polling, no retry button, no socket-push.

Worst case: user assumes the payment failed and closes the tab. The webhook eventually finalizes the payment server-side. The user is now subscribed but the UI never told them. They will discover the upgrade only when they next refresh `Settings → Plan & Billing` (which fortunately reads from the authoritative subscription doc).

## Steps to reproduce

Live (requires real PayU sandbox session):
1. Initiate Pro purchase from `/pricing`.
2. Complete the sandbox card form on PayU's side.
3. On PayU's confirmation step, the user is redirected to `/payment/success?txnid=...`.
4. If the dev backend's `/api/payment/return` finalize is slow (cold start, Firestore cold connection, Azure delay), the verify polls return state='pending' five times.
5. After 5 seconds the loop exits, `info` is set to a pending-state response, the UI shows `state: PENDING` next to the plan/amount.


## Expected

ONE of:
- (a) Exponential backoff up to ~30s, then a manual "Refresh status" button if still pending.
- (b) Subscribe to `onSnapshot(doc(db, 'payments', txnid))` so the page reflects the actual webhook arrival instead of polling at all.
- (c) Stronger backend-side wait inside `/api/payment/verify` (e.g. wait up to 10s inside the request if state='pending') so the client retry budget aligns with PayU SLA.

## Actual

5-second deadline. After that the user is silently stranded on a pending state.

## Notes

The webhook payload IS authoritative. The user's subscription IS active. The bug is purely about the UI acknowledging it. From the user's perspective, this looks like "I paid and nothing happened." That is a real revenue trust risk — a small fraction will dispute / chargeback over confusion.

Pairs with the dev-only concern that PayU sandbox can't actually reach `localhost:3001/api/payment/webhook`, so dev testing relies on the `/payment/return` flow only — meaning the only way to exercise Case B in dev is to artificially delay finalizePayment.
