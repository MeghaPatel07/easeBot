## Description

The Settings shell is a Radix Dialog (modal). When a user clicks "Privacy Policy" inside Settings → About, the link is a **plain `<a href="/privacy">`** with no `target` and no React-Router `<Link>`. The browser performs a full document navigation:
- The SettingsShell modal unmounts.
- AuthContext, ChatContext, sidebarView state, etc., are wiped.
- After reading the policy, hitting Back returns to the route the user was on BEFORE opening Settings — Settings is gone. They have to re-open it manually.

There are three reasonable patterns; the current implementation picks the worst (full reload + state loss without opening in a new tab):

1. `target="_blank"` → open in a new tab (most common SaaS pattern for legal links).
2. React Router `<Link to="/privacy">` → preserves AuthContext / app state, but still closes the modal because the new route renders a different page.
3. Open a nested modal inside Settings (legal text rendered in-modal).

Pattern 1 (`_blank`) is the lightest fix. Pattern 3 also avoids breaking the Settings flow.

DataPrivacyTab.tsx:235 has the same pattern for "Read our Privacy Policy" button (`href="/privacy"` no target).

## Steps to reproduce

1. Open /chat.
2. Open Settings → About.
3. Click "Privacy Policy".
4. Observe full-page navigation; Settings modal is gone.
5. Hit browser Back. You're back on /chat but Settings is closed; ProfileMenu open-state is lost.

## Expected

- `target="_blank" rel="noopener noreferrer"` on policy/terms links, OR
- Use `useNavigate` + close modal explicitly, OR
- Render legal markdown inside a nested modal (best UX).

## Actual

Full-page nav, modal lost, state lost.

## Evidence

- AboutTab.tsx:29-49 — `LINKS[]` defines all entries with `href: '/terms'` etc. and `external: true` ONLY on the Help mailto link.
- AboutTab.tsx:55-58 — `target={external ? '_blank' : undefined}` — `/terms` and `/privacy` are not marked `external`, so no target.
- DataPrivacyTab.tsx:235 — `<a href="/privacy">` with no target.

## Notes

Mailto (`mailto:theweddingease@gmail.com`) is correctly `external: true` → `target="_blank"`. The fix is to either mark internal policy links as `external` for the target-blank effect (cheap) or build the nested-modal pattern (better, but ~1 day of work).
