## Description

Sprint 3 brief adversarial item #9: "Image edit mode — generate image, then edit it with new prompt — does it preserve aspect ratio per project_backend_structure?"

**No.** The controller calls:

```ts
// imageController.ts:50
const imageUrl = await editImageGptImage1(imageBase64, prompt.trim(), '1024x1024', { distinctId: phDistinctId })
                                                                          ^^^^^^^^^ hardcoded
```

The signature `editImageGptImage1(imageBase64, prompt, size = '1024x1024', options?)` accepts a size argument and forwards it to `callAzureImageEdit(...)`. But the controller never threads `preferredAspectRatio` through. The variable IS destructured from `req.body` (line 6) and IS read on line 13 — but only to decide `quality: 'hd' | 'standard'`, NEVER to choose the canvas size.

Meanwhile, the LLM tool spec at `imageGeneration.ts:76-81` documents to the model:
> `aspect_ratio` — Image dimensions ... For "edit": DO NOT set this — **the system will automatically preserve the original image's aspect ratio**.

The system does NOT preserve the aspect — it forces 1024x1024 square. A portrait attire photo (1024x1536) edited via "change the background to a beach" returns a 1024x1024 cropped square. A landscape venue shot (1536x1024) returns the same.

Three impacted surfaces:
1. Direct REST: `POST /api/generate-image` with body `{ imageBase64, prompt, preferredAspectRatio: '1024x1536' }` → ignored, returns square.
2. Chat-mode tool: `generate_image` tool with `action: 'edit'` (LLM is told not to set aspect; backend forces square anyway).
3. Vibe mode: edits on previously generated portrait/landscape images get squashed to square.

## Steps to reproduce

Code-level repro:

```bash
grep -n "editImageGptImage1" easebot-backend/src/controllers/imageController.ts
# 50: ... editImageGptImage1(imageBase64, prompt.trim(), '1024x1024', ...)

grep -nE "preferredAspectRatio" easebot-backend/src/controllers/imageController.ts
# 6, 10, 13   ← read but never piped to editImageGptImage1
```

Live repro (requires authed account + image):
1. Generate a portrait image via `forceImageGeneration: true, preferredAspectRatio: '1024x1536'` — comes back portrait.
2. Send a follow-up edit request with the resulting base64 + a new prompt + `preferredAspectRatio: '1024x1536'`.
3. Response is 1024x1024.

## Expected

Either:
- (a) Detect the original image dimensions from `imageBase64` (sharp/jimp can read this trivially) and pass that size to `editImageGptImage1`.
- (b) Pass `preferredAspectRatio || '1024x1024'` to `editImageGptImage1` so the client can explicitly request a non-square edit.

Aligned with the LLM tool spec which already promises preservation.

## Actual

`editImageGptImage1` is called with hardcoded `'1024x1024'`. Output is always square.

## Notes

If the model-side cost of accepting an aspect parameter for edits is "we don't trust the LLM to pick the right aspect," option (a) (auto-detect from input image) sidesteps that concern entirely. `sharp` is already a backend dependency (used in `imagePostProcessor.ts`).

The text-to-image branch at `imageController.ts:105` also hardcodes `'1024x1024'`, but THAT one is OK because for true text-to-image the tool's `aspect_ratio` parameter is enforced at the chat-tool layer (`callImageGenTool` in imageGeneration.ts). The bug is specifically in the IMAGE-EDIT branch.
