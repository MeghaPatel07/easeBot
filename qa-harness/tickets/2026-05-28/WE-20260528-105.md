## Description

Journeys 4 & 5 surface that the same logical entity is written through two parallel paths from the client:

### Profile
- (a) `accountService.updateProfile(patch)` → PATCH `/api/account/profile` → Express handler → Admin SDK writes `users/{uid}`. Rate-limited 10/min/uid.
- (b) `settingsService.savePersonalization()` → Firestore client SDK direct → `users/{uid}` (merge).
- Settings → Account tab uses (a). Settings → AI Behavior tab uses (b). Same target document, different validation, different audit trail.

### Checklists
- (a) `checklistService.createChecklist()` → Firestore client SDK direct → `users/{uid}/checklists/{id}`.
- (b) Backend route `POST /api/checklists` → controller → Admin SDK → same path.
- AI tool `create_checklist` (planner mode) uses (b). User-initiated "save" in the Planner sidebar uses (a).

## Race & drift consequences

1. **Last-write-wins**: a user editing nickname in AI Behavior (path b) at the same moment they save a name change in Account (path a) — whichever Firestore commit lands second silently overwrites the other. No optimistic-concurrency check (no `If-Match` etag).
2. **Different rate limits**: (a) rate-limits at 10/min/uid in Express middleware; (b) inherits only Firestore client rules. A user spammed by (b) cannot be throttled by the Express limiter.
3. **Different validation**: (a) goes through `accountController` validation (e.g. nickname length, profanity check if any); (b) only goes through Firestore rules. If rules are lax (which I can't inspect — forbidden), the SDK path can write things the API rejects.
4. **Different audit/observability**: PostHog events emit only on path (a) per accountController. SDK writes are invisible to `tool_invoked` and `profile_updated` tracking.

## Steps to reproduce

Static analysis — both paths are present in source. To observe drift live:
1. Tab A: open Settings → Account, type new name `qa-test-name-A`, click Save (path a).
2. Tab B: open Settings → AI Behavior, type new nickname `qa-test-nick-B`, click Save (path b).
3. Submit both within ~200ms (race).
4. Refresh both tabs.

## Expected

Either (a) one canonical write path, OR (b) optimistic concurrency control so the second write fails with 409 and the user is prompted to merge.

## Actual

Whichever Firestore commit lands second wins. The losing tab's UI shows the "Saved" toast successfully; the user has no signal that their change was overwritten.
