## Steps to reproduce
1. Signed in. Open Settings → Account, edit display name to "Megha".
2. `useAccount.updateProfile` runs, `invalidateQueries(['account','me'])` fires.
3. The Settings page updates (TanStack Query refetches).
4. Navigate to chat — `ChatHeader` reads `profile.displayName` from `useAuth()`, NOT from `useAccount()`.

## Expected
ChatHeader shows "Megha" immediately.

## Actual
ChatHeader shows previous name. `useAuth()` returns the snapshot `AuthContext` took on the original `getDoc` call. Until next sign-in, the displayName in context never refreshes.

## Root cause
Two parallel sources of truth:
- `useAuth().profile` — populated once via `getDoc`, never re-fetched.
- `useAccount().profile` — TanStack Query, refetches on invalidate.

`useAccount.updateProfile` doesn't tell `AuthContext` to refresh its copy. Sprint 1 -152 covers AuthContext using `getDoc`; this ticket frames the consumer-side cost: every component reading `useAuth().profile.*` shows stale data until app remount.

## Impact
P1 — display name, photoURL, weddingDate, plan tier (read from profile.plan), nickname, language, location all consumed via `useAuth()` in many components.

Affected read sites (grepped):
- `ChatHeader` (profile menu name)
- `ProfileMenu`
- `Index.tsx` (Hi {name} greeting)
- `MessageBubble` avatar
- many SettingsTab cross-reads

## Fix direction
Move `AuthContext.profile` to be derived from `useAccount().profile` (single source of truth), or have AuthContext subscribe to the user doc via `onSnapshot` (the -152 fix). Then `useAccount` mutations naturally propagate.

## Evidence
- `src/hooks/useAccount.ts:84-92` (proper invalidation)
- `src/contexts/AuthContext.tsx:90` (`getDoc`, no listener)
