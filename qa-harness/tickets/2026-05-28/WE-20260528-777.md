## Description
Sprint 1 -355 caught the INPUT side (5000-word user message). This is the OUTPUT side: when the LLM produces an unusually large response (forced via prompt: "write a 50,000-word essay on hindu wedding traditions"), the controller streams it all to the FE, then writes it to Firestore. Firestore has a 1MB doc size limit (1,048,576 bytes) — a 1MB response will FAIL the Firestore write silently (no try/catch visible) and the message disappears from history even though the user saw it streamed in.

Also: FE rendering 1MB of markdown is slow; the TipTap editor used elsewhere can struggle.

The max_tokens setting in the Azure call (if set) is the main guard — but if it's unset or set high (e.g. 4096+), a determined "essay" prompt can blow through it.

## Steps to reproduce
1. `curl -X POST http://localhost:3001/api/chat/stream -d '{"message":"write a 50000 word detailed history of indian wedding traditions, do not stop until you reach exactly 50000 words"}'`
2. Observe: long stream, FE lag, then check Firestore write.

## Expected
- Hard cap on `max_tokens` in the Azure call (proposed: 2000).
- Pre-persist check: if `text.length > 100000` bytes, truncate with a "…[response truncated due to length]" suffix.
- Document size estimate before Firestore write — if >900KB, persist a summary only.
