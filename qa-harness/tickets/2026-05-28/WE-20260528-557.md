## Steps to reproduce
1. Tab A → Settings → Account. Nickname currently "Sara".
2. Tab B → Settings → Account. Also shows "Sara".
3. Tab A: edit to "Sara A". Click Save.
4. Within 2 s, tab B: edit to "Sara B". Click Save.
5. Both saves return 200.

## Expected
- Either tab B's save fails with a 409 / "out of date" error (optimistic locking via `updatedAt` precondition), or
- The Firestore `onSnapshot` from tab A's save reaches tab B before tab B clicks Save, so tab B sees "Sara A" and adjusts.

## Actual
- `accountService.patchAccountProfile` calls `setDoc` / `updateDoc` with no precondition.
- The TanStack Query for `['account','me']` in tab B has `staleTime: 30_000` (`useAccount.ts:79`) — so tab B's input field still has "Sara" when the user starts typing.
- Last writer wins; tab A's "Sara A" silently overwritten by "Sara B". User in tab A has no idea.

## Impact
P1 — concurrent edit silent overwrite. Happens for partner-shared accounts where both bride and groom log in on different devices.

## Fix direction
- Reduce `useAccount` staleTime to 5_000 OR subscribe via Firestore `onSnapshot` (current implementation uses raw GET).
- Add an `If-Match: <updatedAt>` precondition; reject if mismatch and surface "Profile was updated elsewhere — refresh?".
- Optimistic-update both tabs via BroadcastChannel `profile:updated`.

## Evidence
- `src/hooks/useAccount.ts:72-82` (staleTime: 30_000, raw `useQuery`, no listener)
- `src/services/accountService.ts` — getAccountMe is a fetch, not a subscription
- `src/pages/settings/tabs/AccountTab.tsx:172` rollback snapshot exists for client-error but does not detect remote-write conflict
