## Steps to reproduce
1. Open `/planner` — `PlannerView.tsx:59` opens listener.
2. Click into a checklist — `ChecklistDetail.tsx:71` opens listener.
3. Open AttachmentPicker — `AttachmentPicker.tsx:110` opens listener.
4. `useKnownArtifactIds` (hook always mounted on Index) opens listener at line 47.

Net result: 4 concurrent `onSnapshot` subscriptions on the same `users/{uid}/checklists` collection per browser tab.

## Expected
A single shared subscription with N consumers (via React Query's `useQuery({queryKey: ['checklists', uid]})` or a Zustand store).

## Actual
Each consumer opens its own Firestore listener. Each `unsubscribe` is correctly returned from the `useEffect`, so listeners DO detach on unmount. But during the window where all four components are mounted, four full collection reads stream over WebSocket for each write. With ~10 checklists × 4 listeners × every change, this multiplies Firestore reads and re-renders.

## Impact
P2 — performance + cost. Becomes worse for power users with many checklists; also bumps Firestore read quota in production.

## Fix direction
Lift checklist state into a single Zustand store or TanStack Query key, subscribed once at the app root. Components consume via selector. Same pattern for reminders, notes, timeline events.

## Evidence
- `src/components/PlannerView.tsx:59`
- `src/components/ChecklistDetail.tsx:71`
- `src/components/chat/AttachmentPicker.tsx:110`
- `src/hooks/useKnownArtifactIds.ts:47`
- All four use the same `subscribeToChecklists(userId, setChecklists)` signature.
