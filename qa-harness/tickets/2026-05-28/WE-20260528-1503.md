# WE-20260528-1503 — Image storage upload + Firestore write are serial inside storeGeneratedImage (1-3s saved if parallel)

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Image storage
**Discovered:** 2026-05-28

## Symptom
In `storeGeneratedImage()`, the sequence is:
1. `await uploadBytes(storageRef, buffer, ...)` — ~800-2500ms to Firebase Storage
2. `await getDownloadURL(storageRef)` — ~150-400ms round-trip
3. `await setDoc(doc(db, 'userImages', imageId), imageDoc)` — ~150-400ms

Steps 2+3 can be cut by skipping `getDownloadURL` (the public URL pattern is deterministic) and writing Firestore with a synthesized URL.

## Root cause
imageStorage.ts:137-158 calls `getDownloadURL` for the public URL each time. The bucket+path is known at upload time; the only thing `getDownloadURL` adds is a fresh download token query parameter. If the bucket has public read on `generated/{uid}/*` (or a Storage rules adjustment), the URL is computable client-side.

## Why this matters
- Saves ~200-400ms per generated image
- When `storeMultipleImages` writes 3 variants, the savings multiply (current `Promise.all` parallelizes the 3 — but each call still has the serial chain inside).

## Suggested fix
1. Build the URL once and skip `getDownloadURL` (read-only): `https://firebasestorage.googleapis.com/v0/b/{bucket}/o/{encodedPath}?alt=media`.
2. Or: kick off `getDownloadURL` and `setDoc` in `Promise.all` — `setDoc` doesn't need the URL yet, write a placeholder + patch.
