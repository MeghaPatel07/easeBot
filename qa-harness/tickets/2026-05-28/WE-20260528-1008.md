## Description

(Companion to WE-20260528-015. This one focuses on mutation endpoints under stolen Bearer tokens.)

Preflight from `Origin: https://evil.example.com` to `PATCH /api/account/profile` returns:

```
HTTP/1.1 204
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS
Access-Control-Allow-Headers: Authorization,Content-Type
```

Wildcard origin is technically safe vs drive-by CSRF (no cookies), but it removes the browser defense-in-depth against any scenario where a Bearer token has been observed in a wild context: malicious browser extension, MITM during dev with localhost cert, leaked from `localStorage` via XSS in any same-origin app, or piggybacked via a malicious npm dep. All those scenarios can replay the token from any origin worldwide because we never check `Origin`.

## Suggested fix

1. Reflect a known-good origin allowlist (`https://chat.weddingease.ai`, `https://app.weddingease.ai`, etc.) instead of `*`.
2. For account/payment mutation endpoints, additionally check `Origin` header server-side and refuse mismatched values regardless of CORS.
