## Description

Shared chat links carry an `expiresAt` date. The viewer page (`SharedChat.tsx`) displays expiry as small text "Expires {date.toLocaleDateString()}" — date-only, no time. When the link expires, viewers see only "This shared conversation has expired or does not exist." with no:

- Countdown warning *before* expiry
- Option to request renewal from the owner
- Path to ask the owner via the app
- Explanation of *why* it expired (security? privacy?)

For viewers with cognitive impairments or those returning to a bookmarked link weeks later, the expiry feels like a broken link. WCAG 2.2.1 requires that users get warning AND extension mechanism (or that the timeout is essential).

The OWNER also has no in-app warning that their shared link is about to expire. Pre-expiry warning + one-click extension would satisfy spirit of 2.2.1.

## Steps to reproduce

1. Share a thread (assume default 30-day expiry)
2. Wait until expiry, OR DevTools-set system clock past expiresAt
3. Open the share URL → bare error, no recovery path

## Expected

- Viewer: if within 48h of expiry, show "This link expires in N hours" banner with option to "Save a permanent copy" (via signup) or "Ask owner to extend"
- Owner: notification when their share is about to expire
- Expired page: include link back to TheWeddingBot home, contact owner mechanism

## Actual

Silent expire, dead-end error page.

## Notes

Same pattern applies to invite-partner links (`InvitePartner.tsx`) and password-reset OTP (`OTP_EXPIRY_SECONDS = 5 * 60`) — see -1061 for OTP timeout.
