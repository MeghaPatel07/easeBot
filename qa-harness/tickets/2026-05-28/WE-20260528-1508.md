# WE-20260528-1508 — Firestore listener census: up to 10 concurrent onSnapshot subscriptions per user session

**Severity:** P1
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Memory / Firestore quota
**Discovered:** 2026-05-28

## Symptom
Searching `src/services/*.ts` for `onSnapshot(` returns **38 call sites** across ~12 services. Per logged-in user on the chat+notes view, simultaneously open:

| Subscriber | Source | Doc/Collection |
|---|---|---|
| Threads list | chatService.subscribeToThreads | `chats` collection (where userId == uid) |
| Active thread messages | chatService.subscribeToMessages | `chats/{tid}/messages` |
| Notes list | notesService.subscribeToNotes | `notes` (ownerId == uid) |
| Trashed notes | notesService.subscribeToTrashedNotes | `notes` (same query, different filter!) — DUPLICATE QUERY |
| Shared notes | notesService.subscribeToSharedNotes | `notes` (array-contains email) |
| Folders | notesService.subscribeToFolders | `folders` |
| Notifications | notificationService.subscribeToNotifications | `notifications` |
| Saved items | savedItemsService.subscribeToSavedItems | `savedItems` |
| Liked products | likedProductsService.subscribeToLikedProducts | `likedProducts` |
| Budget | budgetService.subscribeToBudget | `budgets/{uid}` |
| Shopping | shoppingService.subscribeToShopping | `shopping` |
| Comments (per note) | notesCommentsService.subscribeToComments | `notes/{nid}/comments` |
| Invite partner | InvitePartner.tsx | `collabs/{uid}` |

**Total: 10-13 active listeners per session.** Each holds a WebSocket frame + an in-memory snapshot. Firebase JS SDK keeps ~5-20KB of metadata per listener.

## Critical duplication
`subscribeToNotes` and `subscribeToTrashedNotes` issue the **exact same query** (`where('ownerId','==',uid)`) but filter client-side. **Two listeners on the same query = 2× the WebSocket traffic.**

## Why this matters
- ~50-200KB per session held permanently in memory across listeners
- Each Firestore write to `notes` collection triggers BOTH listeners to re-fire → 2× the client work
- After 30min, no garbage collection because all listeners are anchored to React contexts/components that don't unmount

## Suggested fix
1. **Merge subscribeToNotes + subscribeToTrashedNotes** — one listener, split results client-side, expose via context.
2. Add a `listenerRegistry` debug helper that logs all active subscriptions in dev — eyeball that we don't leak on unmount.
3. Lazy-mount the Notes listeners only when the user opens the notes view (not on app boot).

## Evidence
- Listener census: `grep -rn "onSnapshot" /Users/krish/Desktop/easebot/Wedding-Ease-Viva-Chat/src/services/ | wc -l` → 38 sites
- Duplicate query: notesService.ts:204-256 (subscribeToNotes vs subscribeToTrashedNotes)
