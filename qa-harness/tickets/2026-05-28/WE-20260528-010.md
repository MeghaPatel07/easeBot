## Description

`POST /api/chat/cancel { requestId: "..." }` returns HTTP 200 with **empty body** regardless of whether the requestId matched a live in-flight chat request. The frontend's "Stop generating" surface calls this fire-and-forget, but if the user re-hits Stop or the requestId is stale, there is no signal back. Combined with WE-20260527-222 (`Client-supplied requestId — duplicate registrations silently overwrite`), the cancel surface is effectively a black box.

Live response on unknown id:

```
HTTP/1.1 200 OK
RateLimit-Remaining: 29
(empty body)
```

A clean contract would be `204 No Content` for "ok-cancelled" and `404 Not Found` for "no such request".

## Steps to reproduce

1. `curl -sS -X POST http://localhost:3001/api/chat/cancel -H 'Content-Type: application/json' -d '{"requestId":"xyz-never-issued"}' -i` → 200 empty body.
2. `curl -sS -X POST http://localhost:3001/api/chat/cancel -H 'Content-Type: application/json' -d '{}'` → `{"error":"requestId is required"}` (correct).

## Expected

- 204 No Content when a live request was found and aborted.
- 404 (or 410 Gone) `{error:"requestId not found"}` when the id is unknown.

## Actual

- Always 200 empty body, regardless of state. No way for FE to surface "cancel didn't take effect."
