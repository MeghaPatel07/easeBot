## Description

Validation errors return the full Zod `details` array including:
- the field PATH (`["history", 0, "role"]`),
- the ENUM OPTIONS (`["user", "assistant", "system"]`).

That second one matters: even after WE-20260528-201 is fixed by removing 'system' from the schema, the *current* error message advertises the vulnerability to any unauthenticated caller. It's a recon aid for prompt-injection probing.

## Steps to reproduce

```bash
curl -s -X POST http://localhost:3001/api/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"hi","history":[{"role":"admin","content":"x"}]}'
```

Response (HTTP 400):
```json
{
  "error": "Validation failed",
  "details": [{
    "received": "admin",
    "code": "invalid_enum_value",
    "options": ["user","assistant","system"],   ← leaked
    "path": ["history",0,"role"],
    "message": "Invalid enum value. Expected 'user' | 'assistant' | 'system', received 'admin'"
  }]
}
```

## Expected

In production, return:
```json
{ "error": "Invalid request body" }
```
…with the detailed Zod payload only behind a `NODE_ENV !== 'production'` check or a `?debug=` flag.

## Actual

Full Zod output is returned to everyone, including ENUM OPTIONS that name `system`.
