## Steps to reproduce
1. Sign in. Open the same conversation in tab A and tab B.
2. In tab A, send a message → AI responds → both tab A user & assistant messages render in tab A.
3. Look at tab B.

## Expected
Tab B receives the new messages via Firestore `onSnapshot` listener within 1-2 s.

## Actual
Tab B's message list is frozen at whatever it loaded on mount. Switching threads and switching back re-fetches via paginated GET — tab B then sees tab A's messages. But while staying on the same thread, tab B is blind to tab A's writes.

## Root cause
- `chatService.ts:164-180` defines `subscribeToMessages(threadId, callback)` — a proper `onSnapshot` listener.
- Grep confirms **zero call sites**: only `useChat.ts` imports `subscribeToThreads`, never `subscribeToMessages`.
- `useChat.ts:182` initializes `useState<Message[]>([])` and mutates locally via the streaming pipeline.

## Impact
P0 for couples who share a session (bride and groom both logged in on different devices; their messages don't merge). Also breaks the experience of someone leaving a long thread open in a second tab — they think the AI never replied because tab B is silent.

## Fix direction
- In `useChat`, when `activeThread` changes, replace local-only message state with an `onSnapshot` subscription via `subscribeToMessages(activeThread, setMessages)`.
- Keep the optimistic local insert during streaming, then merge with Firestore snapshot on completion (de-dup by message id).

## Evidence
- `src/services/chatService.ts:164-180` (subscribeToMessages defined)
- `src/hooks/useChat.ts:9, 212` (only subscribeToThreads imported/used)
- Grep `subscribeToMessages` → only 1 hit (the export itself)
