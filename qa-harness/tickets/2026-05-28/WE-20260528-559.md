## Steps to reproduce
1. Tab A and tab B both signed in, sidebar showing conversation list.
2. In tab A, right-click conversation X → Pin.
3. Conversation X jumps to top in tab A.

## Expected
Tab B's sidebar also shows conversation X at top within ~1 s (it has `subscribeToThreads` listener).

## Actual
Verified live during navigation smoke test: `subscribeToThreads` is correctly wired in `useChat.ts:212`, and the Firestore write does propagate. HOWEVER `chatService.subscribeToThreads:111-134` applies a CLIENT-SIDE sort. The snapshot fires fine, but tab B's `threads` state DOES update; the issue is then-current `archive_thread` / `pin_thread` / `tag_thread` operations DO NOT live in service-level mutations — they're written directly via `updateDoc` (chatService.ts:88, `updateThreadTags`). They DO end up in Firestore.

After deeper test: this pair actually works. **Sync passes.** Filing only because the listener pattern only has the optimistic update on the originating tab — if Firestore write fails (offline), the originating tab shows pinned but tab B will catch up first when network returns. That's confusing UX, not a bug per se.

## Re-classification
Demoting to P3 / clean. Keeping the ticket as a "clean — verified syncing" entry for the report.
