## Description

ChatRequestSchema (schemas/chat.ts:3-20) validates only:
- message, threadId, mode, imageData, imageMimeType, toneSettings, language, history, forceImageGeneration, preferredAspectRatio, vibeTitle, vibeDescriptors

But the controller destructures (line 651, 1162):
- `audioBase64`, `userPersonalization`, `imageBase64` (vs schema's `imageData`), `lastGeneratedImageUrl`, `styleMemory`, `skipImageGeneration`

These extra fields **bypass validation** entirely. `userPersonalization.nickname` is the prompt-injection vector in -1211. `audioBase64` flows to STT without a size cap. `imageBase64` (vs schema's `imageData` — naming mismatch) — schema may not even catch the right field.

`imageBase64` vs `imageData` — controller uses `imageBase64`. Schema declares `imageData`. So the schema's `imageData` field is **dead code**; the actual field name on the wire is `imageBase64`, which is NOT in the schema. Confirmed: live request with `imageBase64` passes Zod (extra fields allowed by default) AND flows through to vision LLM call without bounds.

## Expected

Schema covers every consumed field. Use `.strict()` to reject unknown fields. Add base64 size caps (e.g. `.max(7_000_000)` on imageBase64 for ~5MB images).

## Actual

7 unscreened fields. Naming mismatch on `imageBase64` vs `imageData`.
