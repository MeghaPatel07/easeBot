## Description

`gracefulShutdown`:
```ts
function gracefulShutdown(signal: string): void {
  console.log(`[easebot] Received ${signal}. Starting graceful shutdown…`)
  stopReminderScheduler()
  stopGuestCleanupCron()
  stopSubscriptionScheduler()
  void shutdownPostHog()
  server.close(() => { process.exit(0) })
  setTimeout(() => { process.exit(1) }, SHUTDOWN_TIMEOUT_MS).unref()
}
```

`server.close()` stops accepting NEW connections but waits for existing requests to complete. SSE streams keep responses open for as long as the LLM is generating. A user mid-stream during deploy → connection waits up to `SHUTDOWN_TIMEOUT_MS = 10s` then force-killed. The stream half-completes; the SSE `d` (done) frame never sends; the FE shows an incomplete response.

Two costs:
1. Deploy latency: 10s minimum every time a stream is in-flight during SIGTERM.
2. Token leak: when SIGTERM happens mid-Azure-completion AND the Azure SDK does not have the abort signal (-1401), Azure completes the generation, debiting the user, but the response is dropped.

## Expected

In `gracefulShutdown`, before `server.close()`:
```ts
import { abortAll } from './services/cancellationRegistry'
abortAll('shutdown')
```
where `abortAll(reason)` iterates the registry, calls `entry.controller.abort()`, and emits a `stream_aborted_by_shutdown` event for refund accounting downstream.
