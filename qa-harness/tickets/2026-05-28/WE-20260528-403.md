## Description

PRD-TTS-Pipeline §9 #1 documents "No server-side caching" as a known limitation, and §3d sets `Cache-Control: no-store` explicitly. Sprint 2 brief calls this out as a focus area ("tts cache hit/miss").

Verified live:
- `curl -X POST :3001/api/tts -d '{"text":"Hello from Viva"}'` → 200 OK, 94 KB WAV (audio/wav), Azure roundtrip ~1.5 s.
- Identical request 5 minutes later → identical Azure roundtrip cost. No `If-None-Match`, no ETag, no in-process cache.
- Frontend `ttsAudioUrls` cache (per `Index.tsx`) caches blob URLs **per session per message ID**. The cache is dropped on tab close. Even within a session, switching tabs/threads invalidates it because `ttsAudioUrls` is component-state.

Impact: every Volume2 click on the same assistant text — same voice, same language — produces an identical Azure Speech billable request. At scale, 1000 daily users replaying 3 messages each is 3000× the Azure cost it could be.

## Steps to reproduce

1. Send a chat message, click Volume2 → audio plays (Azure billed).
2. Refresh page → click Volume2 on the same message → Azure billed again (frontend cache lost).
3. `curl :3001/api/tts -d '{"text":"hello"}'` twice in a row → both produce 200 + WAV, both call Azure.
4. Check backend logs / Azure Cognitive Services dashboard → 2 synthesis requests for identical input.

## Expected

- Hash `text + voiceName + language` → Redis or in-process LRU keyed by that hash. Return cached WAV on hit.
- Respond with `ETag: "<hash>"` and `Cache-Control: public, max-age=86400, immutable` so browsers + CDNs can cache.

## Actual

No caching layer. Every call is a billable Azure synthesis.

## Evidence

- `ttsController.ts:69` sets `Cache-Control: no-store` (explicit).
- `azureTTS.ts:107-127` calls `synthesizer.speakSsmlAsync` directly with no memoization.

## Notes

PRD §9 already documents this; sprint 2 should fix or formally accept the risk. Cheapest path: in-memory LRU with 24h TTL, ~256 entries × ~150 KB = 40 MB ceiling on the Node process.
