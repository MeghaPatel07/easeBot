## Description

The original chat image-attach button (`Index.tsx:365-378`) does enforce the 4MB cap:
```ts
if (file.size > 4 * 1024 * 1024) { alert('Image must be under 4MB'); return; }
```
This was the WE-20260527-220 fix.

But ChatMessages.tsx exposes **two more file inputs** for the inline-edit experience (when a user edits a previously sent message and wants to swap the attached image):
- Line 289-305: the "Replace" button (visible when `inlineEditImage` exists).
- Line 315-331: the "Attach image" dashed-border drop area (visible when there's no inline image).

Both fire `FileReader.readAsDataURL(file)` directly with **NO size check**. A 50MB image will:
1. Block the main thread during `readAsDataURL` (the original WE-20260527-220 symptom).
2. Get stored as a data URI in `inlineEditImage` state — 67 MB string in React state, balloons re-render cost.
3. Submit to the chat backend on Save Edit, with the full data URI riding on the message payload — 67 MB request body.

The original fix landed in the wrong place (or only on one of three identical surfaces). Same root cause, different file.

## Steps to reproduce

1. Send a chat message with an image attached.
2. Click the message → edit (pencil icon, opens inline edit panel inside ChatMessages.tsx).
3. Click "Replace" → file picker.
4. Select a 30 MB JPG (`dd if=/dev/urandom bs=1M count=30 | base64 > big.txt` style, or any large photo).
5. Observe: tab freezes 2-5 s, no alert, the image is loaded in state, edit submits with 40+ MB payload.

## Expected

Mirror `Index.tsx:368`: reject files >4MB with the same alert text. Better: extract to a shared `validateChatImage(file): string | null` utility used by all three file inputs.

## Actual

No cap, no alert, browser freeze on large pick.

## Evidence

- Source: `ChatMessages.tsx:289-305` (Replace input — no `file.size` check), `:315-331` (Attach input — no `file.size` check).
- Compare: `Index.tsx:367-378` (handleFileSelected — has cap).

Not a duplicate of WE-20260527-220 — that was the primary file input. These are sibling inputs on the same component tree that were missed during the fix sweep. Sprint 2 brief explicitly asks: "verify the WE-20260527-220 fix" — this is the verification finding.
