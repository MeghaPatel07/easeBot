## Description

`src/index.css:872` correctly applies a global `prefers-reduced-motion: reduce` rule that kills CSS animation/transition. However `useTypewriter` is a JS hook using `requestAnimationFrame` at 12ms/char cadence — completely unaffected by CSS media queries. A user who has set "reduce motion" still sees every assistant message animate character-by-character, often for 5–30 seconds depending on length, violating 2.2.2 (no mechanism to pause/stop) and confusing SR users (the visible text mutates while their announcer is still parsing).

## Steps to reproduce

1. macOS: System Settings → Accessibility → Display → Reduce Motion ON
2. Open `/`, send a message, wait for assistant reply
3. Observe: text still animates in character-by-character

## Expected

The hook should detect `window.matchMedia('(prefers-reduced-motion: reduce)').matches` and short-circuit to set `displayedText = targetText` immediately when streaming pauses (and skip the RAF loop entirely while preference is on).

## Actual

Typewriter runs unconditionally.

## Notes

Pairs with the existing -651 ticket (which fixes the live-region SR announcement strategy). This ticket is the visual + JS-animation half of the same UX. Add `useMatchMedia('(prefers-reduced-motion: reduce)')` and early-return targetText.
