## Description

Several views catch mutation errors and log to console only — no toast, no UI state revert. Optimistic UI shows the edit applied; on next page reload the edit is gone (because the backend rejected/timed out).

Confirmed sample:
- `GalleryView.tsx:102-104` — image delete: `try {...} catch (err) { console.error('[GalleryView] delete error:', err) }`. UI removed the image from the grid; backend kept it. Reload → image is back.
- `BudgetDashboard` — add category / add line item mutation has same pattern (multiple try/catch with console.error only).
- `PlannerView` — same.
- `NotesView` — autosave catches errors without surfacing.

A user spends 5 minutes building out a budget; backend is silently 500ing on every save; user closes the tab; data is lost.

## Steps to reproduce

1. Open /budget. Add a category.
2. DevTools → Network → Offline (or kill backend mid-flow).
3. Add another category. UI shows it added.
4. Refresh.
5. Observe the second category is gone, no toast warned them.

## Expected

Every catch → `toast({ title: 'Save failed', description: 'Your change wasn't saved. Tap to retry.', action: { label: 'Retry', onClick: () => mutation.mutate(...) } })`.

For optimistic UI, also REVERT the local state (TanStack Query `onError` rollback — see also Sprint 1 -170 which covers `useAccount`).

## Actual

Console-only error, optimistic UI not reverted → user thinks save succeeded.

## Evidence

- GalleryView.tsx:102-104 cited above.
- Sprint 1 -170 covers a similar pattern in `useAccount` (different scope).

## Notes

This is a data-loss bug class — escalated from P2 to P1. Companion to -862 (generic-error-copy) but distinct: -862 is about toast wording; this is about toasts not firing AT ALL.
