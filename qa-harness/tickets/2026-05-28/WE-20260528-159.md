## Description

`useUsageStats` uses `staleTime: 30_000` and `refetchInterval: 60_000`. When the user sends a message and the backend mints token usage, the bar does NOT update until the next polling tick — up to 60 s of "I just sent a 50k-token request and the meter still says I'm at 12%" UX. There is no invalidation hook in the chat send pipeline; nothing calls `qc.invalidateQueries(['account','usage'])` post-message. Users who hit caps in the meantime see a hard 402 with the bar still showing room — confusing and erodes trust.

## Steps to reproduce

1. Sign in. Open ProfileMenu — note TokenPoolBar value (e.g. "12K / 3M monthly").
2. Send 3 large messages in a row.
3. Reopen ProfileMenu within 5 s.

## Expected

Bar update is visible within ≤2 s of the response landing.

## Actual

Bar shows the pre-message value for up to 60 s. User can also burn through cap silently before the bar catches up.

## Evidence

- Screenshot(s): `qa-harness/evidence/WE-20260528-159/screenshots/`
- Console log: `qa-harness/evidence/WE-20260528-159/console.log`

## Notes

Two clean fixes: (a) backend pushes token usage on the SSE/stream channel for the chat response and the chat hook calls `qc.setQueryData(['account','usage'], …)` on stream end; (b) chat-send hook explicitly `qc.invalidateQueries({queryKey: ['account','usage']})` after each stream end.
