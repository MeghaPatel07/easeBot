## Description

Sprint 3 brief adversarial item #8: "Concurrent checklist edits — same checklist, 2 tabs, edit different items simultaneously — both persist?"

**No.** Both controller paths fetch the doc, rebuild the entire `items[]` array in memory, and overwrite it. Without a Firestore transaction (or array-element mutation primitive like `arrayUnion`/`arrayRemove`), the second write loses any edit the first write made.

```ts
// checklistService.ts:149-165 (editChecklistItem) — same pattern in toggleItemDone
const resolved = await resolveChecklist(userId, checklistIdOrTitle)
const items = resolved.data.items || []
const nextItems = items.map(item =>
  item.id === target.id ? { ...item, text: newText } : item,
)
await updateDoc(checklistRef(userId, resolved.id), {
  items: nextItems, updatedAt: serverTimestamp()
})
```

Lost-update sequence (two tabs):

| Time | Tab A | Tab B | Firestore items[] |
|---|---|---|---|
| t=0 | `getDoc` → snapshot [a:'A', b:'B'] | | [a:'A', b:'B'] |
| t=10 | | `getDoc` → snapshot [a:'A', b:'B'] | [a:'A', b:'B'] |
| t=20 | edit a → 'A-new'; map | | [a:'A', b:'B'] |
| t=30 | `updateDoc` { items:[a-new, b] } | | **[a:'A-new', b:'B']** |
| t=40 | "Saved ✓" | edit b → 'B-new' (uses STALE snapshot) | [a:'A-new', b:'B'] |
| t=60 | | `updateDoc` { items:[a, b-new] } | **[a:'A', b:'B-new']** |
| t=70 | | "Saved ✓" | Tab A's edit silently lost |

Distinct from `WE-20260528-105` (which calls out the dual write-path architecture issue at the profile/checklist level). Even after collapsing to a single backend write path, this bug still exists at the Firestore atomicity layer.

## Steps to reproduce

Live repro (requires two browser tabs + same logged-in user):

1. Create a checklist with items "A" and "B" via the planner UI.
2. Open the same checklist in two tabs.
3. In tab A, edit "A" → "A-new", click Save.
4. In tab B, *without refreshing*, edit "B" → "B-new", click Save.
5. Refresh tab A. Item "A" reverted to original — tab B's stale snapshot wrote back over tab A's edit.

Source-level repro (no UI needed):

```bash
grep -n "items: nextItems" easebot-backend/src/services/checklistService.ts
# → 163, 187 — both non-transactional overwrites
grep -nE "runTransaction|arrayUnion|arrayRemove" easebot-backend/src/services/checklistService.ts
# → no matches
```

## Expected

ONE of:
- (a) Wrap both helpers in `runTransaction()` so the read+write is atomic.
- (b) Mutate via `arrayRemove(oldItem) + arrayUnion(newItem)` — atomic at the field level (note: requires the item objects to be byte-identical for arrayRemove to match; safer to use a transaction).
- (c) Store items as a sub-collection (`users/{uid}/checklists/{cid}/items/{iid}`) so each item is its own doc and atomic.

## Actual

Last write wins on the entire items array. Both tabs show "Saved ✓".

## Notes

The same risk applies to **AI tool-mediated edits**: the chat planner can `edit_checklist_item` via the AI tool while the user has the checklist open in another tab. The user's manual edit will silently lose to the LLM's edit (or vice-versa) depending on order.
