## Description

In src/main.tsx, initAnalytics() and startReplay() are called synchronously before createRoot(), executing posthog.init() which loads the posthog-js bundle inline at boot. posthog-js is ~140KB raw (~50KB gzipped) and contributes to the main vendor chunk size (302).

PostHog also fires several /ingest requests during the critical path (config.js, config?ip=0, flags) which compete with main bundle download on bandwidth-constrained networks.

## Steps to reproduce

1. View src/main.tsx
2. Network panel: see /ingest/array/.../config.js fire alongside main JS

## Expected

Analytics should initialize after first paint, ideally inside a requestIdleCallback or after window 'load' event, and posthog-js should be dynamically imported.

## Actual

Init runs synchronously on module-init; render is blocked until posthog code is parsed and initAnalytics returns.

## Evidence

- Lighthouse JSON: `qa-harness/evidence/perf-2026-05-28/lh-*-prod.json`
- Build log: `/tmp/perf-build.log`
- Screenshot: `qa-harness/evidence/perf-2026-05-28/*.jpg`

## Notes

Fix: defer to 'setTimeout(initAnalytics, 0)' inside a useEffect in App, or use requestIdleCallback. Better: dynamic-import posthog-js so it doesn't enter the critical bundle.
