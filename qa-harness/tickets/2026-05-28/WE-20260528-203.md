## Description

inputSanitizer (line 7) only sanitizes string fields whose KEY is in SANITIZE_FIELDS = {message, prompt}. The middleware recurses into objects/arrays, but the sanitization filter is keyed on the field NAME. Inside history[i], the user-controlled string lives under the key "content" — which is NOT in the set — so it bypasses control-character stripping entirely.

Locally reproduced (Node REPL):

```js
const body = { message: 'hi', history: [{ role: 'user', content: 'NUL+BEL+evil+ESC[31m' }] };
sanitizeObject(body);
// AFTER: history[0].content is unchanged
```

Concrete consequences:
1. NUL bytes can corrupt Postgres / Firestore writes downstream (drivers throw or truncate silently).
2. ANSI escape sequences get logged into server logs and admin terminals — a log-injection vector that can hijack output of a sysadmin tailing `pm2 logs`.
3. Control characters reach the LLM messages, potentially bypassing keyword-based guardrails in promptGuard.

## Steps to reproduce

Curl with --data-binary and embedded control bytes in history[0].content. HTTP 200, bytes accepted verbatim.

## Expected

The sanitizer should also strip control chars from history[].content (and any other free-text field, e.g. vibeTitle, vibeDescriptors[], toneSettings keys, language, threadId).

Better: invert the allowlist — define SANITIZE_FIELDS as a "do NOT sanitize" list (base64 fields) and sanitize EVERYTHING ELSE that is a string. Allowlist-by-name is the wrong default.

## Actual

history[].content, vibeTitle, vibeDescriptors[*], imageMimeType, language, threadId all bypass sanitization.
