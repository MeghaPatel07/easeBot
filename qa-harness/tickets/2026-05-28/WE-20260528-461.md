## Description

`ThemeContext.tsx` line 74 + 88:
```ts
return (profile?.preferences?.theme as Theme | undefined) ?? 'light'
const initial = readStoredTheme() ?? (profile?.preferences?.theme as Theme | undefined) ?? 'light'
```

For a guest with no profile and no stored theme, the fallback is hard-coded `'light'`. The code does support a `'system'` Theme value (line 54: `window.matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light'`) but never selects it as the default.

Result: a guest browsing in Safari/Chrome with OS dark mode on still gets the **bright pink-mosaic light theme** on first load. They must discover the sun-icon toggle to switch — and even then they likely don't realize the app supports dark mode.

## Steps to reproduce

1. macOS System Settings → Appearance → Dark
2. Clear localStorage for `localhost:8081`
3. Open the site as a fresh guest
4. App renders in light mode despite OS preference

## Expected

The fallback in both line 74 and line 88 should be `'system'` (which then resolves dynamically via the existing `prefers-color-scheme` matcher). Honoring OS preference is standard browser-app expectation in 2026.

## Actual

App ignores OS preference; always renders light by default.

## Evidence

- Code inspection at `src/contexts/ThemeContext.tsx:74` and `:88`

## Notes

This is a small two-character change (`'light'` → `'system'` at two sites) but has outsized polish + a11y impact. WCAG SC 1.4.8 (informative) recommends respecting user-set preferences.
