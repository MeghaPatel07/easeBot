## Description

The chat `<textarea>` has no `maxLength` attribute. Backend caps `message` at 10 000 chars (`ChatRequestSchema`). User can paste a longer string (or repeatedly type past the cap); when they hit Enter, the server returns:

```
HTTP/1.1 400 Bad Request
{"error":"Validation failed","details":[{"code":"too_big","maximum":10000,"path":["message"],"message":"String must contain at most 10000 character(s)"}]}
```

The frontend `useChat.ts` catch-all maps this to "Something went wrong" (per WE-20260527-223). User has no idea their message was too long.

## Steps to reproduce

1. Open `/` in browser.
2. Paste 12 000 chars into the chat input (any lorem-ipsum will do).
3. Press Enter.
4. Observe a generic error toast / no clear "message too long" guidance.

## Expected

1. `<textarea maxLength={10000}>` on the element.
2. Live char counter (e.g. `1234 / 10000`) appears when the user types past 8 000.
3. Send button disables (with tooltip "Message too long — max 10 000 chars") past 10 000.

## Actual

No client-side cap, no counter, no warning, no tooltip. Backend rejection surfaces as generic toast.

## Evidence

- `qa-harness/evidence/WE-20260528-009/curl.log` (backend response shape).

## Notes

Related to WE-20260527-212 (history[].content has no max length on the backend) and WE-20260527-220 (chat image-attach no client-side file-size cap). All three are the same general weakness: client trusts the user, server says "no", client has no graceful surface.
