## Description

The play-TTS handler in `Index.tsx:742` resolves the effective voice with `getLocalVoiceId() ?? profile?.voiceId ?? undefined`. `SettingsModal.handleSave` writes voiceId to Firestore via `savePersonalization` but never calls `setLocalVoiceId(voiceId)` and never refreshes the AuthContext profile. So after a voice change:

- `getLocalVoiceId()` is whatever the previous session wrote (often `null` or a stale id) — the new voice was never mirrored into localStorage.
- `profile?.voiceId` still points at the OLD voice because the AuthContext profile is the frozen object from sign-in (see WE-20260528-152).
- Net effect: next TTS playback uses the stale voice. The user picks "Sage", saves, presses play, hears "Aoede".

The Voice preview in the modal works (it calls `requestTTS` with the just-clicked preset directly), which masks the bug — the user assumes playback will use the chosen voice.

## Steps to reproduce

1. Open SettingsModal → Voice tab. Note current voice.
2. Pick a clearly different voice preset (e.g. switch Aoede → Sage). Save.
3. Without reloading, press play on any AI message in the chat.

## Expected

The new voice plays.

## Actual

The OLD voice plays. Reloading once is required for the new selection to take effect.

## Notes

Fix candidates: `savePersonalization` should also call `setLocalVoiceId(voiceId)` AND the AuthContext needs a live listener (WE-20260528-152) so `profile.voiceId` reflects the new value.
