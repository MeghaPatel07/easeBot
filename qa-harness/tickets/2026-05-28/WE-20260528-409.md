## Description

The free-tier 5-checklist cap is checked by:

```ts
case 'create_checklist': {
  if (!isPremium) {
    const existingCount = await countChecklists(uid)   // ← getDocs(...)
    if (existingCount >= 5) { … }
  }
  …
}
```

And `countChecklists`:
```ts
export async function countChecklists(userId: string): Promise<number> {
  const snap = await getDocs(checklistsCol(userId))   // ← FULL collection scan
  return snap.size
}
```

Firestore charges **one document read per item returned**. A user with 4 checklists pays 4 doc-reads on every save attempt; at the cap (5), they pay 5 doc-reads PER save before getting the rejection. Premium users skip the check entirely, so they don't pay this — but **free users pay more** than premium users for the same write. Inverted cost incentive.

There is also a race: if two `create_checklist` calls land within ms (e.g. user double-taps the LLM confirmation), both reads return `count = 4`, both inserts succeed, user ends with 6 checklists. No transaction guard.

## Steps to reproduce

1. Free-tier user with 4 checklists.
2. Send "Save these as two separate checklists" to LLM (single turn, two `create_checklist` tool calls).
3. Observe: both succeed. User now has 6.
4. Firestore Read counter: 1 read for the count check on the first call (returns 4), 1 read for the second (returns 4 — first hasn't committed). Two writes both succeed.

Or:

1. Single-tap save: 1 collection scan = N doc reads on every save attempt.

## Expected

- Use Firestore's `count()` aggregation (1 billed unit, regardless of collection size) instead of `getDocs(...).size`.
- Use a transaction so the count + write is atomic per `create_checklist` call.
- Cache the count in `users/{uid}.checklistCount` field, increment/decrement on create/delete, with periodic reconciliation.

## Actual

- Full collection scan on every save attempt.
- Race condition allows free users to exceed the cap via concurrent calls.
