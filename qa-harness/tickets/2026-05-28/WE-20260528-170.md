## Description

The mutation has no `onMutate` snapshot and no `onError` rollback. With `onSuccess` invalidation only, a failed mutation that DID flip a stale-time-window cached value (e.g. via a partial write or via the AccountTab's own local `setName` rollback path that doesn't propagate to Query cache) results in inconsistent reads across components: AccountTab shows rolled-back form, but ProfileMenu reading `useAccount` may still hold the optimistic patch from a previous partial state. The AccountTab does its own local rollback but the Query cache is never patched, so any sibling reading the same Query gets a different answer.

## Steps to reproduce

1. Throttle network and force `PATCH /api/account/profile` to return 500 (or unplug WiFi during the request).
2. Edit name in AccountTab → Save → wait for error toast.
3. Open ProfileMenu — observe identity row.

## Expected

ProfileMenu identity row matches the actual server state (pre-edit value).

## Actual

Inconsistency between AccountTab (rolled back to previous local snapshot) and ProfileMenu (may show transient or partial state depending on cache lifecycle).

## Evidence

- Screenshot(s): `qa-harness/evidence/WE-20260528-170/screenshots/`
- Console log: `qa-harness/evidence/WE-20260528-170/console.log`

## Notes

Standardise on TanStack Query optimistic+rollback pattern. Delete the local `setName(original.name)` etc. fallback in AccountTab, replace with reliance on `onError` cache rollback.
