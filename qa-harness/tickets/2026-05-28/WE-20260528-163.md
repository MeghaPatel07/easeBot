## Description

`addMessage` writes the message doc, then `updateDoc(doc(db,'chats',threadId), {updatedAt: serverTimestamp()})`. The order is correct, but `subscribeToThreads` sorts by `updatedAt` and may emit a snapshot where the thread is back at its old position momentarily because the SDK delivers the message doc + the thread doc updates separately. Visible flicker: sidebar order jumps back and forth for ~200–500 ms. Title preview ("last message") is read from `thread.preview` which the client doesn't seem to update at all — preview text in the sidebar lags significantly behind the actual last message.

## Steps to reproduce

1. Open chat. Send a message in a thread that's NOT at the top of the sidebar list.
2. Watch the sidebar order during the round trip.

## Expected

Thread moves to top exactly once when the message lands, with smooth ordering.

## Actual

Order can flicker; thread preview text often stays at the OLD last message until you reopen the thread.

## Evidence

- Screenshot(s): `qa-harness/evidence/WE-20260528-163/screenshots/`
- Console log: `qa-harness/evidence/WE-20260528-163/console.log`

## Notes

Fix: update `thread.preview` field in `addMessage` (currently only `updatedAt`). Consider batching the two writes via `writeBatch` so one snapshot ships both changes atomically.
