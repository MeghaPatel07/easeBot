## Description

Asset audit:
- `src/assets/images/easebot.png` → 457 × 498 px source.
- Used at `<img className="w-full h-full" />` inside `<div className="w-[31px] h-[31px]">` (ChatMessages.tsx:428) → displayed at 31 × 31 CSS px.
- At DPR 1.0 (older laptops) source 457 needs 31 = fine.
- At DPR 2.0 (most retina screens) target = 62 px = fine.
- At DPR 3.0+ (iPhone 12+ Pro, Pixel 7+ Pro, Galaxy S24) target = 93 px — still fine for 31px, but if any other surface uses easebotAvatar at larger sizes (e.g. empty-state hero) we risk softness.

The bigger concern is `Wedding ease.png` (469 × 469) used as logo in ChatHeader at h-6/w-6 (24 CSS px) — fine for sharpness, but the file is **also** used in the WeddingEaseFloater at w-16/h-16 md:w-20/md:h-20 — 64–80 CSS px → at DPR 3.0 = 240 px target, 469 still sharp.

Real issue: `public/images/easebot.png` is the 275×300 mascot used on **landing page hero** at much larger sizes (~120-160 px CSS). At DPR 3.0 the target is 480 px, but the asset is 300 px → noticeable softness on iPhone 12+ Pro hero.

Also: no `<picture>` element with WebP/AVIF fallbacks anywhere. No `srcSet` either (confirmed by grep). PNG everywhere.

## Steps to reproduce

1. Open / on iPhone 14 Pro (DPR 3.0) Safari OR DevTools → Device Toolbar → custom DPR 3.0.
2. Zoom into the mascot hero (Cmd+Plus on Safari, pinch on iPhone).
3. Observe softness; compare to actual SVG icons in lucide-react which stay crisp.

## Expected

- For decorative hero mascots, ship `easebot.png` at 2× (550×600) and 3× (825×900), wire via `srcSet="...@1x 1x, ...@2x 2x, ...@3x 3x"`.
- Migrate landing-page hero to WebP/AVIF with PNG fallback.
- Logos used at small sizes (<48 CSS px) are fine — no action.

## Actual

Single source per asset; no DPR-aware srcset; no modern formats.

## Evidence

- `file` output above: easebot.png 457×498, logo.png 4874×3078 (oversized — Sprint 2 -306).
- `grep -rn "srcSet" src/` → zero matches.

## Notes

Sprint 2 -306 flagged `logo.png` as 4874×3078 / 297KB — that's an unrelated issue (oversized source). This ticket is the inverse — landing hero source is *too small* for 3× displays.
