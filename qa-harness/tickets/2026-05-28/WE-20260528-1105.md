# WE-20260528-1105 — No TTS cache — every TTS request re-synthesizes identical greetings/prompts via Azure Speech SDK

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / External-service caching
**File:** `easebot-backend/src/services/azureTTS.ts`, `easebot-backend/src/routes/tts.ts`
**Discovered:** 2026-05-28

## Symptom
Grep for cache implementation in `services/azureTTS.ts`, `services/geminiTTS.ts`, `routes/tts.ts`: **zero matches**.

Every TTS synthesis hits Azure Speech SDK round-trip. Common phrases that absolutely repeat across users:
- Default welcome message played on `/chat` first open
- Mascot voice prompts ("hi, ready to plan?", "saved!", "let's keep going")
- Re-plays of the same assistant response when user toggles audio on a chat bubble

Azure neural TTS round-trip is typically 600-1500ms for a short utterance. With audio responses being a primary UX (the product's "Viva" branding is voice-first), this is on every interaction.

## Root cause
No caching layer; no Cloud Storage / CDN-backed audio cache.

## Suggested fix
1. **In-process LRU** (5000 entries, ~5MB total) keyed on `sha256(voiceName + ssmlText + language)` for short utterances (<200 chars).
2. **Firebase Storage cache** for everything else — write to `tts-cache/<hash>.mp3`, serve via signed URL on subsequent identical request.
3. **Pre-warm** the 50 most-common prompts (the mascot lines from `voicePresets.ts`) at deploy time.

## Expected impact
Voice flow latency drops from ~1s to ~50ms for repeated prompts. For voice-first users this is the single biggest perceived-latency win.

## Evidence
Source inspection: `services/azureTTS.ts` (no cache), `services/geminiTTS.ts` (no cache), `routes/tts.ts` (no cache).
