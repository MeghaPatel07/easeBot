## Description

`handleSoftDelete` flips `deletionPending: true` on the user doc, revokes refresh tokens, and tells the user: *"account flagged for deletion (30-day grace period); sessions revoked"*. This is a lie. There is **no hard-delete endpoint, no cron job, and no scheduled function anywhere in `easebot-backend/src/`** that converts soft-deletes into actual data removal. Verified by grepping for `deletionPending`, `purge`, `adminAuth.deleteUser`, `deleteUser`, and `cron` — only the write of the flag exists; nothing ever reads it back to perform deletion.

What survives indefinitely after "deletion":
- `users/{uid}` Firestore doc (profile, email, phone, wedding date, partner name, budget, custom instructions)
- `users/{uid}/checklists/*`, `images/*`, `shoppingLists/*`, `calendarEvents/*`, `notifications/*`, `budget/main`
- `chats/{tid}` documents owned by uid (only `handleClearHistory` clears these, and only if the user explicitly invokes it)
- All `notes/*` documents authored by uid (not deleted even by `clearHistory`)
- Firebase Auth user record (only refresh tokens revoked; account can be re-activated)
- Firebase Storage uploads (image attachments, generated images, vendor photos)
- `feedback/*` rows containing the user's email
- `passwordResetOtps/*`, `payments/*` (PayU txn rows with PII), invoices

## Repro

1. `POST /api/account/delete` with a valid Firebase ID token → 200 `{ok:true, status:"soft-deleted", message:"...30-day grace period..."}`.
2. Wait 31+ days.
3. Inspect `users/{uid}` in Firestore → still exists with `deletionPending: true` and all profile fields intact.

## Impact

- GDPR Article 17 (Right to Erasure) violation. Indian DPDP Act 2023 also requires deletion on request.
- Misleading UX copy ("30-day grace period") implies a guaranteed purge that never happens.
- `clearHistory` is the only mutation that actually deletes anything, and it's chats-only.

## Suggested fix

1. Add a scheduled Cloud Function (or backend cron) that runs daily: `WHERE deletionPending == true AND deletedAt < now - 30d` → cascade-delete all subcollections, then `adminAuth.deleteUser(uid)`.
2. Cascade must enumerate every collection that stores `userId == uid`: `notes`, `chats`, `feedback`, `payments`, `subscriptions`, `passwordResetOtps`, `sharedChats`, Storage prefix `users/{uid}/*`.
3. Also expose `POST /api/account/delete/hard` for immediate purge (post 30-day flow) so DSAR (data subject access request) handling has a tool.
