## Description

`src/routes/chat.ts:11` registers POST `/api/chat/` (the chat send) with `chatBurstRateLimiter`. The cancel endpoint at line 20 is registered WITHOUT the burst limiter — but the burst limiter is keyed at the route level on `req.user?.uid || guestFingerprint(req)`, and Express applies middleware in registration order. The fact that cancel isn't gated is correct for the cancel itself — but the user's rapid send flow looks like:

1. User sends 10 messages back-to-back → 10/10s burst window full.
2. User clicks "Stop" on the 10th → frontend fires `POST /api/chat/cancel` (per useChat.ts:941).
3. If the user then tries to send an 11th message, they'll get a 429 — but the more subtle case is that the in-flight send was supposed to be cancelled and the user expects to immediately start a NEW send. The 429 also returns the inconsistent shape from WE-20260528-213 (no `retryAfter` from apiRateLimiter, which is the FIRST limiter app.ts mounts globally).

This is a state edge case: cancel succeeds, but the next attempt to send hits a 429 the user doesn't understand, and the "Stop generating" → "Send new message" flow stalls until the burst window clears.

## Steps to reproduce

1. Send 10 chats in <10s (e.g. open devtools, smash Enter on the chat input).
2. While the 10th is streaming, click Stop.
3. Type a fresh message and hit Send.
4. Observe: 429 with the apiRateLimiter generic shape; no retryAfter; no UX guidance.

## Expected

- The Stop → New-Send flow should NOT be punished by the burst limiter (cancel is the user's signal that they want a different reply).
- Either skip cancelled-then-resent messages in the burst counter, OR show a clear "Waiting (8s)…" countdown on the Send button when the burst limit is hit.

## Actual

429 with no retryAfter. Stop-then-resend stalls until the 10s window expires.
