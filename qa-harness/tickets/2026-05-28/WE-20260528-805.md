## Description

Sprint 3 brief adversarial item #3: "guest sends 5 messages, signs up, do those 5 messages migrate to the new account or get lost?"

Verified by code path analysis (cannot script a Firebase signup in this harness without real auth credentials). The flow is:

1. Guest sends 5 messages → useEffect at `Index.tsx:849-856` writes `sessionStorage['easebot-guest-chat'] = JSON.stringify(messages)`.
2. Guest clicks "Sign up", completes Firebase email/Google signup.
3. `onAuthStateChanged` fires → `useAuth().user` becomes the newly created Firebase User.
4. Index.tsx:800-812 useEffect runs WHEN `user` changes:

```tsx
useEffect(() => {
  if (user) {
    setGuestMessageCount(0);
    ...
    sessionStorage.removeItem('easebot-guest-chat');     // ← DELETES the 5 messages
    sessionStorage.removeItem('easebot-guest-images');
    localStorage.removeItem('easebot-guest-msg-count');
    localStorage.removeItem('easebot-guest-img-count');
  }
}, [user]);
```

5. **No migration code exists** — `grep` for any of `migrateGuest`, `importGuest`, `guestToUser`, `attachGuestMessages` across both `Wedding-Ease-Viva-Chat/src` and `easebot-backend/src` returns ZERO results.
6. Nothing under `useChat.ts`, `threadsService`, or `chatController.ts` accepts a guest message blob on first signed-in chat call.

Result: **the 5 guest messages disappear silently the moment the user signs up.** The new Firestore thread under `users/{uid}/threads` starts empty. The user sees a blank chat after signup — directly contradicting the guest-flow promise of "sign up to save your progress".

PostHog can't even detect when this happens — `AuthContext.tsx:155` and `:195` hardcode `is_guest_conversion: false` on every signup, never `true`. So the funnel metric for "guest who converted" is always 0%.

Secondary bug: `beforeunload` at `Index.tsx:858-869` wipes the same keys on tab close. So even a guest who opens a new tab loses the 5 messages.

## Steps to reproduce

```
1. Open http://localhost:8081 in an Incognito window.
2. As guest, send 5 chat messages.
3. Open DevTools → Application → Session Storage — verify `easebot-guest-chat`
   contains 5 messages.
4. Click "Sign up" → complete email signup.
5. After signup completes, recheck Session Storage — `easebot-guest-chat` is gone.
6. Open the chat — empty. The 5 messages are not in Firestore under the new uid either.
```

## Expected

ONE of:
- (a) On signup, POST guest messages to a `/api/threads/ingest-guest` endpoint that creates a new thread under `users/{uid}/threads` with the guest history pre-loaded.
- (b) At minimum: capture the wipe in PostHog as `guest_history_discarded` with `count: messages.length` so growth can quantify the leak.
- (c) Even simpler stop-gap: rename the storage key from `easebot-guest-chat` to `easebot-user-${uid}-chat` on signup and restore on first authed render before the AI thread loader runs.

`is_guest_conversion: true` should be emitted in PostHog when sessionStorage had >0 guest messages at signup time.

## Actual

- All 5 messages deleted from sessionStorage.
- Nothing written to Firestore.
- PostHog `signup_completed` emits with hardcoded `is_guest_conversion: false`.

## Notes

This is the kind of bug that survives 2 sprints because the test paths never include the literal guest→signup→assert-history-exists assertion. Recommend adding an E2E playwright test that:
1. Visits as guest, sends a message.
2. Triggers Firebase Auth signup with a throwaway test account.
3. Asserts the chat view contains the guest message after sign-in.

Pairs with the architecture-level concern in WE-20260528-105 (multiple write paths to same Firestore doc) but is a distinct user-facing bug.
