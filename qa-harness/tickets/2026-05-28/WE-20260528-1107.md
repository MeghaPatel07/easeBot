# WE-20260528-1107 — Firebase Admin SDK initialized with zero pool/gRPC tuning — defaults can saturate under burst

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Database connection management
**File:** `easebot-backend/src/lib/firebaseAdmin.ts`
**Discovered:** 2026-05-28

## Symptom
`firebaseAdmin.ts` calls `initializeApp({ credential, projectId })` and exposes `getFirestore(adminApp)` without ever calling `db.settings({ ... })`. No tuning of:
- `preferRest` (would reduce gRPC channel cost on low-volume reads)
- `host` / `ssl` (default)
- gRPC `maxIdleChannels` (Firestore SDK default is 1; under burst this serializes)
- Connection pool depth

## Why this matters
A burst-rate sustained load test was bounded to /api/health (no auth) per the "don't disrupt other agents" rule — got 538-625 req/s with 0 errors at p95 5.5ms (excellent). However, **the same endpoint never touches Firestore**. The real production workload (/api/chat) involves 2-5 Firestore reads/writes per turn + transactions (token meter uses `runTransaction()` ~5 sites in `tokenMeter.ts`).

With one gRPC channel and default settings, ~50 concurrent /api/chat requests will serialize their Firestore calls in chunks, adding ~20-50ms of queueing per request. Cannot directly measure without auth tokens for the chat endpoint.

## Suggested fix
1. Add `getFirestore(adminApp).settings({ preferRest: false, maxIdleChannels: 8 })` immediately after init.
2. For read-heavy paths (`countChecklists`, `getChecklistStats`, `getCachedUserLanguage`) prefer the REST transport: `preferRest: true` cuts per-call latency by ~10ms.
3. Run an authenticated burst test (50 concurrent /api/chat) under fix-performance and confirm p95 stays < 1500ms.
