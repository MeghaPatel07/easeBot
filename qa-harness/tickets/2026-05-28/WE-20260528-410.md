## Description

`chatController.handleChat` and `handleChatStream` both trigger summarization when `history.length > 10`:

```ts
if (history.length > 10) {
  …
  const summary = await summarizeConversation(olderMessages, getClient(), targetLanguage)
  effectiveHistory = [
    { role: 'assistant' as const, content: `[Previous conversation summary]: ${summary}` },
    ...recentMessages,
  ]
}
```

Two problems:

1. **Role smell**: the summary is injected with `role: 'assistant'`. The downstream LLM cannot distinguish "this is a synthesized summary" from "this is something I actually said in turn 5". If the summarizer hallucinates ("user agreed to a $50k budget" when they only mentioned a "small budget"), the downstream model treats it as an authoritative prior commitment and will reinforce the hallucination in its reply. Should be `role: 'system'` with a clear prefix, or a separate `summary` field outside the chat array.

2. **Silent failure**: on summarizer error:
   ```ts
   } catch (err) {
     console.error('[chatController] summarization failed, using full history:', err)
     // Fall back to full history on error
   }
   ```
   We fall back to the **full 12+ message history**, which is the exact situation the summarizer was meant to mitigate (context-length explosion, Azure rate-limit, or pricing). The user sees no error, the chat appears to work, but the next 5-10 turns are 2-3× more expensive per request than the model expected.

Sprint 2 brief explicitly asks: "Conversation summarizer — send 12+ messages in one thread, verify backend kicks in summarizer (per project_backend_structure: history>10 → keep last 5 + summary), the summary doesn't leak system instructions". Verified locally with a 12-msg POST to `/api/chat/stream` — no observable in the SSE, no header, no PostHog event ('summarizer_invoked' missing).

## Steps to reproduce

1. POST to `/api/chat/stream` with a 12-message `history` array. Confirm a 200 with normal streaming reply (verified live).
2. Set `AZURE_DEPLOYMENT_NAME=does-not-exist` temporarily on the summarizer call OR mock the AzureOpenAI client to throw. Backend silently uses full 12-msg history.
3. Send the same 12-msg payload — no error surfaced, but token count for the downstream call is 2-3× normal.

## Expected

- Inject summary with `role: 'system'` (or as a dedicated `metadata` field on the request) so the downstream model can't be misled.
- On summarizer error, surface a soft observability signal (PostHog event, X-Easebot-Summarizer-Failed header) so we can detect cost/latency spikes.
- Add an explicit unit test that a downstream model receiving a summarized history doesn't echo or treat the summary content as ground-truth user statements.

## Actual

- Summary injected as `assistant`-role content, model can be steered by hallucinated summary.
- Silent fallback to full history doubles token cost without telemetry.

## Evidence

- Source: `chatController.ts:717-733` (non-stream), `:1222-1244` (stream — same logic duplicated).
- Source: `conversationSummarizer.ts:34-49` — no error type, no retry, no telemetry.

## Notes

Code duplication between non-stream and stream handlers is its own smell — they should share a helper to avoid divergent fixes.
