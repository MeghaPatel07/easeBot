## Description

Both `handleChat` and `handleChatStream` cap the tool-execution loop at `MAX_TOOL_ROUNDS = 3`. After round 3, the final call to `callAzureAIWithToolResults` is invoked with `tools = undefined`, forcing the LLM to emit a textual reply instead of more tool calls.

For prompts that require a longer chain — e.g. "Generate an image of a mandap, save it to my Wedding Inspiration note, then create a checklist with steps to recreate it, then set a reminder for the florist meeting" — the LLM might emit a chain of 4-5 dependent tool calls. The 4th+ call is dropped silently; the model just narrates its plan without executing it.

Two related issues:
1. The model can no longer call `mark_as_done` after creating a checklist in round 3 — but checklists are immediately addressable, so "create checklist + mark first item done" works in 2 rounds. The risk is multi-step planning + write workflows.
2. There is NO error event sent to the client when the round cap is hit. The user sees text like *"I'll save this and remind you next week"* and never realizes the second action didn't happen. No `tool_error` SSE event.

## Steps to reproduce

Hard to repro deterministically because of LLM nondeterminism, but the structural issue is visible at:

```ts
// chatController.ts:1499
const MAX_TOOL_ROUNDS = 3
// ...
const allowMoreTools = round < MAX_TOOL_ROUNDS - 1
const nextRoundToolCalls: ... = []
// after MAX_TOOL_ROUNDS the loop exits; no telemetry event fired.
```

Send a prompt that intentionally requires 4 chained tools and observe: assistant narrates 4 actions but `toolActions` array has ≤3 entries.

## Expected

- Bump MAX_TOOL_ROUNDS to 5 (most natural workflows fit in 4-5 calls; cap is a runaway-loop guard, not a real budget).
- Emit `tool_round_limit_hit` SSE event + log telemetry when the cap forces a final-pass.
- Optionally: if the LLM tries to call a tool in the final pass but tools are stripped, detect that case and tell the user "couldn't complete the last step".
