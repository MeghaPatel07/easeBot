## Description

Sprint 1 -068 and Sprint 2 -451 covered the AnalyticsConsent banner clipping at specific widths. The deeper structural issue: the banner is `fixed bottom-4`, and the ChatInput is in the document flow at the bottom of the chat column — they don't know about each other.

At mobile widths the banner covers the upper portion of the ChatInput's chip rail. The cap is 520px width, but on phones the banner is `92vw` (~345px) and the chat input is full-width minus padding (~343px). They occupy the same vertical band when the banner is shown.

Other systems with floating consent banners (e.g. Stripe, GitHub) push the page content up by `padding-bottom: var(--consent-height)` when the banner is visible. WeddingEase doesn't.

## Steps to reproduce

1. Clear localStorage.
2. Open /chat at mobile width (375).
3. Observe banner overlapping chat input's chip rail and mode picker.

## Expected

When AnalyticsConsent mounts, expose its height via CSS var `--consent-banner-height` on `:root`. Chat page applies `padding-bottom: var(--consent-banner-height, 0px)` to its scroll container so the input is pushed up.

When user dismisses banner, var goes to 0 and chat returns to normal.

## Actual

Banner overlaps; user has to dismiss banner just to use chat.

## Evidence

- AnalyticsConsent.tsx:46.
- Sprint 1 -068, Sprint 2 -451 (related but different specific breakpoints).

## Notes

This is the structural fix; -068 and -451 are width-specific symptoms.
