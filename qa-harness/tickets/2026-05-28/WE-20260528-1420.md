## Description

```ts
const outcome = cancelRequest(requestId, req.user?.uid ?? null)
if (outcome === 'forbidden') { res.status(403).json({error:'forbidden'}); return }
res.status(204).end()
// 'cancelled' AND 'not_found' both fall through to 204
```

The contract is partially leaky:
- `cancelled` (registry hit, aborted) → 204
- `not_found` (no such requestId) → 204
- `forbidden` (registry hit but uid mismatch) → 403

By probing for `forbidden` an attacker can confirm a `requestId` BELONGS TO SOMEONE ELSE. That's an enumeration oracle for live stream IDs.

Worse: per `cancellationRegistry.cancel`:
```ts
// Guest requests (uid === null) can be cancelled by anyone with the requestId
// since the id itself is the only capability the client has.
if (entry.uid !== null && entry.uid !== callerUid) return 'forbidden'
```

A guest's stream can be cancelled by ANYONE who guesses (or scrapes) their `requestId`. The requestId comes from the client — if the FE uses a non-random/predictable scheme (e.g. timestamp+uid suffix), an attacker can grief any guest stream. Need to confirm the FE generator is `crypto.randomUUID()` (TODO: read FE).

## Expected

- Return `404` for `not_found` (explicit), `204` only for true cancellation.
- Treat guest requestId as a security capability: require it be a 128-bit random UUID generated by the BACKEND on connect (not client-supplied), returned in the first SSE event for the client to echo on cancel.
