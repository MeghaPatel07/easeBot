## Description

```ts
console.warn('[requireAuth] token verification failed:', message)
res.status(401).json({ error: 'Invalid or expired token', detail: message })
```

Two problems:
1. The `detail` field on the JSON response leaks the Firebase Admin verifier's internal error message (e.g. `"Decoding Firebase ID token failed. Make sure you passed the entire string JWT which represents an ID token..."`). This is recon info for an attacker probing the auth surface.
2. The `console.warn` writes the same string to stdout. If a malicious payload included a JWT-like string with embedded ANSI escapes or NUL bytes (paired with WE-20260528-203), those bytes land in logs.

Combined risk: an attacker can send bogus tokens designed to elicit specific error strings, then read those strings echoed in the 401 response body to fingerprint the Firebase Admin SDK version.

## Steps to reproduce

```bash
curl -i -X POST http://localhost:3001/api/chat \
  -H "Authorization: Bearer not-a-real-jwt" \
  -H "Content-Type: application/json" \
  -d '{"message":"hi"}'
```

Observe the `detail` field in the 401 body verbatim from the Admin SDK.

## Expected

- Omit `detail` from the response body. Generic message only: `{"error":"Invalid or expired token"}`.
- Log the detail server-side only (and sanitize it before logging).

## Actual

`detail` leaked in 401 body.
