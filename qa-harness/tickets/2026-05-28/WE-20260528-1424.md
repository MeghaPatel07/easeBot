## Description

```ts
const visionData = (imageBase64 && imageMimeType) ? { base64: imageBase64, mimeType: imageMimeType } : undefined
const visionImageCount = visionData ? 1 : 0
```

This only counts the legacy single `imageBase64` field. The new `attachments[]` block (per `chatAttachments.ts`) can carry MULTIPLE `kind:'image'` entries (up to `MAX_ATTACHMENTS_PER_MESSAGE`). The attachments are injected into the user message via `injectAttachmentsIntoUserMessage`, so the LLM receives them as text references (URLs or transcripts) — NOT as multimodal image content parts.

Wait — that's a separate issue. If attachments contain images, they are stringified into the user message text, not sent as `image_url` content parts. The model can't actually "see" them visually. So the vision charge is correctly 0 for attachments. BUT this means the product feature "send multiple images for analysis" doesn't actually work as vision; it works as a text reference to URLs.

If/when that's fixed (real multimodal multi-image), the vision charge will need to count `attachments.filter(a => a.kind === 'image').length` plus the legacy `visionData` count.

## Expected

Document the current behavior: attachments are NOT processed as multimodal vision parts; only the single legacy `imageBase64` is. When the feature evolves, fix vision count accordingly. Until then, surface a warning in logs when `attachments.length > 0 && some(kind === 'image')` so we know what users expect.
