# WE-20260528-1510 — Translator stress test: no client-side concurrency throttle, 20 concurrent calls hit Azure rate-limit

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Translation throughput
**Discovered:** 2026-05-28

## Symptom
Per Sprint 3: detect 100-440ms, translate hi→en cold 1048ms warm 150ms. Sprint 4 stress test (static analysis — backend not restarted):

`translation.ts` makes raw `fetch` calls to `api.cognitive.microsofttranslator.com` with **no shared connection pool, no semaphore, no batching**.

If 20 concurrent users send 20 messages near-simultaneously, the backend issues 20 parallel `detectLanguage` + 20 parallel `translateText` calls = 40 connections to Azure Translator. Azure Translator's S1 tier limit is **120 req/min per region** = ~2 req/sec sustained.

## Estimated behavior
- First 2-3 requests/sec land within the rate limit → 150-1000ms each
- Burst beyond 2/sec → Azure returns 429 → withRetry adds 500ms exponential backoff
- After 3 retries, circuit breaker (`translatorCircuitBreaker`) trips after 3 failures in 60s
- Once circuit opens, all translation calls fail-open to "return original text" until the 30s cooldown

## Throughput estimate
- **Steady-state max:** ~2 translations/sec (Azure S1 limit)
- **Burst tolerance:** ~5 before retries kick in
- **20 concurrent requests = 8-15 second total wall time** for the last to clear, with 4-6 likely hitting circuit breaker degradation

## Suggested fix
1. Add a `p-limit`-style semaphore to `translation.ts` capped at the Azure tier limit (S1 = 2/sec sustained).
2. Use Azure Translator's **batch endpoint** — POST `/translate` accepts up to 1000 items per request. Batch concurrent translations within a 50ms window.
3. Persist `detectLanguage` results per-thread (the language doesn't change mid-conversation) — eliminates ~95% of detect calls.
