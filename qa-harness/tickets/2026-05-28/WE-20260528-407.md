## Description

`handleFileSelected` calls `FileReader.readAsDataURL(file)` and ships the raw data URI to state without normalizing EXIF orientation. Phone cameras (especially iOS) record the sensor orientation as EXIF tag 0x0112 (1–8) and rely on the renderer to rotate.

Chrome **stopped** honoring EXIF orientation for `<img>` tags loaded from data URIs in v81 (2020) — they only honor it for top-level navigation. As a result:
- A landscape photo shot with phone rotated 90° has EXIF orientation = 6 (rotate 90° CW).
- Loaded into `<img src="data:image/jpeg;base64,…">` it renders sideways.

The chat preview thumbnail AND the persisted message bubble both show the sideways image. The Azure vision model also sees the raw pixels (sideways), so it may misinterpret the scene.

Sprint 2 brief explicitly calls out "EXIF strip" as a verification target.

## Steps to reproduce

1. On iPhone Safari, rotate phone to landscape, shoot a photo.
2. Attach to chat — preview thumbnail shows it rotated 90° or upside-down.
3. Send — message bubble persists the same rotation.
4. The assistant's vision-derived response references the wrong subject orientation (e.g. "I see a bookshelf" when the photo is of a cake on its side).

## Expected

Use `canvas` + `Image.bitmap.imageOrientation = 'from-image'` (or `createImageBitmap(file, {imageOrientation: 'from-image'})`) to normalize, then re-encode the data URI. Strips EXIF as a side effect (privacy bonus — EXIF carries GPS, device serial, timestamps).

## Actual

Raw bytes passed through. Sideways photos look sideways. EXIF GPS/device metadata persists into Firestore via the message payload.

## Evidence

- Source: `Index.tsx:369-376` — direct FileReader → data URI, no canvas normalization.

## Notes

Privacy side: EXIF GPS coordinates leak the user's home address into Firestore. Sprint 2 brief asks about "EXIF strip" — both UX and privacy implications.
