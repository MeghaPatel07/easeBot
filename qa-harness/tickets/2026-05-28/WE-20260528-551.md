## Steps to reproduce
1. Open `http://localhost:8081/` in tab A and tab B (same browser context).
2. In tab A devtools → `localStorage.setItem('easebot-theme', 'dark')`.
3. Observe tab B — html `class` remains `light`; no re-render fired.

## Expected
Tab B reacts (theme flips, banner hides, draft refreshes, etc.) when tab A mutates a shared localStorage key.

## Actual
Verified live: tab B's React state never updates. Browser DOES dispatch `storage` events (probe confirms — see Evidence). The app has ZERO `window.addEventListener('storage', …)` registrations.

## Affected keys (all stale cross-tab)
- `easebot-theme` (ThemeContext)
- `ph_consent` (AnalyticsConsent — banner persists in tab B after tab A declines)
- `easebot-guest-msg-count`, `easebot-guest-img-count` (Index.tsx guest meters)
- `easebot:note-draft:<id>` (useNoteEditor — second-tab editor shows stale content)
- `eb_currency_override`, `eb_user_currency` (geolocationService)
- `weddingease_remember_email` (SignInModal Remember-me)
- `easebot-audio-speed` (AudioPlayer)
- `easebot-image-aspect-ratio` (VibeComposer)

## Impact
Editing settings in one tab leaves the other tab with stale UI until full reload. Worst case for note drafts: user has the same note open in two tabs, types in tab A, opens tab B expecting fresh content, sees old draft, types over it → tab A's changes lost on next save.

## Fix direction
Add a generic `useStorageSync(key, onChange)` hook and wire each consumer. ThemeContext should call `setThemeState(e.newValue)` when key matches. AnalyticsConsent should hide banner if `e.newValue === 'declined' | 'accepted'`. useNoteEditor should refresh draft from new value.

## Evidence
Live probe (chromium, same context, 2 tabs):
```
Tab B received storage events: [{"key":"easebot-theme","newValue":"dark"}, …]
  → browser DOES fire storage event; app code has no listener
```
Grep: `grep -r "addEventListener.*'storage'" src` → zero results.
Sprint 1 WE-20260527-162 covers ThemeContext specifically; this ticket is the broader pattern.
