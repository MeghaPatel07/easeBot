## Description
If the backend emits a malformed SSE data frame — e.g. `data: {t:"c","text":"hi"}` with missing JSON quotes, or `data: <NOT JSON AT ALL>` — the FE SSE parser will either:
1. Throw on `JSON.parse` and unmount the chat (bad), or
2. Silently swallow the frame and proceed (also bad — user sees a stalled message).

The backend SHOULD always emit valid JSON, but with concatenation bugs (e.g. partial buffer flushed mid-token, server-side `JSON.stringify` of an object containing an unescaped quote) it's a real possibility. There's no defensive parser on the FE side that handles malformed frames gracefully — log and continue.

## Steps to reproduce
Manual: write a fake backend that emits `data: {bad-json}\n\n` and connect the FE to it. Observe behavior.
Or: use DevTools to intercept the SSE response, inject a bad frame in the middle of the stream, see what FE does.

## Expected
- FE wraps `JSON.parse` in try/catch.
- On parse failure: log to PostHog (`malformed_sse_frame`), continue reading the next frame, do not unmount the chat or kill the request.
- If too many malformed frames in one stream (>3), surface "Connection issue — please retry" with a retry button.

## Actual
Likely unhandled — needs code review of the FE SSE consumer to confirm but no defensive parser found in a quick `grep`.
