# WE-20260528-1504 — Sharp double-runs on image gen path: compressImage in imageGeneration.ts + postProcessImage are both invoked

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Image pipeline
**Discovered:** 2026-05-28

## Symptom
Two Sharp pipelines run back-to-back on every generated image:
1. `imageGeneration.ts:342` — `Promise.all(rawImages.map(b64 => compressImage(b64)))` — invokes Sharp metadata + jpeg conversion (only triggers compression if > 2MB, else returns original)
2. `chatController.ts:537` — `Promise.all(base64Images.map(b64 => postProcessImage(b64, ...)))` — invokes Sharp upscale + format conversion

Step (1) ALWAYS allocates a buffer + reads metadata even when the input is small (<2MB). Step (2) re-decodes the PNG immediately after — wasted decode-encode cycle.

## Root cause
- `compressImage` in `imageGeneration.ts:178` always runs `Buffer.from(b64, 'base64')` and checks size. For typical 1024x1024 PNGs (1.2-1.8MB) it short-circuits, but the buffer allocation already happened.
- `postProcessImage` in `imagePostProcessor.ts:29` then runs `sharp(buffer).metadata()` immediately again.

## Why this matters
- Wastes ~200-500ms of CPU per image (Sharp ramps + buffer alloc + metadata I/O)
- On the parallel `Promise.all` path with 3 variants, this is 600-1500ms of duplicated work

## Suggested fix
1. Make `compressImage` in `imageGeneration.ts` a no-op when input is ≤2MB (skip even the buffer alloc — check the base64 length / 0.75 first).
2. Pass the already-decoded `Buffer` to `postProcessImage` instead of re-encoding to base64 between stages.
3. Combine into a single Sharp pipeline: `sharp(buf).resize(...).webp(...).toBuffer()`.
