## Description

`handleReturn` builds redirect URLs like:
```ts
res.redirect(302, `${frontend}/payment/failure?txnid=${encodeURIComponent(txnid)}&reason=${encodeURIComponent(status || 'failed')}`)
```

Probe with a hostile txnid:
```bash
curl -i -X POST http://localhost:3001/api/payment/return \
  -d "txnid=javascript:alert(1)&hash=deadbeef&status=success" \
  -H "Content-Type: application/x-www-form-urlencoded"
# 302 Location: http://localhost:8080/payment/failure?reason=hash_mismatch&txnid=javascript%3Aalert(1)
```

Backend correctly encodes `txnid` so the URL is well-formed. But the failure page **will** display this txnid. If the FE component does `<div>{txnid}</div>` (React JSX) it's safe; if it does `dangerouslySetInnerHTML` or `el.innerHTML = txnid`, this becomes reflected XSS.

This ticket is **defense-in-depth**: even if today's FE is React-safe, any future migration / SSR / non-React surface that renders this query param without escaping inherits an XSS.

Severity P1 not P0 because attack vector requires the attacker to construct a PayU-return URL pointing to easebot's backend with a payload they control (no PayU is involved — they can just POST directly). The attacker effectively becomes the redirect source.

Recommendation: validate `txnid` server-side against a strict pattern `^[A-Za-z0-9\-_]{8,64}$` BEFORE redirecting; reject otherwise.

## Steps to reproduce

```bash
curl -s -i -X POST http://localhost:3001/api/payment/return \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d 'txnid=<script>alert(1)</script>&hash=deadbeef&status=success' | grep Location
# Location: http://localhost:8080/payment/failure?reason=hash_mismatch&txnid=%3Cscript%3Ealert(1)%3C%2Fscript%3E
```

## Expected

Server-side: regex-validate `txnid` against the mint format (`EB-<timestamp>-<8hex>` or `DIRECT-...`); on mismatch redirect to `/payment/failure?reason=bad_payload` (no txnid in URL).
