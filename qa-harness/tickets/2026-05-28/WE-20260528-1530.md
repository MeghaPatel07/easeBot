# WE-20260528-1530 — withRetry uses exponential backoff up to 4-8s — translator P95 amplified by retries

**Severity:** P2
**Status:** fix-in-review
**Assigned:** fix-performance
**Area:** Performance / Translation latency tail
**Discovered:** 2026-05-28
**Branch:** `fix-WE-20260528-1530`
**PR:** https://github.com/MeghaPatel07/easeBot/pull/103
**Evidence:** `qa-harness/evidence/WE-20260528-1530/progress.html`

## Symptom
`translation.ts` wraps `detectLanguage` and `translateText` in `withRetry(..., { maxRetries: 2, baseDelayMs: 500, maxDelayMs: 4000 })`. On Azure 429 (rate limit) or 5xx, the chain becomes:
- Attempt 1: fails (~150-500ms)
- Sleep 500ms
- Attempt 2: fails (~150-500ms)
- Sleep ≤4000ms
- Attempt 3: succeeds or fails

**P99 latency on a single translation call: up to ~9 seconds.** Frontend doesn't know if a slow detect call is retrying or the network is slow.

## Why this matters
- The translator is in the critical path for non-English chat — both for incoming user message (detect+translate) AND outgoing assistant response (translate to user's locale).
- A 9s tail on translator turns a ~3s chat round-trip into 12s for the user.

## Suggested fix
1. Lower `maxDelayMs` to 2000ms; cap at maxRetries=1 for translation specifically.
2. Pre-cache the detected language per-thread (the user's language doesn't change mid-conversation).
3. Add `Server-Timing: translate;dur=XXX, retries=Y` so the FE can show "Connecting to translation..." vs "Translating...".

## Fix applied (2026-05-29)
Tuned the `withRetry` envelope wrapping both `detectLanguage` and `translateText` from
`{maxRetries: 2, baseDelayMs: 500, maxDelayMs: 4000}` to
`{maxRetries: 1, baseDelayMs: 200, maxDelayMs: 800}`.

Math:
- Before: 3 attempts + sleeps up to 500ms + ≤4000ms ⇒ ~3.45-8.5s worst case per call
- After: 2 attempts + single sleep ~200-260ms ⇒ ~1.0-1.5s worst case per call
- Per non-English chat turn (inbound + outbound translation): ~7-17s → ~2-3s tail

Translation was already wired behind `translatorCircuitBreaker` (threshold 3 / 60s window,
30s cooldown) with graceful fallbacks (`'en'` for detect, original text for translate).
Sustained failures still roll up to the breaker; the retry envelope now only handles
fast-recovery transient blips, which is what Azure 429 token-bucket behavior actually
needs.

Refactor: pulled options into a single `TRANSLATOR_RETRY_OPTIONS` constant so both call
sites stay in sync and the rationale lives next to the value.

Tests:
- `npx tsc --noEmit` — clean
- `npm run test:langfix` — 15/15 pass

Out of scope (recommended follow-ups, separate tickets):
1. Per-thread language cache (suggested fix #2 — user language doesn't change mid-conversation).
2. `Server-Timing` header exposure for FE retry awareness (suggested fix #3).
