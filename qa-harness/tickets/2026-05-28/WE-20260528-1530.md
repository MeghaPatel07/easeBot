# WE-20260528-1530 — withRetry uses exponential backoff up to 4-8s — translator P95 amplified by retries

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Translation latency tail
**Discovered:** 2026-05-28

## Symptom
`translation.ts` wraps `detectLanguage` and `translateText` in `withRetry(..., { maxRetries: 2, baseDelayMs: 500, maxDelayMs: 4000 })`. On Azure 429 (rate limit) or 5xx, the chain becomes:
- Attempt 1: fails (~150-500ms)
- Sleep 500ms
- Attempt 2: fails (~150-500ms)
- Sleep ≤4000ms
- Attempt 3: succeeds or fails

**P99 latency on a single translation call: up to ~9 seconds.** Frontend doesn't know if a slow detect call is retrying or the network is slow.

## Why this matters
- The translator is in the critical path for non-English chat — both for incoming user message (detect+translate) AND outgoing assistant response (translate to user's locale).
- A 9s tail on translator turns a ~3s chat round-trip into 12s for the user.

## Suggested fix
1. Lower `maxDelayMs` to 2000ms; cap at maxRetries=1 for translation specifically.
2. Pre-cache the detected language per-thread (the user's language doesn't change mid-conversation).
3. Add `Server-Timing: translate;dur=XXX, retries=Y` so the FE can show "Connecting to translation..." vs "Translating...".
