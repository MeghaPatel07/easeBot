## Description
A user can paste an arbitrarily long `message` field. Reproduced with the string `"wedding "` repeated 5000 times (~40 KB / ~10,000 tokens) and the backend accepted it, called Azure OpenAI, billed the tokens against the user's quota, and produced a normal "That's a lot of wedding energy!" reply. There's no validation gate that says "messages over X tokens are clamped or rejected." This is both a cost-control problem (one request can burn a huge chunk of a free user's monthly quota) and a DoS vector (a script firing 5000-word messages drains the rate-limit + token budget in seconds).

## Steps to reproduce
```bash
LONG=$(python3 -c "print('wedding ' * 5000)")
curl -s -X POST http://localhost:3001/api/chat/stream \
  -H "Content-Type: application/json" \
  -d "{\"message\":\"$LONG\"}" --max-time 30 | tail -3
```
Result: ~10,000-token prompt, 48-token reply, full Azure call charged.

## Expected
- Hard cap on `message.length` (proposed: 8000 chars / ~2000 tokens) enforced by `ChatRequestSchema`.
- If exceeded, return 400 with `{"error":"message exceeds maximum length of 8000 characters"}`.
- Stream route should reject before SSE headers flush.

## Actual
Request accepted, processed, billed. No warning logged.

## Notes
Add `message: z.string().max(8000)` (or a token-aware version using `tiktoken`) to `ChatRequestSchema`. The pessimistic quota gate in `quotaMiddleware.ts` runs BEFORE the message is in hand so it can't enforce input-length there. Easiest fix is at the schema layer + a redundant pre-Azure-call length check in `chatController.ts` for the stream path which currently bypasses validation (see WE-20260528-354).
