**Fix summary:** Wrapped each scheduler start in `setTimeout` with staggered delays (reminder=0ms, guestCleanup=2000ms, subscription=5000ms). Each timer is `unref()`'d so it never blocks shutdown. Single-file change at the call site; scheduler modules untouched. Adds log lines emitting scheduler order on `listen()` so ops can confirm cold-boot timing. Verified `npx tsc --noEmit` clean.

## Symptom
`server.ts:29-44` starts THREE in-process schedulers inside the `server.listen()` callback (synchronously):
- `startReminderScheduler()` — setInterval, hits Firestore on first tick
- `startGuestCleanupCron()` — setInterval, hits Firestore on first tick
- `startSubscriptionScheduler()` — setInterval, hits Firestore on first tick

Each scheduler likely runs an initial sweep within milliseconds of start. Three concurrent Firestore queries on a cold Firebase Admin SDK = significant first-request degradation.

## Why this matters
- A user request hitting the server within ~500ms of cold-boot competes with three cron-driven Firestore connections.
- Reduces "ready for traffic" latency by ~1-2s on cold-start.

## Suggested fix
1. Defer each scheduler with `setTimeout(start*, 5000)` so the server gets a 5s warm-up window for real users.
2. Stagger the schedulers (5s, 10s, 15s) so they do not all hit Firestore simultaneously even after warm-up.
3. Add an env flag `SKIP_INITIAL_SWEEP=true` for the very first cron tick.
