## Description

```ts
router.post('/', requireAuth, chatBurstRateLimiter, validateBody(ChatRequestSchema), quotaCheck('chat'), handleChat)
```

Middleware order:
1. requireAuth (no enforcement — WE-20260528-202)
2. chatBurstRateLimiter (10/10s — drains FIRST regardless of validity)
3. validateBody (rejects with 400)
4. quotaCheck (only runs after validation passes — good)

The concerning sequence: an attacker fires 10 malformed payloads in 1 second:
- 10 requests pass requireAuth.
- 10 increment the burst counter → counter at 10/10.
- 10 fail validation → 10 × 400 responses.
- The legitimate 11th request (in the same 10s window) is now blocked by `chat_burst_limit` even though no LLM work has happened.

A burst-limit reset path that's only "after 10s" means malicious clients can deny service to legitimate clients sharing the same key for 10s windows by spamming malformed bodies.

## Steps to reproduce

```bash
# Burn the burst with garbage:
for i in $(seq 1 10); do curl -s -o /dev/null -X POST http://localhost:3001/api/chat \
  -H "Content-Type: application/json" -d 'garbage'; done

# Now any legit request:
curl -s -X POST http://localhost:3001/api/chat -H "Content-Type: application/json" -d '{"message":"hi"}'
# 429 chat_burst_limit (even though no chat actually succeeded)
```

## Expected

Move `chatBurstRateLimiter` AFTER `validateBody` so only valid requests count toward the burst budget. Or count "failed validation" separately under a stricter per-key rate (lower max, longer window).

## Actual

Burst counter increments on validation failures too.
