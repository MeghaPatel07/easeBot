## Description

`POST /api/feedback` uses `requireAuth` (guest-pass-through). The body is parsed by a Zod schema that accepts arbitrary `email`, `isGuest`, `userAgent`, `path`. The handler writes them verbatim:

```
const doc = {
  feedback, email, type, isGuest: isGuest === true || !uid,
  userId: uid, userAgent, path, status: 'new', createdAt: ...
}
```

There is no check that the supplied `email` matches `req.user?.email`. Verified:

```
curl -X POST http://localhost:3001/api/feedback \
  -H "Content-Type: application/json" \
  -d '{"feedback":"impersonation test 1234567890","email":"shilpa@weddingease.ai","isGuest":false}'
-> 201 {"success":true,"id":"vsgRmhabal7wHv1ZITBz"}
```

An anonymous attacker just planted a "feedback" row attributed to the CEO email with `isGuest:false`. If the support admin tool sorts by "logged-in user feedback" or auto-replies, this poisons the workflow.

Bonus: the same handler accepted `path:"<script>alert(1)</script>"` and `userAgent:"<img src=x onerror=alert(2)>"` -- both written raw to Firestore. If the admin console renders any of those fields without escaping, this is a stored-XSS chain into the support tool (P0 if confirmed; admin app needs to be checked separately).

## Suggested fix

1. If `req.user?.uid` is present, OVERWRITE `email` from `req.user.email` and ignore the body field. Force `isGuest = false`.
2. If guest, ignore the body `email` entirely (do not accept arbitrary impersonation strings) -- collect a reply email via a separate, validated form.
3. Sanitize `path` and `userAgent` to strict whitelists.
