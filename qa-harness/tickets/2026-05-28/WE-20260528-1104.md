# WE-20260528-1104 — No translation cache — repeated identical phrases pay 150-500ms Azure Translator round-trip each time

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / External-service caching
**File:** `easebot-backend/src/services/translation.ts`
**Discovered:** 2026-05-28

## Symptom
Live Azure Translator latency (eastus region, from local dev box):

| Call | Run 1 | Run 2 | Run 3 | Run 4 | Run 5 |
|---|---|---|---|---|---|
| `detect` | 408ms | 132ms | 103ms | 105ms | 442ms |
| `translate hi→en` | 1048ms | 968ms | 374ms | 126ms | 163ms |
| `translate en→hi` | 193ms | 138ms | 128ms | 99ms | 123ms |

For a non-English user message both `detect()` and `translate()` run on **every** turn — minimum ~225ms, sometimes 1.5s combined when Azure's edge is cold. Common short phrases like "हैलो", "मेरी शादी कब है", "checklist बनाओ" are translated identically every request.

Grep for caching in `services/translation.ts`: **zero matches**. No content-hash cache, no LRU.

## Root cause
`detectLanguage()` and `translateText()` both make direct REST calls with retry but no memoization. The retry helper makes cold starts worse: 2 retries × 500ms backoff = up to 1s additional on transient slowness.

## Suggested fix
1. Wrap both functions with `LRUCache<sha256(text), result>` keyed on the (text, fromLang, toLang) tuple. TTL 24h, max 5000 entries. Memory cost is trivial (mean phrase ~80 bytes + 200B value).
2. Skip `detect()` entirely when the chat request already carries `body.language` or the cached user-language preference is fresh (see `userPrefsCache.ts` pattern).
3. Track hit/miss via PostHog event `translation.cache` so we can validate ratio.

## Expected impact
For repeat phrases (very common in chat): translation latency drops from 150-500ms to <1ms. Realistic chat session with 70% cache-hit on a non-English speaker saves ~200ms × 0.7 = 140ms per turn TTFB.
