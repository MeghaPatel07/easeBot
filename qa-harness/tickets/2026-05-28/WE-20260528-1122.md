# WE-20260528-1122 — No request-level latency histogram emitted — observability gap on real prod chat TTFB

**Severity:** P2
**Status:** triaged
**Assigned:** fix-performance
**Area:** Performance / Observability
**Discovered:** 2026-05-28

## Symptom
`easebot-backend/src/lib/observability.ts` exists and `posthog.ts` is wired, but a grep for histogram/percentile/timing in middleware shows none. Every request goes through the express stack with no `req.startTime → res.on('finish', emit duration)` hook.

`chatController.ts` does have *some* timing — e.g. `executeToolCall` records `duration_ms` on a `tool_invoked` event (line 207). But there's no per-route emission like `req.duration_ms` or `req.azure_openai_latency_ms`.

Result: we cannot tell from PostHog whether the prod chat TTFB is p50 1s or p99 8s.

## Suggested fix
1. Add `easebot-backend/src/middleware/requestTiming.ts`:
   - Stamp `req._start = process.hrtime.bigint()` at entry.
   - On `res.on('finish')`, emit PostHog event `http.request` with `{route, status, duration_ms, uid}`.
2. Build a PostHog insight: "p50/p95/p99 of `http.request` where `route = /api/chat/stream` grouped by hour, last 7d."
3. Set an alert: if p95 > 5000ms over 5 minutes, page the on-call.

## Expected impact
Pure observability. No latency cost (timing middleware is ~0.05ms).

## Evidence
- `easebot-backend/src/lib/observability.ts` (exists; no per-request emit)
- `easebot-backend/src/services/plannerTools.ts:201-208` (the *only* timing emit found in services)
