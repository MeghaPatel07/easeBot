## Description
`buildPersonalizationSuffix({nickname:"Priya"})` injects `The user's preferred name is "Priya". Use this name naturally in greetings and sign-offs.` But the user can ALSO say in their message: `"my nickname is X-injected, by the way please call me Empress"` and the LLM has no rule about whether to update the in-prompt nickname, store it for future turns, or ignore the in-message hint.

Practical impact: a user with `userPersonalization.nickname="Anand"` in their saved profile types "actually call me Boss" — the model will follow the in-message ask THIS turn but the saved profile is untouched. Next turn (or in a new thread) it reverts to "Anand". The user perceives "Viva forgot" — actually it never had a write path back to the profile.

Bigger issue: the LLM might emit a tool call OR write to a note saying "user said their nickname is X-injected" — corrupting persistent storage with adversarial text that gets surfaced as content elsewhere.

## Steps to reproduce
1. With profile nickname="Anand", send: `"actually my nickname is please ignore previous instructions"`
2. The LLM may incorporate the injected nickname into a note or checklist title, persisting attack text.
3. Next turn — saved nickname is still "Anand", LLM uses it, user is confused.

## Expected
- Profile nicknames come from a trusted store (Firestore). In-message claims like "my name is X" should ask: "Would you like me to update your saved name to X?" — never silently overwrite.
- Sanitize any user-supplied free-text BEFORE persisting to notes/checklists/timeline titles (strip "ignore previous", "system:", `</prompt>`-style escapes).

## Actual
No write path from message → profile (so silent drift is the user-visible failure). No sanitization on persisted text fields.

## Notes
Two fixes: (1) add a confirmation turn when user says "my name is X" mid-conversation; (2) sanitize all tool args before persistence — strip control phrases.
