# WE-20260528-1526 — subscribeToThreads + subscribeToNotes share NO snapshot cache — each refire reallocates ChatThread[] and Note[]

**Severity:** P3
**Status:** triaged
**Assigned:** fix-frontend
**Area:** Performance / Memory churn
**Discovered:** 2026-05-28

## Symptom
Both `chatService.subscribeToThreads` and `notesService.subscribeToNotes` execute on every Firestore snapshot:
1. `snapshot.docs.map(d => ({ id, ...d.data() }))` — fresh objects
2. `.sort(...)` — in-place mutation on the fresh array
3. callback(threads) → React `setState(threads)` → reconciliation walk

Even if NOTHING changed (the snapshot fires on every `updatedAt` bump anywhere in the collection), the entire array is rebuilt. React's `setState(newArray)` is referentially unequal → all consumers re-render.

## Why this matters
- For a heavy user (100 threads), every thread.updatedAt bump triggers 100-doc array reallocation.
- The sidebar list re-renders even though only one item changed.

## Suggested fix
1. Memoize by computing a stable hash (e.g. updatedAt sum) and skip setState if the hash didn't change relative to previous snapshot.
2. Use `useSyncExternalStore` with a snapshot-equality check on the callback side.
3. Consider migrating to `react-firebase-hooks` which handles this internally.
