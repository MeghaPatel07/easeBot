## Description

`POST /api/tts` has no Zod schema. The controller reads `text` directly from `req.body` and only does an inline `text.slice(0, 5000)` AFTER first running 8+ heavy regex replaces on the **full input**. The Express body limit is 20 MB (`express.json({ limit: '20mb' })`), so an attacker can send a 19 MB string and the server will:

1. Pass the entire 19 MB through 8+ regex substitutions (CPU spike, possible ReDoS).
2. Cap to 5000 chars only after the regexes run.
3. Still ship the 5000-char output to Azure TTS, which returns up to ~16 MB of WAV.
4. Send the 16 MB WAV back to the attacker.

Proven: 200 K "hello " repeated → HTTP 200 with `Content-Length: 15610244` (15 MB WAV streamed back to caller).

Combined with the rate-limit budget of 30 req/min, a single attacker can cause ~450 MB/min of Azure→server→client bandwidth + 30× full-text regex passes per minute.

## Steps to reproduce

```
python3 -c "import json; print(json.dumps({'text':'hello '*200000}))" \
  | curl -sS -X POST http://localhost:3001/api/tts \
      -H 'Content-Type: application/json' -d @- --max-time 30 -i \
  | head -25
```

→ `HTTP/1.1 200 OK`, `Content-Length: 15610244`, `Content-Type: audio/wav`.

## Expected

1. Reject `text.length > 5000` with `400 Bad Request` BEFORE the regex pipeline runs.
2. Use a Zod schema like `{ text: z.string().min(1).max(5000), voiceName: z.enum([...]).optional(), language: z.string().max(10).optional() }`.
3. Cap the per-uid TTS bandwidth budget separately from the request-count rate limit.

## Actual

- No schema, entire payload runs through the regex pipeline first.
- Body returns up to ~16 MB regardless of caller's actual need.
