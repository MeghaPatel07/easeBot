## Description

The handler tries to be safe by returning `"If an account exists, a code has been sent."` for unknown emails (line 53). But then it explicitly differentiates Google-linked accounts (line 60):

```
if (!hasPassword) {
  res.status(400).json({ error: 'This account uses Google sign-in. Please sign in with Google.' })
  return
}
```

So response shapes are:
- Unknown email → HTTP 200 `{message:"If an account exists, ..."}`
- Known + Google → HTTP 400 `{error:"This account uses Google sign-in..."}`
- Known + password → HTTP 200 `{message:"If an account exists, ..."}`

An attacker can distinguish: (1) `[unknown email]` vs `[known Google account]` vs `[known password account]` purely from the response. Verified with real WeddingEase emails:

```
POST /api/auth/forgot-password/send-otp {"email":"shilpa@weddingease.ai"}
→ HTTP 400 {"error":"This account uses Google sign-in. Please sign in with Google."}

POST /api/auth/forgot-password/send-otp {"email":"megha@weddingease.ai"}
→ HTTP 400 {"error":"This account uses Google sign-in. Please sign in with Google."}

POST /api/auth/forgot-password/send-otp {"email":"not-a-real-user-xyz@nowhere.fake"}
→ HTTP 200 {"message":"If an account exists, a code has been sent."}
```

## Impact

- Lets an attacker pre-validate a corporate-email list to confirm which addresses are WeddingEase customers.
- Lets them learn the auth provider, so they can craft a Google phishing page rather than a generic one.
- Combined with the global apiRateLimiter (30/min/IP — and rate-limit fairness is also weak; see WE-20260528-1004), an attacker can enumerate ~1800 emails/hour.

## Suggested fix

Always return HTTP 200 with the generic `"If an account exists, a code has been sent."` message regardless of provider. For Google-linked accounts, send the user a real email saying *"You tried to reset your password, but this account uses Google sign-in. Please sign in with Google instead."* — exactly the info they need, but routed off the response channel.
