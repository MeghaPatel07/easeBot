## Description

`history` items declare `content: z.string()` with no `.max()`. Each item also has no overall array-size cap besides the implicit `historyLimit = 10`. So a client can send 10 history items × 50,000 chars each = 500KB of context. The request passes zod, reaches the LLM, and Azure OpenAI either errors with a vague "Connection error" or burns prompt-token quota.

In testing, 10×50KB returned `HTTP 500 {"error":"Connection error."}` — vendor error string leaks through the unsafe catch path (related to ticket 200). This is both a resource-abuse vector (free quota burn) and contributes to the vendor-leak issue.

## Steps to reproduce

```bash
python3 -c 'import json,sys; hist=[{"role":"user","content":"x"*50000} for _ in range(10)]; sys.stdout.write(json.dumps({"message":"hi","history":hist}))' \
  | curl -X POST http://localhost:3001/api/chat -H "Content-Type: application/json" --data-binary @-
```

## Expected

`history[i].content: z.string().max(4000)` (roughly 1000 tokens per history entry is more than enough). Total history payload should also be size-capped before reaching the LLM.

## Actual

Schema accepts any-length strings. Request reaches LLM. Vendor error leaks through.
