## Description

`/api/feedback` uses the guest-pass-through `requireAuth`, accepts a body with raw `feedback` string, and persists to Firestore returning a doc id (verified via a single test write returning HTTP 201 + `{"success":true,"id":"91uzWwWwkLXHQOv0XW1J"}`).

Two issues:

1. **Unauth writes**: any visitor — and any external script — can pile up Firestore docs in the `feedback` collection. Per the route comment, the only protection is the global `apiRateLimiter` at 30 req/min/IP. That is trivial to scale via residential proxies; cost of storage rises and admin UIs become unusable.
2. **Stored HTML**: the controller saves `feedback` verbatim. A POST with `feedback="<img src=x onerror=alert(1)>"` was accepted and persisted. If an internal admin tool ever renders feedback as `dangerouslySetInnerHTML`, this becomes stored XSS against admins (full DOM + auth-cookie access).

## Steps to reproduce

```bash
curl -X POST http://localhost:3001/api/feedback -H "Content-Type: application/json" -d '{"feedback":"<img src=x onerror=alert(1)>","rating":5}'
# → 201 {"success":true,"id":"..."}
```

## Expected

- Require a verified bearer token (use `requireStrictAuth` like the account routes do), OR
- Add a hidden CAPTCHA-equivalent (hCaptcha / Turnstile) for unauth submissions, AND
- Sanitize HTML server-side before storing (strip tags or DOMPurify on the JSDom side).

## Actual

Unauth write returns 201; HTML stored as-is.
