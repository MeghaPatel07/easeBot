## Description
The stream route reads the `Last-Event-ID` header on reconnect, logs it (`[chat:sse] Client reconnecting with Last-Event-ID: …`), then ignores it. A client reconnecting after a dropped connection re-receives the full response from id:1 onward, not the suffix starting after the last seen id. EventSource auto-reconnect with Last-Event-ID is the standard SSE recovery protocol and the frontend likely depends on it.

## Steps to reproduce
1. Start an SSE stream with a long-running request.
2. Drop the connection at id:10.
3. Reconnect to the same `requestId` with `Last-Event-ID: 10`.
4. Server starts a fresh response from id:1, not from id:11.

## Expected
Either:
- (a) Reconnect with Last-Event-ID resumes the original response from id:N+1 (requires server-side buffering of stream frames per requestId).
- (b) Server responds with HTTP 410 or an explicit `replayUnsupported:true` SSE event so the client knows not to expect resume.

## Actual
Logged-and-forgotten. Client sees a full restart silently, which on a 10s-streamed response means perceived duplicate text.

## Notes
Replay buffering is non-trivial. The simpler interim fix is option (b): document `replayUnsupported` and have the client suppress duplicate replay.
