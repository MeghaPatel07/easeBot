## Description
The non-streaming chat handler builds a regex from each `imageUrls[]` entry to strip duplicate markdown image tags from the LLM output:
```ts
const esc = u.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
textForClient = textForClient.replace(new RegExp(`!\\[[^\\]]*\\]\\(${esc}\\)`, 'g'), '')
```
For a guest user, `imageUrls[]` contains full `data:image/png;base64,…` blobs (~600KB each). Passing a 600KB string into `new RegExp(…)` throws `Invalid regular expression: …: Regular expression too large` in V8, which surfaces to the user as a 500 error with the giant base64 in the response body.

The **streaming** handler at line 1640-1648 has already been fixed with `if (!u || u.startsWith('data:')) continue` and a leading comment explaining the issue. **The non-stream handler at line 1058-1064 was missed.**

## Steps to reproduce
1. `curl -X POST http://localhost:3001/api/chat -d '{"message":"Draw me an image of a wedding mandap with marigolds","forceImageGeneration":true}'`
2. With a guest user (no Authorization header), observe HTTP 500 with `{"error":"Invalid regular expression: /!\\[[^\\]]*\\]\\(data:image\\/png;base64,…"}` and a multi-hundred-KB body.

## Expected
- The data: URI should be skipped during the de-duplication pass (same as the stream handler).
- Response should be HTTP 200 with the image surfaced via `imageUrls`.

## Actual
HTTP 500 with the regex-build error and the full base64 blob in the error body. This also creates a bandwidth amplification (small request → massive response).
