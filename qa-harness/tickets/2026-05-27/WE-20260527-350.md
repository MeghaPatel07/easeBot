## Description
The planner system prompt rule states: "Maximum 3-5 checklist items per response. Never dump full timelines." The LLM repeatedly violates this in production. With a guest-user request asking for a "full 12-month timeline" or "detailed task list", planner mode returns 31 and 39 numbered items respectively, broken into 5+ time bracket subsections — exactly what the contract forbids.

## Steps to reproduce
1. `curl -X POST http://localhost:3001/api/chat -H 'Content-Type: application/json' -d '{"message":"Give me a full 12-month wedding planning timeline with everything I need to do"}'`
2. Count numbered list items in the `text` field.

## Expected
≤ 5 numbered checklist items per response, per planner.ts:53 "RESPONSE RULES".

## Actual
- Test 1 ("Give me a full 12-month wedding planning timeline…") → **31 numbered items** across 7 time brackets, 2407 chars.
- Test 5 ("Make me a detailed task list to plan the wedding step by step") → **39 numbered items** across 7 time brackets, 3307 chars.
- Test 2 ("What vendors do I need to book?") → **10 items**.

## Notes
Either the system prompt needs hardening (the LLM is ignoring the "Maximum 3-5" line) or the controller needs a post-LLM length-check that re-prompts with "shorten to 3-5 items" when it overruns. The prompt itself contradicts: line 53 caps items at 3-5, but lines 63-66 describe building 12-6-3-1 month timelines, which encourages the model to dump everything.

## Resolution (2026-05-29)
Fix shape: prompt-only, +8 / -2 lines in `easebot-backend/src/prompts/planner.ts`.
1. Hoisted a new `HARD LIMIT` block to the top of the prompt with explicit trigger phrases, a structured-output recipe for "full timeline" requests, an example opener, and a DO / DON'T line.
2. Re-worded the contradictory `12–6–3–1 month milestones` line under `Your role` to make clear phases are walked ONE per reply.
3. Cross-referenced the existing RESPONSE RULES cap to the new HARD LIMIT.

Verification: `npx tsc --noEmit` clean. Live LLM smoke test requires `.env` with Azure OpenAI keys (not in worktree) — repro steps documented in `qa-harness/evidence/WE-20260527-350/after-fix-notes.md`.
