## Description

`ChatRequestSchema` declares `imageData` and `imageMimeType` as the image-payload fields. But the controller destructures `imageBase64` and reads it everywhere (lines 651, 653, 774, 932, 964). The schema field is never used. Because `ChatRequestSchema` does not list `imageBase64` and does not call `.strict()`, the field passes through unchecked — Zod's default behavior is to ignore unknown keys.

Effect:
- `imageBase64` has NO max-length enforcement (the imageData cap from ticket 202 is moot; attacker just uses imageBase64).
- `audioBase64` is referenced at line 653 but does not exist in the schema either — same bypass.
- `lastGeneratedImageUrl`, `styleMemory`, `userPersonalization` (all at line 651) are likewise read by the controller but absent from the schema.

This is a static-typing-doesn't-help bug: TypeScript trusts `as ChatPayload` cast on line 651 but zod sees nothing.

## Steps to reproduce

```bash
# 19MB junk via imageBase64 (NOT imageData), succeeds at 200
python3 -c 'import json,sys; sys.stdout.write(json.dumps({"message":"hi","imageBase64":"a"*(19*1024*1024),"imageMimeType":"image/png"}))' \
  | curl -X POST http://localhost:3001/api/chat -H "Content-Type: application/json" --data-binary @-
```

## Expected

1. Add `imageBase64`, `audioBase64`, `userPersonalization`, `lastGeneratedImageUrl`, `styleMemory` to the schema.
2. Add `.strict()` so unknown keys are rejected.
3. Cap base64 lengths (e.g. `~5_000_000` chars).
4. Optionally rename one side so the destructure matches the schema.

## Actual

Schema and controller are out of sync. Validation provides false confidence.
