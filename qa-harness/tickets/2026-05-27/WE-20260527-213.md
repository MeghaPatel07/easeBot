## Description

The SSE wrapper sets up a 15-second heartbeat (`: heartbeat\n\n`) and a `req.on('close')` hook to clear the interval. The route comment itself acknowledges that "reverse proxies and LBs often hold the upstream socket open so `req.on('close')` never fires" — which is exactly why the `/api/chat/cancel` endpoint exists. However: in dev (no proxy) `req.on('close')` does fire, but the controller's underlying Azure OpenAI stream call is NOT abort-coupled to the close event in all paths.

When a client kills its curl mid-stream, the heartbeat interval clears, but the running Azure call continues until completion, generates tokens, hits Firestore writes, and may still charge the user's token quota. Confirmed empirically: 5 parallel streams started, immediately killed clients — backend kept running and eventually responded with the full completion in the next request's prompt history.

## Steps to reproduce

1. Start `curl -N -X POST http://localhost:3001/api/chat/stream -d '{"message":"give me a 500-word essay"}'`
2. After 2 seconds, kill the curl process.
3. Server-side: confirm via logs that the stream handler completed all chunks and reached `[chat:sse] heartbeat cleared` only after the FULL Azure completion (not at kill time).

## Expected

- `req.on('close')` should signal an `AbortController` passed into the Azure OpenAI SDK call.
- Cancellation registry should auto-revoke the request id.
- Token charge should be refunded for unconsumed tokens (the controller's catch block at line 1108 hints this exists, but verify it fires on user-disconnect).

## Actual

Stream continues to completion after client kill (in dev — no proxy in the path).
