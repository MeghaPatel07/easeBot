## Description

`validateBody` returns `{ error: 'Validation failed', details: zodError.errors }` with the full ZodIssue array, exposing internals: `code`, `expected`, `received`, `inclusive`, `exact`, `minimum`, `maximum`, `path`, plus the human message. This advertises the entire request-schema shape to anyone who can hit the endpoint (including unauthenticated guests on /api/chat). An attacker can enumerate optional/required fields, max sizes, and enum values without legitimate access.

## Steps to reproduce

1. `curl -X POST http://localhost:3001/api/chat -H "Content-Type: application/json" -d '{}'`
2. Observe the entire schema gets reflected back via zod issue path lists.

## Expected

In production: opaque `{ error: "Validation failed", code: "VALIDATION_ERROR" }`. In dev: full details OK.

## Actual

```json
{"error":"Validation failed","details":[{"code":"too_big","maximum":10000,"type":"string","inclusive":true,"exact":false,"message":"String must contain at most 10000 character(s)","path":["message"]}]}
```

## Evidence

- `qa-harness/evidence/WE-20260527-203/curl.log`

## Notes

Gate `details` behind `NODE_ENV !== 'production'`, or transform Zod issues into a minimal `[{ field, message }]` shape and drop the rest.
