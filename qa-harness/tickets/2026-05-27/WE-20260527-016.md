## Description

Selecting "Engagement" then asking "What should I wear for the bride?" returns a thoughtful response, but the response is generic to any engagement — there is no indication the selected occasion is being forwarded to the backend. Inspecting the `POST /api/chat/stream` request body shows only `{message, mode}` — no `occasion` field. The user-visible response includes "Engagement outfits are…" only because the user typed the word.

Without forwarding occasion to the backend (occasion appears nowhere in the SSE payload visible), users selecting "Haldi", "Mehendi", etc. and then asking "What should I wear?" will not get occasion-aware replies. The chip exists for visual signal but has no contract with the AI.

## Steps to reproduce

1. Open `http://localhost:8081/`, dismiss consent.
2. Select "Haldi" chip.
3. Type "What should I wear?" → press Enter.
4. Watch DevTools network → `POST /api/chat/stream` body.

## Expected

Request body contains `{ message, mode, occasion: "haldi" }` (or system prompt is augmented), and the assistant tailors to haldi (yellow/floral palette, marigold, etc.).

## Actual

No occasion in request payload. Response is generic to whatever keyword the user typed.

## Evidence

- Network log in `qa-flow.mjs` shows only `200 http://localhost:3001/api/chat/stream`. Need to inspect body via interception — but the source code (`Index.tsx:1630`) only mutates local state.

## Notes

This is a contract gap: a prominent UI element implies a behavior that's not implemented.
