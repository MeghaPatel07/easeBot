## Description

After a few QA requests from the same IP, the backend returns `HTTP/1.1 429 Too Many Requests`. The response headers shown are:
```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Resource-Policy: same-origin
Origin-Agent-Cluster: ?1
Referrer-Policy: no-referrer
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
X-DNS-Prefetch-Control: off
X-Download-Options: noopen
X-Frame-Options: SAMEORIGIN
```
No `Retry-After` header is present, no `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`. Clients can't back off intelligently — they must guess.

## Steps to reproduce

1. `for i in 1..50; do curl -X POST http://localhost:3001/api/chat/stream -d '{}'; done`.
2. Observe response headers when 429 fires.

## Expected

Standard rate-limit headers per IETF RFC 6585:
```
Retry-After: 60
X-RateLimit-Limit: 30
X-RateLimit-Remaining: 0
X-RateLimit-Reset: <unix-ts>
```

## Actual

No rate-limit metadata.

## Fix summary (2026-05-29)

Refactored `easebot-backend/src/middleware/rateLimiter.ts`:

1. Switched `standardHeaders: true` → `standardHeaders: 'draft-7'` on all three limiters. Now emits the modern combined header `RateLimit: limit=N, remaining=N, reset=N` + `RateLimit-Policy: N;w=W` + `Retry-After: <seconds>` (auto-set by the lib on 429).
2. Replaced opaque `message` option with custom `handler`s that emit a structured JSON body: `{ "error": "rate_limited", "retry_after": <seconds>, "limit": <n>, "window_seconds": <n>, "scope": "<api|chat_burst|image>" }`. The `chatBurstRateLimiter` preserves `code: "chat_burst_limit"` for back-compat with observability alerts.
3. Added `RateLimitInfo` type augmentation on `Express.Request` for typed access to `req.rateLimit.resetTime`.
4. Added `src/middleware/__tests__/rateLimiter.test.ts` (3 tests) and an `inspectHeaders.ts` evidence tool. Wired `npm run test:rate-limit` into `npm run test:all`.

Per-uid bucketing for chat is already handled by `chatBurstRateLimiter`'s `keyGenerator` (uses `req.user?.uid || guestFingerprint(req)`). The `apiRateLimiter` and `imageRateLimiter` still bucket by IP — separating guest vs authed buckets there is the same problem as backlog item -1009 (needs Redis decision); deferred per Krish.
