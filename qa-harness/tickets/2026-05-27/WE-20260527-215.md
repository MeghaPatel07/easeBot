## Description

Every router is mounted at BOTH `/api/<name>` and `/api/v1/<name>`. Both paths share the same handlers, middleware order, and validation. Any security regression on one path applies to the other; conversely, future v1-only fixes must remember to backport to /api/, and vice versa. This kind of mirror has historically been the source of WAF bypasses where attackers find one path is rate-limited and the other isn't.

In testing, `/api/v1/chat` accepted the same unauth requests as `/api/chat`. The chat-burst rate-limiter is keyed on the same fingerprint, but having two URLs doubles the surface area for cache-poisoning, anomaly-detection alerts, and bot-detection rules.

## Steps to reproduce

```bash
curl -X POST http://localhost:3001/api/chat    -d '{"message":"hi"}' -H "Content-Type: application/json"  # 200
curl -X POST http://localhost:3001/api/v1/chat -d '{"message":"hi"}' -H "Content-Type: application/json"  # 200 — identical
```

## Expected

Either deprecate `/api/` (keep `/api/v1/` only) and have the unversioned path 301 to the v1 path, OR explicitly document the mirror in code comments and add an integration test to assert that EVERY rate-limit / auth rule applies on both paths.

## Actual

Mirrored silently in app.ts:89 via a for-loop. No assertion that future routes obey the mirror correctly.
