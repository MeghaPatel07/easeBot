## Description

Per the code comment at lines 54-56:

> Guest requests (uid === null) can be cancelled by anyone with the requestId since the id itself is the only capability the client has.

The requestId is client-supplied, in-process, and currently appears to be unauthenticated. If the requestId is short (UUID-like is fine; integer-incrementing is bad) or guessable, any guest who knows or guesses another guest's requestId can abort it. The cancel endpoint responds 204 regardless of `cancelled` vs `not_found` outcomes — so an attacker can probe IDs blindly.

The 204-for-not-found behavior also masks the case where the abuse is happening.

## Steps to reproduce

1. Open two guest sessions (different browsers / curl with different fingerprints).
2. From session A, observe what requestId session B is using (via shared network, side channel, or brute force if the id is sequential).
3. `curl -X POST http://localhost:3001/api/chat/cancel -d '{"requestId":"<B id>"}'` → 204.
4. Session B sees its stream aborted.

## Expected

- Use cryptographically-strong, 128-bit UUIDs for requestId.
- Bind the requestId to the request's IP-fingerprint for guests (so cross-fingerprint cancels are 403).
- Differentiate 204 (cancelled) from 404 (not found) — let the client tell the user "this request is already done" vs "we aborted it".

## Actual

Same 204 for any input; no fingerprint binding for guests.
