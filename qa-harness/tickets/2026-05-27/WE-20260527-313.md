# WE-20260527-313 — Dev server measurement (LCP 89 s) confirms HMR / source-loading pipeline is too slow even for local QA

**Severity:** P3
**Status:** triaged
**Assigned:** fix-performance
**Area:** Developer experience
**Page:** http://localhost:8081/
**Discovered:** 2026-05-27

## Symptom
Lighthouse on the **dev server** (Vite + HMR + esbuild on-demand) reported:
- LCP **88.9 s**, FCP **47.1 s**, TTI **89.0 s**
- 256 network requests, 15.1 MB total transfer
- `chunk-RPCDYKBN.js` (Vite's optimized-deps shim) is 928 kB raw on the first request

This is artificial — the production build (`vite preview`) measured LCP 9.9 s. But the dev server is so slow on cold start that any QA agent measuring `localhost:8081/` is getting garbage data and could file false tickets. The original prompt directed me to measure `localhost:8081` — I deliberately swapped to the prod-preview build to avoid this trap.

## Why surface it
1. Other QA agents (Marcus, Anya, etc.) running Lighthouse against `localhost:8081` are getting useless numbers and may be filing nonsense regressions.
2. The dev experience itself (waiting 50+ s for first paint) is painful for Krish.

## Suggested fix
1. Document in `CLAUDE.md` that all perf QA must run against `npm run build && npm run preview` (port 4173), not the dev server.
2. Investigate why the dev server is so slow:
   - 928 kB in the optimized-deps shim suggests Firebase + Radix bundles aren't pre-bundled cleanly.
   - `optimizeDeps.include` in `vite.config.ts` could help warm the cache.
   - The `lovable-tagger` plugin runs only in dev — confirm it isn't the culprit by toggling it off.
3. Consider switching to Vite 6 + Rolldown for faster dev cold-start.
