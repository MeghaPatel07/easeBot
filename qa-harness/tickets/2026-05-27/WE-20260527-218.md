## Description

When `/api/chat/stream` receives an empty body, the response is HTTP 200 with an SSE event containing `{"t":"e","msg":"message, audioBase64, or imageBase64 is required"}`. Two issues:

1. The HTTP status code is 200, NOT 4xx — front-end fetch wrappers that gate on `response.ok` will believe the request succeeded.
2. Other validation paths return 4xx JSON (non-SSE). The stream endpoint is inconsistent: some validation hits zod (returns 400 JSON), some hits the controller (returns 200 SSE error frame).

Effect: front-end error handling for the stream path needs to inspect both response status AND the first frame's `t` field. That's brittle and a likely source of "stuck loading" bugs.

## Steps to reproduce

```bash
curl -N -X POST http://localhost:3001/api/chat/stream -H "Content-Type: application/json" --data-binary ''
# HTTP/1.1 200 OK
# id: 1
# data: {"t":"e","msg":"message, audioBase64, or imageBase64 is required"}
```

## Expected

- Validation failures on `/stream` should return HTTP 4xx with JSON body, just like `/api/chat`, BEFORE opening the SSE stream.
- If headers are already sent, an error event frame is fine, but headers should NOT yet be flushed at validation time.

## Actual

200 OK + SSE error frame.
