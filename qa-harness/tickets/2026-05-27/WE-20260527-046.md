## Description

Sending an invalid payload to the chat stream:
```
curl -X POST http://localhost:3001/api/chat/stream -H "Content-Type: application/json" -d '{"text":"hi"}'
```
Returns HTTP 200 with body:
```
id: 1
data: {"t":"e","msg":"message, audioBase64, or imageBase64 is required"}
```

The error is wrapped in SSE format with a `t: "e"` discriminator and HTTP 200. Generic HTTP clients (curl, monitoring tools, dev frontends not yet on the SSE consumer) will see "success" status with an error payload — confusing. Standard REST behaviour is HTTP 400 for validation errors.

## Steps to reproduce

1. `curl -fsS -X POST http://localhost:3001/api/chat/stream -H 'Content-Type: application/json' -d '{"text":"hi"}'`.

## Expected

HTTP 400 with JSON body `{ "error": "message, audioBase64, or imageBase64 is required" }`. For SSE-aware clients, the server can still stream the error event before closing — but the status code should be a client error.

## Actual

HTTP 200 + SSE error event.

## Evidence

- Curl output captured in this QA session.

## Notes

The OpenAPI / contract docs need to clarify this is intentional SSE design. If kept, document the `t:"e"` discriminator publicly.
