## Description

Flow A step 3 (first-time guest → first chat) is broken end-to-end on the very first interaction. When a fresh browser context lands on `/`, the `AnalyticsConsent` dialog renders as a fixed modal at the bottom-center of the viewport with `z-[100]`. Although it is *visually* below the chat input, its rounded surface and surrounding clickable area sit on top of the input/composer such that Playwright (and presumably real users with imprecise taps) cannot click into the textarea. Playwright retries 57+ times across 30s before timing out — every attempt is intercepted by `<div role="dialog" aria-label="Analytics consent">`.

This is distinct from ticket **WE-20260527-050** which describes the visual overlap. This ticket describes the *interaction* failure: the consent dialog **breaks the primary first-time-user CTA path** because the user has to find and dismiss the consent banner before they can type their first message. Many users will assume the input is disabled or broken and bounce.

After dismissing the consent (click "Accept" or "Decline"), the chat input becomes immediately interactive and Flow A completes cleanly (verified — message sent, AI streamed reply, guest cap banner appeared at message ~10).

## Steps to reproduce

1. Open a fresh, incognito browser context.
2. Navigate to `http://localhost:8081/`.
3. Wait for landing UI to render fully (~2s).
4. Without scrolling or dismissing anything, click into the "ask me anything" textarea.

## Expected

The textarea is immediately focusable on first click; consent dialog must not intercept pointer events targeting the chat composer (either dialog should not overlay the input, or its hit-area should be tight to the visible card with `pointer-events: none` on its container backdrop).

## Actual

The chat textarea is visible/enabled/stable per the DOM but `<div role="dialog" aria-label="Analytics consent">` subtree intercepts the pointer event. The click is consumed by the consent dialog's invisible area; the textarea never receives focus. Repeated retries also fail.

Playwright log excerpt:
> "element is visible, enabled and stable" → "scrolling into view if needed" → "done scrolling" → "<div...AnalyticsConsent.tsx...> subtree intercepts pointer events" → "retrying click action" × 57

## Notes

- Cross-reference WE-20260527-050 (visual overlay) — same root component, but this ticket is the *interaction* impact, which is much more severe than visual.
- Fix direction candidates:
  - Move the consent dialog to a smaller, top-right toast that doesn't overlap the bottom composer.
  - Add `pointer-events: none` to the dialog's outer container, with `pointer-events: auto` only on the card itself, so transparent margin around the card doesn't capture clicks.
  - Auto-dismiss on first chat-input focus attempt (the user is signaling intent).
  - Lower z-index so chat input is in front; consent still visible but not interactive-blocking.
- All 6 e2e journeys verified that this blocks the first interaction; J2/J5/J6 worked because they navigated *away* from `/` first.
