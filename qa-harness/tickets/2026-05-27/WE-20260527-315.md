# WE-20260527-315 — Could not measure SSE first-token latency / image-gen latency — backend health endpoint returns 404

**Severity:** P2 (BLOCKER for backend perf QA)
**Area:** Performance / Backend SSE
**Page:** Backend http://localhost:3001/
**Discovered:** 2026-05-27

## Symptom
The QA brief asks for SSE first-token latency and image-gen latency measurements. Attempts to probe the backend returned:
```
curl http://localhost:3001/  → HTTP 404
```

No root health endpoint. To measure SSE/image latency we need either:
1. A reproducible chat-stream endpoint reachable without auth (`/api/health/stream`?), or
2. A test thread + service-account auth flow documented somewhere.

`src/hooks/useChat.ts` line 511 streams via `streamChatMessage(...)` from `@/services/functionsService`. The route, headers, payload, and auth requirements aren't trivial to reverse-engineer from a perf-QA pass.

## What I tried
- `curl http://localhost:3001/` → 404
- No `.env.local` examined (forbidden by hooks)
- No `Wedding-Ease-Viva-Chat/src/config/api.ts` inspected yet — possibly contains the routes

## Blocker, not solvable from this seat
- Backend has no exposed perf endpoint
- Auth/CSRF wrapped SSE → can't be hit from curl without a real Firebase ID token
- Without these, P95 first-token latency, time-to-first-image, and abort-handling latency cannot be measured

## Suggested fix
1. Add a backend route `GET /healthz/stream-latency` that emits a 5-token SSE stream with no auth (rate-limited by IP). Returns timing markers. Use this for synthetic monitoring.
2. Or document the curl + Firebase ID token flow for QA agents in `easebot-backend/README.md`.
3. Add PostHog `track('first_token_received', { latencyMs })` and `track('first_image_received', { latencyMs })` in `useChat.ts` — instrument the actual user flow.

## Suggested verification
Once instrumented, set SLO: SSE first token < 500 ms p75, first image < 4 s p75. File regression tickets if either slips.
