## Description

`requestId` is taken straight from the client request body (chatController.ts:1140-1147). Two concurrent requests with the same id silently overwrite each other in `registry.set`. Effect:

- The first request's AbortController is no longer reachable; it cannot be cancelled.
- If the first request hangs / leaks, the registry holds no reference to abort it; only the TTL sweep (every 60s, eligible after 10min) will free it.
- A malicious client can deliberately collide on a static id like `"abc"` to override any in-flight legitimate request's cancellation handle.

Empirically verified: two concurrent streams with `requestId: "collide-abc"` both completed (50 + 54 chunks); the registry entry for request 1 was replaced by request 2.

## Steps to reproduce

```bash
# Window 1
curl -N -X POST http://localhost:3001/api/chat/stream -d '{"message":"...","requestId":"collide-abc"}'
# Window 2 (start during window 1)
curl -N -X POST http://localhost:3001/api/chat/stream -d '{"message":"...","requestId":"collide-abc"}'
# Now POST /api/chat/cancel {"requestId":"collide-abc"} — only window 2 aborts.
```

## Expected

- Reject duplicate requestIds (return 409 Conflict from the stream endpoint).
- OR generate the requestId server-side and return it in a header (so the client can't collide).
- Detect collision in `register()` and abort the prior entry's controller (preferable to leaking it).

## Actual

Silent overwrite. Prior request becomes uncancellable.
