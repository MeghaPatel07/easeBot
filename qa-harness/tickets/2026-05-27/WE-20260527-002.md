## Description

A guest sends the prompt "Generate an image of pastel mandap with white roses". The bubble immediately shows "generating... creating your image" and the request POSTs to `http://localhost:3001/api/chat/stream` (returns HTTP 200, SSE). After ~110s the placeholder is replaced with "Something went wrong. Please try again." No image ever renders. No image is added to the gallery. The free-tier image counter stays at 3.

This blocks the documented Gemini-primary / Azure-fallback image pipeline end-to-end for guest users.

## Steps to reproduce

1. Open `http://localhost:8081/` as a guest (incognito).
2. Dismiss the analytics consent banner.
3. In the chat input type: `Generate an image of pastel mandap with white roses` and press Enter.
4. Wait up to 2 minutes.

## Expected

Either (a) an image renders inline within ~30 s, the gallery and image counter update, **or** (b) a clear, fast failure path with a useful error message and no token/quota debit.

## Actual

After ~110s the bubble swaps to the generic "Something went wrong. Please try again." string. No actionable error code, no retry payload visible, and the image counter does NOT decrement (so token-debit behaviour on failure is at least correct, but the UX is broken).

Polling output (every 10s) confirms no `<img>` element ever appears beyond static UI assets.

## Fix (2026-05-29 by fix-backend-api)

**Root cause**: `callAzureImageGeneration` and `callAzureImageEdit` in `easebot-backend/src/services/imageGeneration.ts` invoked `fetch()` with only the caller's `AbortSignal` (the SSE stream's signal). No per-attempt timeout. When Azure stalled, fetch waited indefinitely until the upstream client cut the SSE (~110s), surfacing as the catch-all `sse({ t: 'e', msg: err.message })` envelope that the frontend (`useChat.ts:582`) re-throws and renders as the generic "Something went wrong. Please try again." (`useChat.ts:829`).

**Fix**: Added a `withTimeoutSignal()` helper that composes the caller's `AbortSignal` with a fresh `AbortController` armed by `setTimeout(60_000)`. Both Azure fetch sites now race the upstream signal against a 60s timer. On timeout, fetch throws `TimeoutError` → existing fallback chain (GPT-Image-1.5 → GPT-Image-1) runs → ultimately resolves to the actionable "Image generation failed. The service may be temporarily unavailable." tool result that the LLM rephrases for the user.

Also added structured `status` + `code` on Errors thrown from non-2xx Azure responses so `withRetry`'s default retryable() check sees 429/5xx and retries instead of giving up after one transient hiccup.
