## Description

Express body limit is 20MB (`express.json({ limit: '20mb' })`). The `ChatRequestSchema` accepts `imageData: z.string().optional()` with NO format and NO max-length. A malicious client can repeatedly POST 19MB junk strings; the server allocates and zod-parses each one before any further check. Combined with the guest-pass-through auth (no token required) and the chat-burst limit being only 10/10s, an unauthenticated attacker can sustain ~190 MB/s of memory pressure.

## Steps to reproduce

1. Send a 19MB body where `imageData` is `"a".repeat(19*1024*1024)`:
   `python3 -c '...' | curl -s -X POST http://localhost:3001/api/chat -H "Content-Type: application/json" --data-binary @-`
2. Observe HTTP 200, normal text response. No validation kicks in.

## Expected

Reject obviously-malformed `imageData` (it must be a data URL or pure base64 with a sane max length, e.g. ~5MB) with HTTP 413 / 400 before zod sees it.

## Actual

200 OK with normal chat response; backend silently accepted and discarded the bogus image.

## Evidence

- `qa-harness/evidence/WE-20260527-202/payload-sizes.txt`

## Notes

Recommended schema: `imageData: z.string().regex(/^(data:image\/[a-z]+;base64,)?[A-Za-z0-9+/=]+$/).max(5_000_000).optional()`.

Lower the express body limit to ~8MB if chat doesn't legitimately need 20MB.
